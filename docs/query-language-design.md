# Язык запросов как источник — постановка

Дата: 2026-08-17. Статус: согласовано с владельцем; текущее состояние реализации
зафиксировано в `CHANGELOG.md`.

## Зачем

Сервер описывает структуру конфигурации и синтаксис платформы, но не язык
запросов. Граница проверена поимённо: в `shcntx_ru.hbk` нет ни `ВЫБРАТЬ`, ни
`ГДЕ`, ни `ЕСТЬNULL`, ни `ВЫРАЗИТЬ`.

Подтверждено на живом агенте 2026-08-16: владелец попросил стороннего агента
собрать запрос и спросил, откуда что взято. Тот разделил честно — структура
объектов и связи от сервера, грамматика из собственной памяти, «синтаксис
запросов сервер не отдаёт».

Риск не в `ВЫБРАТЬ`: грамматика стабильна, и модель её знает. Риск в тонкостях —
параметры виртуальных таблиц, `РАЗРЕШЁННЫЕ`, `ИТОГИ ПО` с иерархией, поведение
`ЕСТЬ NULL` с составными типами. Там модель ошибается уверенно, и проверить
нечем.

## Что измерено

Файлы из поставки, замер 2026-08-17 на `exporter-1c/shquery_ru.hbk`:

| Показатель | Значение |
|---|---|
| Файл | 169 КБ |
| Записей в контейнере | 7 (`FileStorage` — zip на 153 КБ) |
| Страниц внутри | 128 + служебный `__categories__` |
| Разметки суммарно | 366 КБ, медиана страницы 1 438 Б |
| Крупных (>8 КБ) | 9, максимум 24,8 КБ (`present.html`) |
| Средних (2–8 КБ) | 44 |
| Мелких (<2 КБ) | 75 |
| Чтение контейнера | 0,01 с |

Для сравнения: справка платформы — 25 511 страниц, слитый индекс на пяти
версиях 25 701 элемент и 109 МБ. Язык запросов — **0,75% по числу страниц**.

Два факта, изменившие постановку по сравнению с записью в доске задач:

1. **Это не сплошная проза.** Страниц-функций **52**: 47 с заголовком
   «Функция …» и 5 с «Агрегатная функция …». Остальные 76 — операторы, секции,
   ключевые слова, литералы и длинные статьи.

   Уточнено 2026-08-17 после первой реализации. Прежняя запись «33 страницы
   несут сигнатуру в первом абзаце» была получена грубой эвристикой и оказалась
   неверной вдвойне: функций больше, а сигнатура лежит не там. Где она на самом
   деле:

   | Где сигнатура | Страниц |
   |---|---|
   | в `<PRE>` | 28 |
   | первой строкой первого абзаца | 2 |
   | скобка есть, форма иная | 1 |
   | формальной сигнатуры нет вовсе | 21 |

   `Функция МЕСЯЦ`, `Функция ГОД`, `Агрегатная функция СРЕДНЕЕ` описаны прозой —
   и это нормально, они всё равно функции. Отсюда правило: **вид определяется
   заголовком, а не наличием сигнатуры**; сигнатура извлекается, когда есть.

   **Уточнено замером в задаче 6 (2026-08-17).** Прямой прогон парсера по
   живому `shquery_ru.hbk` (не по памяти, не по эвристике) даёт другое
   распределение: сигнатура из `<PRE>` — у **27** страниц, первой строкой
   первого абзаца — у **3**, формальной сигнатуры нет вовсе — у **22**
   (27 + 3 + 22 = 52 без остатка). Заполнена сигнатура итого у **30** из 52
   функций. Таблица выше — предыдущий проход, ещё до того, как код стал
   надёжно отличать `<PRE>`-сигнатуру от абзацной; вывод раздела («вид
   определяется заголовком, а не сигнатурой») от расхождения не меняется.

2. **Версий появления в файле нет.** В `__categories__` рядом с каждой
   страницей стоят контексты исполнения (`CONFIG`, `ENTERPRISE`,
   `MNG_ENTERPRISE`, `WEB_ENTERPRISE`) и три поля версии — и **все 624 отметки
   равны `0.0.0`**. Тот же почерк, что у справки 8.3.5, где отметок «начиная с
   версии» не было ни на одной из 18 936 страниц.

Подзаголовков `H2` почти нет (2 страницы из 128), поэтому резать страницу на
части нечего: **одна страница — один элемент**.

## Решения и на чём они стоят

| Решение | Основание |
|---|---|
| Тот же MCP-сервер, не отдельный | 0,75% объёма против 300–450 МБ на контейнер и второй адрес. Главное — агент не делает второго шага сам (проверено 2026-08-17 на пометке «есть замена»), а польза от статьи про виртуальные таблицы появляется только вместе с именами регистров конкретной конфигурации |
| Только `shquery_ru.hbk` | В `shlang_ru.hbk` — грамматика встроенного языка, которую модель и так знает. Взять можно позже, если появится промах |
| Тот же поисковый индекс, новые виды | Правило `tools.py`: источник обогащает ответы существующих инструментов, а не добавляет новых. Каждый инструмент висит в контексте агента постоянно |
| Распознавание по содержимому | На имя файла полагаться нельзя: справки у нас лежат переименованными (`syntax-8.3.5.1570.hbk`) |
| Версий нет — экземпляр один | Из данных версии не выводятся, сравнивать нечего |
| Крупные статьи целиком только по имени | 8–25 КБ это 2–7 тыс. токенов; в выдаче поиска столько же на десять строк недопустимо |

## Модель данных

Новых классов не заводится. Используются существующие `SyntaxItem`,
`SyntaxVariant`, `SyntaxParam` из `syntax_model.py`.

Три новых вида рядом с `query_table` и `query_field`:

| Вид | Что это | Сколько | Что заполняется |
|---|---|---|---|
| `query_function` | функции языка запросов | 52 | `description`, а `variants[0].signature` и `params` — когда сигнатура на странице есть |
| `query_keyword` | операторы, секции, ключевые слова, литералы | ~67 | `description` |
| `query_article` | длинные статьи | 8 | `description` целиком |

Граница вида — **заголовок**: «Функция …» и «Агрегатная функция …» дают
`query_function`, длина страницы отделяет статью от ключевого слова.
Определять функцию по наличию сигнатуры нельзя: у 22 из 52 её нет.

Поля:

- `id` — `query/<имя страницы>`, например `query/LEFTJOIN`.
- `name_ru` — русский заголовок из `<H1>` без слова «Функция»: `КОНЕЦПЕРИОДА`,
  `Левое внешнее соединение`.
- `name_en` — имя страницы (`LEFTJOIN`, `ENDOFPERIOD`) как запасной ключ.
- `since`, `until` — **всегда пустые**. Фильтр версии пропускает такие элементы
  сам собой (`available_in_tuple` возвращает `True` при пустых границах),
  никаких исключений в коде фильтрации не появляется.
- `availability` — **не заполняется**. Контексты в `__categories__` одинаковы у
  всех 134 записей (`CONFIG`, `ENTERPRISE`, `MNG_ENTERPRISE`, `WEB_ENTERPRISE`
  — по 134 каждый), то есть не различают ничего. Это режимы показа статьи в
  книге справки, а не контексты исполнения кода, и переводить их в словарь
  `AVAILABILITY` (`syntax_model.py`) нечем: там русские фразы вроде «тонкий
  клиент», словарь другой. Пустое поле честнее выдуманного.

Три вида надо добавить в `KIND_TITLES` (`syntax_model.py`), иначе
`search_syntax` и `get_syntax` напечатают сырое `query_function`: они рисуют
заголовок через `KIND_TITLES.get(item.kind, item.kind)`.

Граница вида определяется так, в порядке проверки:

1. заголовок начинается с «Функция» или «Агрегатная функция» →
   `query_function`;
2. длина **декодированной** страницы больше порога `ARTICLE_BYTES` →
   `query_article`;
3. иначе → `query_keyword`.

Порог — именованная константа с комментарием и цифрой замера, а не число в
условии. Значение 8 192 применяется к длине декодированного текста, а не к
сырым байтам: в UTF-8 русская страница вдвое длиннее, и по байтам статей
получалось 13 вместо измеренных.

Сигнатура ищется по порядку: `<PRE>` (там она у 28 страниц — уточнено
замером в задаче 6 до **27**, см. раздел «Разбор» выше), затем первая строка
первого абзаца, если имеет форму `ИМЯ(…)`. Не нашлась — поле остаётся
пустым, элемент всё равно функция.

## Приём

Файл кладётся туда же, куда справка платформы: `data/bootstrap/`, страница
`/sources`, команда `reg-add`. Отдельной кнопки «это язык запросов» нет.

Вид источника определяется по содержимому `FileStorage`:

- есть страницы `objects/**.html` → справка синтакс-помощника (нынешний путь);
- есть `__categories__` **и** страницы секций (`SELECTSection`, `UNIONSection`,
  `ORDERBYSection`) → язык запросов;
- ни то ни другое → прежний отказ с объяснением, какой файл нужен.

Обе половины правила обязательны, и вот почему — замер 2026-08-17:
`shlang_ru.hbk` тоже содержит `__categories__`, но страниц с `Section` у него
**ноль против трёх**. По одному лишь `__categories__` он был бы принят за язык
запросов, хотя объявлен вне объёма.

**Порядок проверок в `add_syntax` меняется, и это часть работы.** Сегодня
`dashboard.py` и `cli.py` отправляют любой `.hbk` в `registry.add_syntax` по
одному лишь расширению, а внутри стоит безусловная проверка версии
(`registry.py:537-543`). Для `shquery_ru.hbk` `derived_platform()` вернёт пустую
строку — версий в файле нет, — и файл будет отвергнут сообщением «не удалось
определить версию платформы», то есть ровно противоположным обещанному. Значит:

1. распознавание вида выполняется **до** проверки версии;
2. проверка версии остаётся обязательной для справки синтакс-помощника и не
   применяется к языку запросов;
3. то же касается `restore()` при каждом старте: источник поднимается с
   сохранённым видом, а не переугадывается.

**Отказ на языконезависимом варианте.** `shquery_root.hbk` устроен так же
структурно, как `shquery_ru.hbk`, и правило распознавания его пропустит.
Нужна та же защита, что уже стоит для `shcntx_root.hbk` (`registry.py:566-574`):
ни у одной страницы нет текста описания — отказ с объяснением. Без неё сервер
молча примет пустой источник, а это тот же класс дефекта, за который проект уже
один раз заплатил.

Экземпляр один на сервер. Повторная загрузка заменяет прежний.

## Разбор

Новый модуль `src/mcp1c/query_parser.py`. `syntax_parser.py` не трогается: он
разбирает разметку с классами `V8SH_*`, которых в этих страницах нет вовсе.

Низкоуровневое переиспользуется, а не копируется: `_decode`, `_text`,
`_split_bilingual`, `open_file_storage`. Если для этого понадобится сделать их
общими — это часть работы, а не отдельная задача.

Что извлекается со страницы:

- заголовок `<H1>`;
- сигнатура и параметры — из первого `<P>` и следующего `<BLOCKQUOTE>`;
- текст описания — markdown, полученный тем же способом, что и для справки
  платформы (ссылки `v8help://` разворачиваются в имена, теги снимаются);
- ключевые слова из `<STRONG>` в первом абзаце — они дают русские формы вроде
  `ЛЕВОЕ [ВНЕШНЕЕ] СОЕДИНЕНИЕ`, по которым и будут искать.

Таблицы страницы (добавлено 2026-08-18) вынимаются **до** сбора абзацев:
ячейки размечены абзацами внутри `<TD>`, и без этого таблица попадала в
описание столбцом значений. Разделяются по геометрии, а не по классу CSS —
`class=SimplyTable` стоит не на всех и не только на них:

| Вид | Признак | Куда идёт |
|---|---|---|
| таблица данных (51 на 31 странице) | строки одной ширины, нет ячеек из одной черты | `SyntaxItem.tables`, метка `\x00таблица-N\x00` на её месте в описании |
| синтаксическая диаграмма (21 на 17) | ширины рваные, ячейки-черты рисуют ветвление | остаётся в описании лесенкой: отступ = число пустых ячеек слева |

Границы таблиц ищутся счётчиком глубины, а не регуляркой: таблицы вложены, в
том числе таблица данных в таблицу данных (`nestedtables_fetch.html`).
Незакрытая `<TABLE>` даёт `ОбрывТаблицы`; `parse_pages` ловит её, разбирает
страницу без таблиц и записывает имя в `SyntaxIndex.warnings` — оттуда оно
попадает в `Source.warnings`, вывод `reg-add` и на страницу «Источники».

Страница `present.html` — двуязычная таблица ключевых слов рус↔англ. Разбор пар
терминов из неё отложен сознательно (см. «Вне объёма»); страница просто
исключена из элементов — попадает в `СЛУЖЕБНЫЕ` (`query_parser.py`) наравне с
`__categories__` и не даёт ни статьи, ни пар для поиска.

## Хранение и ловушка со слиянием

Разобранное сохраняется отдельным файлом `data/index/syntax/query-ru.json.gz`
тем же `save_syntax`/`load_syntax` — они не зависят от вида элемента, проверено.
Кэш поискового индекса — тем же штампом по коду пакета и источнику, отдельной
записью.

**Источник получает свой вид `KIND_QUERY` и не попадает в `syntax_versions`.**
Это не украшение, а условие работоспособности, и цена ошибки здесь выше, чем
казалось при первой редакции:

- `merge_syntax` **падает** `ValueError` на индексе без версии
  (`syntax_merge.py:76-81`), а `_prepare_syntax` это исключение не ловит
  (`registry.py:665-672`). Положить язык запросов в `syntax_versions` — значит
  уронить сборку слитого вида для **всех** конфигураций при следующей же
  загрузке или перезапуске. Не «спрячется», а перестанет работать целиком.
- `syntax_coverage()` строит покрытие прямо из `syntax_versions`
  (`registry.py:864-885`), поэтому источник с пустой версией навсегда повис бы
  в выдаче как «Справка «» не используется: конфигураций на этой платформе
  нет» — в `list_configurations`, на странице обзора и в `reg-list`.

Источник **регистрируется в `sources`** как обычно и **не регистрируется в
`syntax_versions`**.

**Поправка от 2026-08-17, найдена при реализации.** Первая редакция утверждала,
что `sweep_syntax` файл не тронет, раз источник лежит в `sources`. Это неверно:
уборка собирает список разрешённого по `source.kind == KIND_SYNTAX`, поэтому
источник с новым видом в него не попадал и `query-ru.json.gz` сносился бы на
первом же старте. Проверено опытом — откат одной строки делает тест красным.
Фильтр уборки расширен до `(KIND_SYNTAX, KIND_QUERY)`. Урок прежний: «проверено
чтением кода» — не то же самое, что «проверено запуском».

Соединение с элементами платформы происходит позже и на другом уровне: в
`LoadedSyntax` — поисковый индекс и таблица имён `by_name` строятся по обоим
наборам сразу. Слияние версий их не касается.

На это пишется отдельный тест: элемент языка запросов доступен при конфигурации
на 8.3.5, не получает `until` и не ломает сборку слитого вида.

## Ответы инструментов

Новых инструментов не добавляется.

- **`search_syntax`** — находит наравне с элементами платформы. В строке вида:
  «Функция запроса», «Ключевое слово запроса», «Статья по языку запросов». У
  статьи печатается заголовок и первый абзац, не больше `SNIPPET_CHARS`.
- **`get_syntax`** по имени — карточка целиком: у функции сигнатура и разбор
  параметров, у статьи полный текст.
- **Фильтр версии** их не касается: `since` пуст, в блок скрытого они не
  попадают.

**Совпадение имён — не редкий случай, а половина набора.** Замер 2026-08-17:
**55 имён из 128 совпадают с элементами платформы** — `КОНЕЦПЕРИОДА`, `ДЕНЬ`,
`ЧАС`, `ДЕНЬГОДА`, `Log`, `Cos`, `ACos`, литералы `ДАТА`, `ЧИСЛО`, `СТРОКА`,
`ТИП`, ключевые слова `ВЫБРАТЬ`, `ПЕРВЫЕ`. `get_syntax` ищет точное совпадение
через `find_exact` по одной таблице `by_name` (`registry.py:169-196`,
`tools.py:585`), и без правила агент получит карточку метода платформы там, где
спрашивал про язык запросов, — или наоборот.

**Уточнено замером в задаче 6 (2026-08-17, тем же днём вторым заходом).**
После того как парсер стал чистить служебные записи (`present.html` не
попадает в элементы) и точнее собирать имена, число другое: **57 имён из
127** — 38 совпадений по русскому имени, 49 по английскому (пересечение
даёт объединение 57). Прежнее «55 из 128» получено до этой чистки; вывод не
меняется: совпадение действительно почти у половины набора.

Правило: при совпадении имени показываются **оба** через существующую ветку
«одноимённых элементов» (`tools.py:621-630`), и вид в строке разводит их
однозначно — «Метод» против «Функция запроса». Ветка эта писалась под
однофамильцев внутри платформы; здесь она получает второй домен, и на это
нужен тест — иначе легко получить молчаливую подмену домена, то есть тот же
класс ошибки, что «скрытое выдаётся за несуществующее».

**Работа без справки платформы.** Сегодня `_syntax_context` (`tools.py:328-335`)
отказывает целиком, если `shcntx` не загружен: «Справка платформы не
подключена». Сервер, где есть только язык запросов, обязан отвечать по нему —
иначе источник, поданный как самостоятельный и лёгкий, без второго файла в
40 МБ бесполезен. Отказ остаётся, только когда не подключено **ничего**, и
называет то, чего не хватает.
- **`list_configurations`** — строка «Язык запросов: подключён, 128 страниц»
  рядом с «Индекс модулей: не подключён»; когда файл не загружен — «не
  подключён».
- **Дашборд `/sources`** — принимает файл и показывает распознанный вид.
  Подсказка на странице дополняется: `shquery_ru.hbk` из того же каталога
  установки.
- **CLI** — `reg-list` показывает источник в общем списке.

## Тесты

Все на синтетическом контейнере, собираемом в `conftest.py`: содержимого
`data/` в репозитории нет, и тест, который без него не запускается, бесполезен.

1. Вид источника определяется по содержимому: страницы `objects/**` → справка,
   `__categories__` + секции → язык запросов, мусор → понятный отказ.
2. Файл с `__categories__`, но без страниц-секций (форма `shlang_ru.hbk`) за
   язык запросов не принимается.
3. Языконезависимый вариант (страницы без описаний, форма `shquery_root.hbk`)
   отвергается с объяснением.
4. Язык запросов принимается **без** указания версии платформы, а справка
   синтакс-помощника без версии по-прежнему отвергается.
5. Функция разбирается с сигнатурой и параметрами.
6. Ключевое слово разбирается с заголовком и текстом.
7. Статья по имени отдаётся целиком, в выдаче поиска — урезанной.
8. Элемент языка запросов доступен при конфигурации на 8.3.5 — не прячется
   фильтром версии и не получает `until` от слияния справок.
9. Загруженный язык запросов **не ломает сборку слитого вида**: справка
   платформы добавляется после него и слияние проходит.
10. Покрытие справок (`syntax_coverage`) не показывает язык запросов ни
    недостающей, ни лишней справкой.
11. Совпадение имени с элементом платформы даёт обоих кандидатов с разными
    видами в строке, а не молчаливую подмену.
12. Сервер, где загружен только язык запросов, отвечает по нему; отказ «ничего
    не подключено» остаётся только при пустом реестре.
13. Повторная загрузка заменяет прежний экземпляр, а не плодит второй.
14. Индекс переживает перезапуск: сохранён, поднят с диска, элементы на месте.
15. `list_configurations` называет источник подключённым и не подключённым.

## Замеры и критерии приёмки

Меряется на настоящем файле, до и после:

- время разбора и старта сервера (сейчас 1,5 с на одной справке, 2,2 на трёх);
- прирост памяти (сейчас 109 МБ на пяти справках);
- качество поиска на существующих наборах — **не должно просесть**;
- качество на новом наборе `tests/queries/query-language.json`.

Набор заводится в рамках этой задачи: формулировки вроде «как посчитать итоги
по иерархии», «что вернёт левое соединение, если справа нет строк», «как
привести тип в запросе». Без него улучшение нечем подтвердить, а «замер перед
утверждением» — правило проекта.

Приёмка: сервер отвечает по языку запросов на живом контейнере **после
пересборки**, а не только в тестах одного процесса.
