# Источники данных: что откуда берём

Правило проекта. Определяет, какой источник отвечает за какой кусок знания о
конфигурации, и почему граница проходит именно так. Нарушать — только с правкой
этого документа.

## Четыре источника и явное отсутствие данных ИБ

| Источник | Что даёт | Как получаем |
|---|---|---|
| **A. Обработка выгрузки** (`exporter-1c/`) | структура метаданных | запуск в информационной базе |
| **B. Выгрузка конфигурации в файлы** | тексты модулей и доступная структура `Form.xml`; доказанное происхождение объектов/полей расширений | конфигуратор / EDT |
| **C. Снимок расширений** (`СнимокРасширений_*.json`) | зарегистрированные, действующие и не применённые расширения конкретного сеанса | отдельная обработка на платформе 8.3.8+ |
| **D. Ничего** | данные информационной базы | не собираем принципиально |

## Разделение по элементам

| Элемент | Источник | Примечание |
|---|---|---|
| Состав объектов, реквизиты, табличные части | **A** | |
| Полные имена типов, квалификаторы | **A** | основа графа связей |
| Движения документов, основания ввода, владельцы | **A** | рёбра графа |
| Значения перечислений | **A** | работает на всех платформах |
| Свойства объектов (иерархичность, периодичность, проведение) | **A** | |
| Подписки на события, регламентные задания | **A** | `handler` даёт ребро к общему модулю |
| **Предопределённые элементы** | **A** | проверено на 8.3.5 и 8.3.23 |
| Тексты модулей, сигнатуры процедур | **B** | из встроенного языка недоступны в принципе |
| Структура, элементы и события форм из `Form.xml` | **B** | доступны, когда формат выгрузки содержит `Form.xml` |
| Происхождение собственного объекта или прямого нессылочного реквизита расширения | **B** | дельта основной и отдельной файловых выгрузок по семантическому адресу |
| Фактическая активность расширений в текущем сеансе | **C** | `СеансАктивные` / `СеансОтключенные`; без снимка — `unknown` |
| Порядок элементов, возвращённый API расширений | **C** | сохраняется дословно, но не выдаётся за порядок исполнения модулей |
| Команды, макеты и недостающие в schema v1 данные форм | — | общего источника и принятой задачи сейчас нет |
| Содержимое справочников и регистров | **D** | не собираем |

Источник C намеренно не добавлен в schema v1. Структура может быть актуальна
месяцами, тогда как состав расширений меняется между сеансами и областями
данных. JSON несёт собственные `snapshot_id`, UTC-время и identity
конфигурации; несовпадение помечается `stale`, отсутствие — `unknown`.
Три списка доступны с 8.3.8; отдельный признак изменения после старта сеанса —
только с 8.3.22, поэтому на 8.3.8–8.3.21 его значение равно `null`.

Происхождение из источника B также не входит в schema v1: сама эффективная
структура приходит из A, а B только доказывает, кто объявил уже видимый объект
или поле. При приёме основной выгрузки сохраняется gzip-каталог семантических
адресов; при приёме расширения — только доказанная разность с SHA-256 этого
поколения базы. Снимок заменяется и удаляется атомарно вместе с кодовым
источником и поднимается после рестарта без исходного ZIP. Нет базы или SHA
сменился — ответ `unknown`, без догадки по UUID или префиксу. Табличные части и
ссылочные поля в этот слой пока не входят.

Общая `schema_version 2` не запланирована. Доступная структура `Form.xml` и
модули форм уже приходят из источника **B**. Для команд, макетов или
недостающей разновидности формы сначала нужна конкретная живая задача и замер,
а затем отдельное решение об источнике и формате; номер версии заранее это
решение не заменяет.

## Сгенерированные слои поверх источников

Всё выше — про знание, добытое из базы или из справки. Отдельно стоит текст,
который **сочинён нами**: он не источник знания и не имеет права им казаться.

**Правило: сгенерированное не смешивается с выгруженным.** Три требования,
все три обязательны.

1. **Живёт отдельным слоем в git**, а не приписывается к разобранному
   элементу. Разобранная страница справки и наш текст лежат в разных местах и
   различимы по происхождению — как встроенный словарь отличается от
   локального.
2. **В ответ агенту не попадает.** Ответ по-прежнему собирается только из
   справки. Сгенерированное работает исключительно на попадание в нужную
   статью, а не на её содержание. Иначе агент получит наш пересказ вместо
   документации фирмы «1С» и не сможет их различить.
3. **Отсутствие источника не молчит.** Слой привязан к элементам по
   идентификатору. Элемента нет — привязка не состоялась, и это должно быть
   видно при загрузке, а не проявляться просевшим поиском.

Требование 3 — из того же класса дефектов, что уже ловили дважды: пустое имя
платформы в `list_configurations` и скрытое по версии, выданное за
ненайденное. Молчащая деградация дороже громкого отказа.

| Слой | Что там | Где | Ответ агенту |
|---|---|---|---|
| Поисковые ключи справки | формулировки, которыми спрашивают статью или платформенный метод | `search_keys.py`, git | нет, только поиск |
| Встроенный словарь | синонимы и псевдонимы объектов | `synonyms.py`, git | нет, только поиск |
| Локальный словарь | терминология конкретного внедрения | `data/dictionary.json` | нет, только поиск |
| Оговорки в карточке | предупреждение о ловушке платформы | `render.py`, git | **да**, см. ниже |

### Оговорки в карточке — единственный слой, доходящий до агента

Требование 2 выше писалось для слоёв, работающих на поиск, и для них остаётся
безусловным. Оговорка — другой случай: она нужна ровно в ответе и ровно в тот
момент, когда агент читает поля и пишет по ним запрос. Пересказывать ею справку
по-прежнему нельзя; она говорит только то, чего в справке нет, а без чего
выданные нами верные данные приводят к неработающему коду.

Отсюда два требования сверх общих трёх:

4. **Происхождение видно в самом тексте, а не в комментарии к коду.** Цитата
   из справки называется цитатой («справка прямо запрещает»), наш вывод —
   советом («считайте небезопасным»). Агент поведёт себя одинаково, а читатель
   через полгода отличит проверяемое от нашего.
5. **Непроверенное не выдаётся за проверенное.** Что не подтверждено ни
   справкой, ни живым прогоном, формулируется как осторожность, а не как факт
   о платформе.

**Строки неограниченной длины** — первая такая оговорка, заведена 2026-08-18 по
живому промаху и в тот же день доведена до конца: всё, что стояло советом,
проверено владельцем на живой базе и стало фактом. Разбивка по происхождению:

| Утверждение | Откуда | Что сказала платформа |
|---|---|---|
| нельзя в `КОЛИЧЕСТВО`, `МИНИМУМ`, `МАКСИМУМ` | цитата `shquery_ru.hbk`, страницы `COUNT`, `MIN`, `MAX` | «Не может применяться к … Строкам неограниченной длины» |
| нельзя сравнивать | прогон 2026-08-18, соединение по `КодСкидки` | «неверные параметры в операции сравнения. Нельзя сравнивать поля неограниченной длины и поля несовместимых типов» |
| нельзя группировать | прогон 2026-08-18 | запрос не выполняется |
| нельзя упорядочивать | прогон 2026-08-18 | «недопустимое поле для упорядочивания КодСкидки» |
| нельзя в `РАЗЛИЧНЫЕ` и `ОБЪЕДИНИТЬ` | прогон 2026-08-18 | «в запросе с предложениями РАЗЛИЧНЫЕ или ОБЪЕДИНИТЬ нельзя использовать поля неограниченной длины» |
| рецепт `ПОДСТРОКА(поле, 1, N)` | прогон владельца, работает | — |
| выборка поля без конструкций выше | прогон 2026-08-18, контрольный запрос | работает |

Три вывода из текстов ошибок, которых не было в первой редакции оговорки:

1. **`ОБЪЕДИНИТЬ` тоже под запретом** — платформа называет его в одном ряду с
   `РАЗЛИЧНЫЕ`. В первой редакции его не было вовсе.
2. **Запрет на сравнение шире условия соединения.** Платформа говорит «нельзя
   сравнивать поля неограниченной длины», не «нельзя соединять», — значит под
   него попадают и равенство в `ГДЕ`, и `В (…)`.
3. **Упорядочивание — отдельное ограничение, не следствие сравнения**: у него
   свой текст ошибки («недопустимое поле для упорядочивания»).

Проверено отдельно: страницы `GROUPStatement`, `ORDERBYSection`,
`KeyWordsDISTINCT`, `JOIN`, `UNIONSection`, `query_cast` про неограниченные
строки **молчат**. Справка знает об ограничении только в трёх агрегатных
функциях из шести; остальное знание — наше, и получено оно прогоном.

Второй рецепт, `ВЫРАЗИТЬ(поле КАК СТРОКА(N))`, в карточку не пошёл: справка
описывает `ВЫРАЗИТЬ` как средство для составного типа и ставит потолок
«максимальный размер строки составляет 1024», а на живой базе его никто не
проверял. `ПОДСТРОКА` проверена и потолка не имеет.

## Правило про предопределённые

**Источник — обработка (A), на всех проверенных платформах.** Если платформа
всё же не сможет — не пропускает молча, а помечает выгрузку.

Правильный способ установлен пробником
(`exporter-1c/probe/ПробникПредопределенных.bsl`) на платформе **8.3.23.1997**:

| Способ | Результат |
|---|---|
| `Менеджер.ПолучитьИменаПредопределенных()` | ✗ метод объекта не обнаружен |
| **`ОбъектМетаданных.ПолучитьИменаПредопределенных()`** | **✓ работает** |
| Запрос `ПредопределенноеИмяДанных` | ✗ поле не найдено |
| **Запрос `ИмяПредопределенныхДанных`** | **✓ работает** |
| Запрос `ГДЕ Предопределенный = ИСТИНА` | ✓ признак существует |
| `ОбъектМетаданных.ЭлементыПредопределенныхДанных` | ✗ свойства нет |

Метод висит на **объекте метаданных**, а не на менеджере. Поле запроса —
`ИмяПредопределенныхДанных`.

Ранняя гипотеза «до 8.3.6 предопределённые недоступны в принципе» была сделана
по одной платформе и **не подтвердилась**: на 8.3.23 отказ был тот же самый,
то есть причиной было обращение не к тому объекту, а не версия платформы.

После исправления предопределённые собираются **на обеих платформах**:

| Конфигурация | Платформа | `predefined_available` | Объектов | Имён |
|---|---|---|---|---|
| Отраслевая конфигурация | 8.3.5.1570 | `true` | 33 | 283 |
| Розница для Казахстана | 8.3.23.1997 | `true` | 40 | 1015 |

Предупреждений — ноль в обоих случаях. Источник **B** для предопределённых
не нужен; он остаётся только для текстов модулей.

Исторические цифры таблицы сняты 2026-08-27 командами на соответствующих
выгрузках; `info` подтверждает флаг, `stats` — состав объектов и число имён:

```bash
PYTHONPATH=src .venv/bin/python -m mcp1c.cli info /путь/к/выгрузке.zip
PYTHONPATH=src .venv/bin/python -m mcp1c.cli stats /путь/к/выгрузке.zip
```

Порядок попыток в выгрузке:

1. `ОбъектМетаданных.ПолучитьИменаПредопределенных()`
2. запрос `ВЫБРАТЬ ИмяПредопределенныхДанных … ГДЕ Предопределенный = ИСТИНА`
3. при отказе обоих — флаг, предупреждение, дальше не пытаемся

Обращение делается только к видам, у которых предопределённые вообще бывают:
справочники, планы видов характеристик, планы счетов, планы видов расчёта.
Иначе исключение на плане обмена или бизнес-процессе ложно пометило бы всю
платформу как неподдерживающую.

Загрузчик ориентируется на **атрибут манифеста**, а не на текст предупреждения:

```xml
<manifest ... predefined_available="false">
```

* `true` — предопределённые в выгрузке есть, источник **A** закрыл вопрос.
* `false` — секции `predefined` нет, конфигурация считается неполной,
  и это должно быть видно агенту.

### Почему это важно для генерации кода

Предопределённые адресуются в коде по имени:

```bsl
Если Номенклатура.ВидНоменклатуры = Справочники.ВидыНоменклатуры.Услуга Тогда
```

Без списка агент видит только тип реквизита и начинает угадывать имя —
`.Услуги`, `.Сервис`. Такой код компилируется и падает в рантайме.

| Что | Статус |
|---|---|
| Предопределённые на 8.3.5 и 8.3.23 | ✓ проверено |
| Оба формата дают одинаковую модель | ✓ контрактные тесты и полная реальная пара проверены 2026-08-27 |
| Рёбра графа строятся из обеих сериализаций | ✓ проверено тестами loader/graph |
| Планы счетов и регистры бухгалтерии и расчёта | ✓ проверено 2026-08-17 на живых данных |
| Тексты модулей из источника B | ✓ реализовано: приём, четыре индекса, поиск, карточка и обратные вызовы |

Воспроизводимые проверки текущего кода:

```bash
.venv/bin/python -m pytest \
  tests/test_schema_v1_strict.py tests/test_loader_contract.py \
  tests/test_handler_contract.py
.venv/bin/python -m pytest \
  tests/test_registry_modules_provider.py tests/test_tools_modules.py \
  tests/test_tools_callers.py
PYTHONPATH=src .venv/bin/python -m mcp1c.cli stats /путь/к/выгрузке.zip
```

Единственное неразрешимое ребро в каждой выгрузке — ссылка плана обмена на
`Конфигурация.<Имя>`, то есть на саму конфигурацию. Это не объект метаданных,
загрузчик должен такие ссылки отбрасывать штатно, а не считать ошибкой.

## Возможные источники — обсуждалось, не решено

Пометка на будущее, чтобы граница источников продумывалась заранее, а не
задним числом. Перечисленные ниже направления в работу не взяты.

| Источник | Что дал бы | Как получаем |
|---|---|---|
| **D. Технологический журнал** | долгие запросы, планы СУБД | файлы `.log` с сервера 1С |
| **E. Схемы обмена** | EnterpriseData, правила КД2/КД3 | пакеты обмена и XML-схемы |

Обе — данные о **работе** системы, а не о её устройстве, и меняются они на
несколько порядков быстрее конфигурации. Смешивать их с A и B в одном
хранилище нельзя: у A и B горизонт «до следующей выгрузки», у D — минуты.

## Почему граница проходит здесь

Разделение не по типу данных, а по **скорости изменения** и по тому, что
источник физически способен отдать:

* Обработка ходит по `Метаданные` — видит структуру, но не видит исходный код:
  платформа не даёт доступа к текстам модулей из встроенного языка.
* Файловая выгрузка содержит всё, включая код и предопределённые, но метаданные
  в ней разложены по GUID-ссылкам между файлами — читать их дорого и муторно.
* Данные информационной базы меняются постоянно и к структуре конфигурации
  отношения не имеют.

Каждый источник отвечает за то, что отдаёт дёшево и точно.
