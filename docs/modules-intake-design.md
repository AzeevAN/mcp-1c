# Приём выгрузки конфигурации в файлы — постановка

Дата: 2026-08-19. Статус: согласовано с владельцем, реализация не начата.
Правила ведения и задача — в `AGENTS.md` и `docs/TASKBOARD.md` (ведутся
локально, в репозиторий не входят).

Разведка, на цифры которой опирается эта постановка, —
`docs/modules-and-extensions-2026-08-18.md` (ведётся локально). Модель загрузки
и что внутри выгрузки решены там; здесь решается только одно: **как файл
попадает на сервер и во что превращается**.

## Зачем

Выгрузка конфигурации в файлы — это гигабайты. На разведанном корпусе:
zip 1,5 ГБ, распакованный 2,5 ГБ, 33 188 файлов. Метаданные, с которыми сервер
работает сегодня, — единицы мегабайт, и весь приём построен под них.

Три места, где нынешний приём об это ломается.

**Предел приёма.** `MAX_UPLOAD = 500 МБ` — полуторагигабайтный файл откажется
ещё в браузере.

**Тройное копирование.** `await request.form()` вычитывает тело целиком в
буфер, дальше код копирует его чанками в `tempfile.mkdtemp()`, дальше фоновая
задача распаковывает. Для 1,5 ГБ это:

| Этап | Объём | Где |
|---|---|---|
| буфер `form()` | 1,5 ГБ | `/tmp` внутри контейнера |
| копия в `mkdtemp()` | 1,5 ГБ | там же |
| распаковка | 2,5 ГБ | там же |
| **пик** | **≈ 5,5 ГБ** | записываемый слой Docker |

Смонтирован только `./data`; всё перечисленное уходит в overlay-слой, который
в `docker-compose.yml` ничем не ограничен.

**Полтора гигабайта по HTTP.** Десятки минут при риске обрыва на девяноста
процентах, без возможности продолжить с места разрыва.

При этом кодом является **12,6% выгрузки**. Две трети объёма — двоичные
драйверы и конфигурация поставки, не нужные ни на одном шаге.

## Что решено

| Развилка | Решение | Почему |
|---|---|---|
| как файл попадает на сервер | каталогом тома, не по HTTP | ноль копий, ноль обрывов, `MAX_UPLOAD` не участвует |
| что остаётся на диске | код без балласта, ~315 МБ | тело процедуры есть что отдать, переразбор без повторной передачи |
| что при нехватке ресурсов | отказ до начала, с цифрами | сервер продолжает работать; полуразобранного источника не возникает |

Решения от 2026-08-19, владелец.

## 1. Поток данных

Распакованных 2,5 ГБ не появляется никогда: zip читается членом за членом, на
диск ложится только отобранное.

```
./data/incoming/Розница_модули.zip      ← человек положил (cp, scp, rsync)
        │
        │  чтение потоком, член за членом;
        │  отбираются модули и формы, остальное пропускается
        ▼
data/modules/РозницаДляКазахстана/      ← только код, ~315 МБ
        │
        ▼
data/index/                             ← сигнатуры, 18,1 МБ
```

Пик по диску — размер результата. Пик по памяти — один член zip за раз.

Исходный zip остаётся в `incoming/`: сервер его не копирует, не перемещает и
не удаляет. Убирает человек — той же кнопкой «удалить файл», которая уже есть
для файлов, не заявленных ни одним источником.

**Каталог `incoming/` — новый.** Сегодня `data/bootstrap/` индексируется при
старте целиком; здесь нужен каталог, содержимое которого разбирается **по
команде**, а не само: разбор гигабайтной выгрузки при каждом старте
контейнера недопустим.

## 2. Состояния: что видит человек

Страница «Источники» показывает файлы из `incoming/`. Состояние **вычисляется**
при показе, а не хранится:

| Состояние | Как определяется | Действие |
|---|---|---|
| разобрано | `sha256` файла совпал с `sha256` источника в реестре | — |
| не разобрано | хеша нет ни у одного источника | `разобрать` |
| обновлённая выгрузка | имя то же, `sha256` другой | `переразобрать` |
| разбор устарел | `sha256` совпал, `_code_digest()` в штампе индекса отличается от нынешнего | `переразобрать` |

Реестр уже хранит на каждый источник `id, kind, origin, sha256, loaded_at,
platform, status, error, warnings, items_total, stored_path` — новых полей для
первых трёх состояний не нужно.

Четвёртое состояние делает видимым то, что сегодня не видно никому. Отпечаток
кода уже лежит в штампе кэша индексов (`index_cache._stamp`), но человеку не
показывается. Правило из `AGENTS.md` — «правил разбор → перезагрузи источник,
иначе проверяешь старый разбор» — держится на памяти разработчика и **ловилось
дважды за 2026-08-19**, оба раза выглядя как «правка не применилась». С
модулями цена ошибки выше: переразбор гигабайтной выгрузки не спрячешь.

**Хеш кэшируется.** sha256 полутора гигабайт считается секунды, и считать его
на каждое открытие страницы нельзя. Ключ кэша — `(путь, размер, mtime)`;
изменилось любое из трёх — пересчёт. Это единственное, чего в реестре сегодня
нет.

## 3. Проверка до начала

Сколько места потребуется, известно **до чтения тела**: центральный каталог zip
хранит несжатый размер каждого члена (`ZipInfo.file_size`). Отбираем нужные,
суммируем — точная цифра за миллисекунды, без распаковки.

Не хватает — задание сразу переходит в состояние «ошибка» с текстом вида
«нужно 315 МБ, свободно 90 МБ». Сервер продолжает работать как работал:
ни один загруженный источник не затронут.

Механизм заданий, показа состояния и ошибки на странице уже есть — новым
кодом здесь является только сама проверка.

## 4. Чего эта постановка не решает

**`mem_limit` в `docker-compose.yml` не назначается.** Разведка прямо
перечисляет это первым пунктом в «чего не измерено»: числа складывались по
отдельным замерам, пики частично накладываются. Ставить лимит по сумме
отдельных замеров — то же самое, что цифра без прогона.

Отдельно: `restart: unless-stopped` уже стоит. Лимит, поставленный наугад,
даёт не отказ, а цикл — OOM убивает контейнер, `restart` поднимает, тот снова
грузит те же источники и снова упирается.

**Что для этого нужно:** снять пик памяти одним прогоном на контейнере с
модулями одной конфигурации. Это закрывает первый пункт «чего не измерено».
До замера лимит не ставится: без лимита поведение предсказуемее, чем с
угаданным.

Известное на сегодня, для ориентира, — **не основание для лимита**:

| Что | Память |
|---|---|
| пять конфигураций и три справки сейчас | 628 МБ |
| поиск по всем процедурам (136 909) | 473 МБ |
| поиск только по экспортным (49 068) | 156 МБ |
| сигнатуры на диске / в памяти | 18,1 МБ / 65 МБ |

Отбор экспортных — рабочий рычаг, минус 67% памяти поиска; решено 2026-08-18.
Неэкспортную процедуру из чужого модуля всё равно не вызвать.

## 5. Границы

Здесь решается приём и хранение. **Не решается и решено раньше:**

- модель загрузки (конфигурация → модули → расширения, каждый уровень
  необязателен) — разведка, раздел 5;
- определение «конфигурация или расширение» по `Configuration.xml` — там же;
- привязка к конфигурации по имени и версии — там же;
- отбор экспортных и включение провайдера на конфигурацию, а не на сервер —
  решения 2026-08-18;
- два формата выгрузки (иерархический и плоский) — разведка, раздел 6.

**Приём по HTTP остаётся как есть** для того, подо что он и делался: справка
платформы, язык запросов, выгрузки метаданных — десятки и сотни мегабайт.
`MAX_UPLOAD`, полоса передачи и журнал заданий продолжают работать без
изменений. Каталог `incoming/` — второй путь, а не замена первому.
