# Загрузка конфигураций, расширений и общей справки

Это руководство описывает начальные источники, полную файловую выгрузку Source B, двухфазный intake, стандартные реквизиты и встроенную общую справку. Source A и Source B — взаимоисключающие режимы публикации одной конфигурации; их нельзя смешивать в одном active-поколении.


### Не перепутайте два разных ZIP из 1С

Слова «выгрузка конфигурации» относятся здесь к двум разным операциям. Архивы
не взаимозаменяемы и загружаются разными путями:

| Что за файл | Как получить | Что внутри | Куда передать |
|---|---|---|---|
| `СтруктураКонфигурации_*.zip` | внешняя обработка проекта `ВыгрузкаСтруктурыКонфигурации` | `manifest.xml` или `manifest.json`, затем `objects/*.xml` или `objects/*.json` | форма загрузки дашборда; также `bootstrap/` или `mcp1c.cli reg-add` |
| `СнимокРасширений_*.json` | отдельная обработка из `exporter-1c/`, запущенная в нужном сеансе | зарегистрированные, действующие и не применённые расширения | форма загрузки дашборда или `mcp1c.cli reg-add`; сначала нужна структура конфигурации |
| ZIP выгрузки конфигурации или расширения в файлы | **Конфигуратор → Конфигурация → Выгрузить конфигурацию в файлы… → Архив** | `Configuration.xml`, структура, модули, формы и роли | блок «Полная файловая выгрузка» страницы «Источники»; также двухфазный intake API из browser-upload, `data/incoming/` или `/config-sources/<id>` |
| `shcntx_ru.hbk` | каталог установленной платформы 1С | методы, свойства, события и объекты платформы | форма загрузки дашборда; также `bootstrap/` или `mcp1c.cli reg-add` |

Для Source A и Source B authority разделена на взаимоисключающие режимы
`A_ONLY` и `B_FULL`: смешанное active-поколение не считается допустимым.
Planner принимает только эти 2 режима: `A_ONLY` допускает schema-v1 без
ролевого слоя и не создаёт extension, а `B_FULL` требует готовый слой roles
для create/full update. Старый частичный request не разбирается как действие;
сохранённая job помечается устаревшей и требует новой полной загрузки.
В B-only фактическая версия платформы остаётся `unknown`, пока её явно не
объявит администратор; `compatibility_mode` не является заменой
`platform_version`.
История ранее подключённого расширения хранит только identity, parent, locator,
transport, origin, raw SHA и status. Parsed payload и generation в неё не
попадают; reconnect повторно находит исходник и оставляет changed/missing
источники диагностическими до нового preview.
API списка конфигураций и dashboard sources дополнительно показывают
`activation_mode` и `activation_status`; старый pointer возвращает
`RELOAD_REQUIRED`, а MCP-запросы к объектам, коду, формам и ролям отклоняются
до полной загрузки. Диагностический список источников остаётся доступен,
чтобы показать причину и запустить новое полное обновление; старые подробности
корпуса кода в нём не публикуются.
Если рядом есть доступные конфигурации, их версии, платформа, объекты и
состояние кода остаются в этом же списке.
`GET /api/v1/sources/coverage` для корпуса заблокированной конфигурации
возвращает HTTP 409 `reload_required`, а не журнал старого поколения.
То же относится к старому Registry без native pointer, если к структуре
Source A был отдельно добавлен код, формы или расширение Source B. Чистая
Source A без таких слоёв остаётся доступной.
Для проверки загрузки в тестовой среде выполняются полный `B_FULL` reload,
загрузка расширений, перезапуск, MCP `initialize → tools/list → tools/call`,
проверка дашборда и каскадного удаления. Изменение источников и удаление
выполняются с разрешения пользователя. Проверки Source A и Source B
проводятся отдельно.
Если источник одного из режимов отсутствует, результаты проверки этого режима
остаются `unknown`/`not_checked`; успешный прогон другого режима их не заменяет.
Для активной конфигурации `A_ONLY` или `B_FULL` администратор может задать или
очистить declared platform version:
`POST /api/v1/sources/platform/set` с `{ "configuration": "...",
"platform_version": "8.3.24[.1234]" }` и `POST
/api/v1/sources/platform/clear` с `{ "configuration": "..." }`. Оба маршрута
требуют `ADMIN_TOKEN` и CSRF-заголовок для cookie-сессии; конфигурация должна
быть загружена. Ручное значение является рабочей настройкой
поверх источника: оно используется не только dashboard, но и resolved-контекстом
MCP, фильтрацией синтаксиса и ответами агенту. После очистки снова используется
версия Source A, если она есть, иначе значение остаётся `unknown`; compatibility
mode его не заменяет. При отказе записи Registry изменение не применяется и
работающий сервер продолжает использовать прежнюю effective platform version.

В dashboard конфигурация с `activation_status=RELOAD_REQUIRED` явно помечается
как «Требуется повторная активация» и получает пояснение, что обычный restart не
исправляет старый active generation: для неё нужна полная активация `B_FULL`.
Предупреждения о неизвестной runtime-версии платформы и недоступных
предопределённых именах в dashboard собраны под заголовком «Ограничения
текущего опубликованного источника» только когда active generation действительно
не содержит доказанных имён. Современный Source B передаёт и сохраняет
собственные `Predefined.xml`; Source A остаётся отдельным источником runtime-фактов.
Длинные имена ролей переносятся в боковой
панели, а действия выбранной конфигурации разделены на статус и управляющие
кнопки.
На странице источников фактическая версия показывается как `unknown`, если она
не объявлена. Значение является ссылкой: администратор может задать или
очистить его прямо в dashboard для активного `A_ONLY` или `B_FULL`; рядом
показывается метка ручного значения. Для legacy и `RELOAD_REQUIRED` поле
заблокировано до активации. Архивы из browser/incoming и read-only каталоги используют одну и ту
же Source B/B_FULL семантику; транспорт не меняет activation-контракт.
Dashboard также использует утверждённый знак MCP 1C из
`docs/branding/mcp-1c`: SVG favicon и Paper-совместимый знак в навигации.

Для Source Modes кэш-инвалидация проверяется синтетическим gate:

```bash
.venv/bin/python -m pytest tests/test_intake_v2_registry.py tests/test_intake_v2_operations.py tests/test_intake_v2_extensions.py tests/test_registry_cache.py tests/test_role_access_index.py
PYTHONPATH=src .venv/bin/python tools/lab/measure_object_snapshot.py --data /путь/к/изолированной-копии/data
.venv/bin/python tools/lab/measure_extension_recheck.py --base-identities 57892 --edges-per-extension 458 --extensions 0,1,4 --repeat 20
```

Первый запуск проверяет удаление старых generation/cache и warm restart; два
последних дают воспроизводимые latency/RSS и cold/warm сравнения. Живой
`data/` для этих команд не используется.

Прежняя команда `POST /api/v1/sources/incoming/parse` отключена: возвращает
HTTP 410 и не запускает code-only разбор. Для Source B используйте единый
двухфазный intake ниже: он создаёт конфигурацию или полностью обновляет
согласованные слои из одного кандидата. Прямой legacy-загрузчик модулей также
отклоняет запись поверх native Source A/B.

### Двухфазный intake API

После удаления источника, публикации нового поколения или завершения обычной
фоновой загрузки SPA сбрасывает зависимые карточки, роли, граф и настройки
поиска. Наблюдение за запущенной загрузкой продолжается у администратора при
переходе на другие страницы; `no-op` публикация кэш не сбрасывает.

Страница «Запросы» сохраняет фразы, ссылки на результаты и прокрутку в текущей
вкладке. Сохранённая выдача после смены источников показывается как устаревшая
история, а не как актуальный ответ. При возврате страница заново проверяет
ревизию; повторный прогон обновляет результат. `GET/POST /api/v1/queries`
возвращает непрозрачный `sources_revision`: это общая ревизия источников
сервера, не номер версии выбранной конфигурации. Смена другого источника или
перезапуск сервера тоже консервативно делает историю устаревшей. При смене
снимка во время поиска POST возвращает `sources_revision: null`; старые
сохранённые ответы без маркера также требуют повторного прогона. Это не
непрерывная подписка на внешние изменения Registry и не ревизия словаря.

HTTP-контур допускает **одну тяжёлую операцию одновременно**: обычный
`/api/v1/sources/upload`, приём кандидата `/intake/upload`, `/intake/start`,
`/intake/confirm` и `/intake/discard` (последние пути также под
`/api/v1/sources`). Занятый допуск возвращает **409 до чтения тела**:
очередь ожидающих разборов и временные файлы отклонённых запросов не создаются.
Дождитесь завершения операции и повторите запрос; автоматически в очередь
он не ставится. Проверки административного токена и CSRF выполняются до допуска.

Разбор и публикация используют отдельный лимитер потоков, не занимая общий
допуск чтения. Это устраняет ожидание чтения из-за заполненной очереди загрузок,
но не гарантирует latency при любой нагрузке на CPU/диск. Полная файловая
выгрузка Source B принимается через браузер до 4 ГиБ, прочие загрузки — до
500 МиБ; при копировании upload временно существуют spool и рабочая
копия одного файла. Готовые durable-кандидаты и опубликованные данные не входят
в эту квоту — их жизненный цикл и явное удаление не меняются. Если место или
квота для временного multipart-файла закончились, оба маршрута загрузки
возвращают HTTP 507 с причиной; после освобождения места запрос можно повторить.

Отключение клиента не останавливает уже работающий синхронный обработчик:
допуск освобождается после его завершения, используемый им файл раньше не
закрывается. Результат принятого intake может остаться в списке кандидатов/jobs.
Отмена до handoff удаляет частичную обычную загрузку. Синтетическая проверка
допуска и задержки чтения без рабочих данных:

```bash
PYTHONPATH=src .venv/bin/python tools/lab/measure_upload_admission.py
```

В B-only фактическая версия работающей платформы **неизвестна**:
`CompatibilityMode` из `Configuration.xml` хранится отдельно как
`compatibility_mode`, а не как `platform`. MCP явно предупреждает, что
фильтрация синтаксиса по runtime-версии выключена и доступность метода в базе
не подтверждена. Справка не объявляется совпадающей или ненужной только на
основании режима совместимости. Текущий разбор B также не получает имена
предопределённых элементов: пустой список не доказывает их отсутствие в базе.
Это не блокирует загрузку структуры, кода, форм и ролей B.

Критерии отбора полной файловой выгрузки Source B сохраняются как обычные
объекты `КритерийОтбора.*`: descriptor передаёт тип значения, состав и
назначенные формы, а фактически доступные формы и их модули остаются в общих
слоях content. Поэтому критерий находится прежними `search_objects`,
`get_object` и `get_related` и виден в существующем графе и дашборде; новых
MCP-инструментов, HTTP-маршрутов, CLI-команд или отдельной страницы нет.
Неизвестная цель состава остаётся видимой неразрешённой связью, а не исчезает
из ответа. Имя критерия в descriptor должно совпадать с именем в tree- или
flat-адресе файла без учёта регистра; противоречивая поставка отклоняется до
публикации поколения.

Общие команды Source B также сохраняются как обычные объекты
`ОбщаяКоманда.*`: карточка показывает descriptor-свойства и фактически
доступный `CommandModule`. Тип параметра выводится вместе с составом и
доказанными квалификаторами; если `CommandParameterType` отсутствует,
карточка не подставляет тип. Граф связывает команду с формами, где она
статически объявлена через `CommandName` или
`Form/CommandInterface/**/Command`. В ребре остаётся точный адрес формы и вид
XML-декларации. Строки `CommonCommand.*` внутри BSL связью не считаются:
динамический вызов не доказывает фактическое назначение команды форме.
Отдельных MCP-инструментов, HTTP-маршрутов или страницы дашборда для этого
слоя нет — используются прежние `search_objects`, `get_object` и
`get_related`.

`GET /api/v1/sources` передаёт в строке конфигурации `platform` (пусто, если
неизвестна), `compatibility_mode`, `predefined_available`, `syntax_relation`
(включая `unknown`) и русские оговорки в `notes`. Source A предоставляет
runtime-факты для своей базовой структуры. При полной замене base новой B
старые факты A не переносятся автоматически. Старые B-поколения читаются с
исправленной интерпретацией без перезаписи payload/manifest; текущий разбор имеет
`selection_version=10` и `parser_version=13`. Старые поколения не содержат
descriptor-слой общих команд и доказанные связи команд с формами; само
обновление кода не запускает переразбор источников.
Имена плоских форм `Form` и `Module` сохраняются дословно: descriptor и
XML-структура различаются полной грамматикой пути, а не совпадением хвоста.
Некорректный счётчик обычной формы получает категорию `invalid_count`;
ошибка одной формы не прерывает чтение остальных.
Отпечатки расходных индексов и кэша ролей учитывают все Python-подпакеты,
включая ридеры: после их обновления старый кэш перестраивается автоматически.

Разбор source B различает состояние данных и полноту нашей семантической
модели. Отсутствующий модуль формы и прочитанный пустой модуль — штатные
состояния: они видны отдельными счётчиками и не создают предупреждение.
Общий модуль, объявленный descriptor-ом, но не имеющий доступного тела,
показывается как «исходный текст недоступен». Это также не ошибка загрузки и
не доказательство пароля; ответы о процедурах и вызовах явно ограничиваются
доступными исходниками. Ошибкой остаётся существующее тело или структура,
которые не удалось прочитать из-за повреждения, кодировки, синтаксиса,
ресурсного предела или конфликта.

Обычные формы `Form.bin` и плоские `.Form` проходят отдельную цепочку bounded-
ридеров. Для подтверждённых профилей с маркерами `25`, `26` и `27` сервер
извлекает реквизиты и элементы. Точные привязки событий пока не доказаны и
показываются как «семантика отложена», без статуса ошибки. Незнакомый, но
синтаксически целый профиль остаётся видимым в той же нейтральной категории;
битая или непрочитанная запись переводит корпус в состояние с ограничениями.
Плоские descriptor `*.Form.<Имя>.xml` и структура управляемой формы
`*.Form.<Имя>.Form.xml` объединяются по одному адресу; XML-ридер извлекает из
них реквизиты, элементы и точные привязки событий. Descriptor без тела формы
остаётся видимым как частично прочитанная форма и не считается ошибкой.
Внутренний предел семантической материализации обычной формы равен 500 000
лексем; внешний bounded-скан сохраняет прежние ограничения. Контракт
воспроизводится командой:

```bash
.venv/bin/python -m pytest tests/test_form_reader.py -q
```

Новый API принимает ту же полную файловую выгрузку как самостоятельного
кандидата. Обнаружение и preview ничего не публикуют: активный Registry
меняется только после отдельного `confirm`. Все маршруты административные и
требуют `ADMIN_TOKEN`:

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/sources/intake` | по запросу проверить managed browser staging, `data/incoming/` и настроенный read-only источник; вернуть все кандидаты, группы, локальные ошибки и durable jobs |
| `POST /api/v1/sources/intake/upload` | принять один ZIP до 4 ГиБ в managed staging и выполнить probe без тяжёлого разбора |
| `POST /api/v1/sources/intake/start` | начать `create` или `update_full`; построить semantic preview без публикации. Новый `update` возвращает конфликт |
| `GET /api/v1/sources/intake/jobs/{job_id}` | получить durable progress, послойный diff, no-op или ошибку после рестарта |
| `POST /api/v1/sources/intake/confirm` | атомарно опубликовать готовый preview; повтор того же confirm идемпотентен |
| `POST /api/v1/sources/intake/discard` | отменить неопубликованный preview и удалить его рабочие данные; входной `incoming`-архив не меняется |
| `POST /api/v1/sources/intake/candidates/delete` | удалить по `candidate_id` только загруженный через браузер ZIP и связанные ошибочные jobs; активная операция или готовый preview блокируют удаление |

Предел 4 ГиБ относится только к передаче полной файловой выгрузки Source B
через browser-upload. Для остальных видов upload предел остаётся 500 МиБ.
Браузерный ZIP можно удалить в списке кандидатов кнопкой «Удалить ZIP» после
подтверждения. При работающей операции дождитесь её завершения; готовый
неопубликованный preview сначала отмените. Файлы из `incoming` этой кнопкой
не удаляются. Если удаление ZIP прервалось из-за ошибки файловой системы,
кандидат и связанные ошибочные jobs с их диагностикой остаются в списке;
после устранения ошибки удаление можно повторить, в том числе после рестарта.
Успешная публикация сама удаляет браузерную копию ZIP.
После приёма ZIP браузерный кандидат и архив из `data/incoming/` читаются
одинаково: без фиксированных лимитов на размер отдельного элемента,
коэффициент сжатия и суммарный распакованный объём. Для `incoming` нет и
лимита сырого файла; браузерная передача ограничена 4 ГиБ. Для обоих путей
сервер проверяет безопасные и однозначные пути, symlink, специальные файлы,
шифрование, предел 100 000 записей, CRC и неизменность архива. Проверка
`Configuration.xml` ограничена 8 МиБ в обоих случаях. У настроенного
read-only источника сырой файл также не проходит через HTTP-лимит, но открытые
parser-ом элементы остаются в общем ресурсном бюджете.

Выбранные тела Source B сохраняются не деревом из десятков тысяч файлов, а
последовательным `members.pack` с каноническим `members.index.json` — отдельно
для collection, preview и опубликованного поколения. Сервер проверяет границы,
размеры и SHA-256 и читает по индексу только запрошенный модуль, форму, роль
или XDTO-пакет; распаковки всего pack при MCP-вызове нет. Это внутренний формат
`data/`: пустые members допустимы в любом порядке, но их смещение обязано
совпадать с реальной границей соседних данных; прежние поколения с отдельными
member-файлами остаются читаемыми.
После обновления сервера новые сведения парсера появляются только после
обычного «Обновить полностью» → «Опубликовать» в дашборде — пересборка образа
сама не переразбирает сохранённый Source B. Если collection не построен,
карточка задания показывает не только стадию, но и тип и текст исходной
системной причины; действующее поколение при этом не меняется.

В SPA тот же контракт представлен отдельным блоком «Полная файловая выгрузка»
на странице «Источники». Человек запускает «Создать конфигурацию» либо
«Обновить полностью», видит progress и послойный semantic preview и только
после этого отдельно публикует изменения. Готовый preview сразу появляется в
списке без ручного обновления страницы; его кнопка называет конфигурацию и
исходный ZIP, а не только внутренний `candidate_id`. Preview сохраняется на
сервере автоматически и после подготовки не зависит от browser-upload: очистка
ZIP другим commit и restart не мешают его публикации. Directory-preview перед
публикацией по-прежнему повторно проверяет привязку и неизменность каталога.
Крестик только закрывает диалог, а «Отменить и удалить
preview» явно снимает job и её рабочие данные. После успешной отмены SPA не
запрашивает уже удалённую job. Параллельный снимок списка возвращает
согласованное состояние до либо после отмены, а не временный конфликт из-за
исчезнувшей между чтениями job. До отправки `confirm` ничего не публикует.
После отправки серверная атомарная публикация уже
запущена: диалог блокирует закрытие и повторный intake до ответа, а обновление
или закрытие страницы не является командой rollback. После успешного commit
тяжёлые collection/materialized-копии удаляются, для идемпотентного повтора
остаётся только компактный durable result; managed browser-upload также
снимается, а `incoming` и read-only источник не меняются.

Для любой существующей конфигурации обновление Source B выполняется полностью:
при публикации `update_full` берёт все пять слоёв из одного снимка, даже если
семантически изменился только один слой. Семантический no-op не создаёт нового
поколения, если действующий снимок уже целый. Старое A/B-поколение без
валидной активации получает `RELOAD_REQUIRED`: конфигурационные данные не
выдаются до полной загрузки A или B. Ранее опубликованное частичное B/B-
поколение с валидной активацией остаётся читаемым, но его структурные слои
могут отставать от принятого ZIP; оно не исправляется автоматически.
Новые частичные `update` отклоняются до запуска разбора, в том числе после
первой полной публикации. Сохранённые ранее jobs и preview остаются читаемыми,
но старый частичный preview больше нельзя публиковать: нужно запустить полное
обновление.
Готовый частичный legacy-preview, созданный прежней версией сервера, также
отклоняется контролируемой ошибкой и не приводит к HTTP 500 или частичной
публикации. Он показывается как локально устаревшая failed-job и не блокирует
список кандидатов или остальные операции intake.

При публикации готового слоя ролей сервер строит из сохранённого generation-
snapshot расходный файловый SQLite-индекс. Исходный ZIP после commit для этого
не нужен, полный корпус прав не удерживается коллекциями Python в памяти.
Индекс хранит объявленные права, полные пути дочерних объектов, явные запреты,
RLS и шаблоны. Одно `restrictionByCondition` остаётся одним ограничением, а
все его `field` возвращаются упорядоченным массивом `fields`; пустой
`condition` сохраняется как условное право, а не исчезает — в том числе у
шаблона ограничения. Пустой языковой код синонима роли также сохраняется,
если сам текст синонима присутствует. Повреждение или
несовпадение штампа приводит к пересборке из snapshot. Это сведения о составе
ролей конфигурации, а не об эффективном доступе пользователей информационной
базы. Пользователи, группы и назначения ролей сервер не загружает.

Descriptor без соседнего `Rights.xml` означает пустую роль, а не ошибку:
descriptor остаётся доступен, список прав пуст, три default-флага имеют
значение `null` и показываются как «не задано». Сервер не подменяет неизвестное
значение `false`. `Rights.xml` без descriptor по-прежнему даёт локальную ошибку
ролевого слоя и не блокирует структуру, код или формы.

Для плоской файловой раскладки descriptor-ом считается только точный файл
`Kind.Name.xml`; `Help`, `Predefined`, формы и макеты не выдаются за descriptor.
Обязательный `ExchangePlan.Name.Content.xml` приводится к тому же каноническому
пути, что и tree-вариант, а `Role.Name.xml`/`Role.Name.Rights.xml` — к единому
role snapshot. Скомпилированный `CommonModule.Name.Module` остаётся
скомпилированным member и не декодируется как текстовый BSL.
Расходный индекс такого member и индекс кода native-расширения поднимаются из
warm-кэша; отсутствие или повреждение кэша приводит к безопасной пересборке из
активного generation snapshot.
Параллельные cold-пересборки используют отдельный Snowball stemmer на
поток: сам stemmer изменяет внутреннее состояние, а общий экземпляр
вызывал редкий `IndexError`. На двух read-only CoW-копиях 2026-09-02
thread-local и сериализация lock вернули один digest. Их p50/p95:
66,860/67,096 и 66,547/68,393 с; steady RSS — 327,4/335,1 и
295,7/299,0 МиБ. Воспроизводимая команда:

```bash
.venv/bin/python tools/lab/measure_stemmer_concurrency.py \
  --modules-root /tmp/corpus-a --modules-root /tmp/corpus-b --repeat 3
```

Если фоновая сборка всё же падает, `Source.error` хранит raw-причину,
server log получает traceback, а административная страница «Источники»
показывает bounded техническую причину без имени исходного ZIP.
Обычный read-only ответ сохраняет обезличенную ошибку. Старый coverage-
журнал при `status=error` не выдаётся за актуальный.
После native source-B публикации тот же JSON-журнал создаётся для каждого
корпуса кода; если расходный файл отсутствует или устарел, restart восстанавливает
его из активного generation snapshot без повторной загрузки исходного ZIP.

`start` принимает только `candidate_id`, `action`, необязательные `job_id` для
повторного запроса в текущем процессе и `parent_configuration`. После рестарта
оборванная `parsing`-job уже закрыта как `failed`, поэтому обновление запускают
с новым `job_id`. Произвольного файлового пути в HTTP-контракте нет. Для основной
конфигурации доступно `create`, если такой внутренней identity ещё нет;
для существующей — только `update_full`. Для нового и существующего расширения
доступно `update_full`; оно требует явно выбранного и уже загруженного
`parent_configuration`. Имя и родителя сервер сверяет до тяжёлого разбора.

Browser-upload отправляется multipart-полем `file`. Ответ содержит candidate,
но ещё не job:

```bash
curl -fsS -H "X-Api-Token: $ADMIN_TOKEN" \
  -F 'file=@configuration.zip;type=application/zip' \
  http://127.0.0.1:5001/api/v1/sources/intake/upload

curl -fsS -H "X-Api-Token: $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"candidate_id":"candidate-...","action":"create"}' \
  http://127.0.0.1:5001/api/v1/sources/intake/start
```

Локальный каталог подключается **отдельно к каждой уже загруженной основной
конфигурации**. Добавьте в `volumes` сервиса Docker Compose read-only mount
корня файловой выгрузки:

```yaml
- type: bind
  source: /absolute/path/to/export
  target: /config-sources/config-a
  read_only: true
  bind:
    create_host_path: false
```

Личные пути можно вынести в исключённый из Git `compose.local.yaml`:
поместите приведённый блок под `services` → `mcp1c` → `volumes`, а в `.env`
добавьте `COMPOSE_FILE=compose.yaml:compose.local.yaml` (macOS/Linux).
Основной `compose.yaml` при этом не требуется менять. Локальный файл каждый
оператор создаёт у себя; в репозитории он не распространяется.

Для следующей конфигурации добавьте другой mount, например
`/config-sources/config-b`. ID — 1–128 латинских букв, цифр, `_`, `-`, `.`,
первый символ не точка. `Configuration.xml` должен лежать непосредственно
в подключённом корне. После изменения mounts контейнер требуется пересоздать.
Устаревшая переменная `MCP1C_CONFIG_SOURCE` больше не используется: перенесите
её mount под `/config-sources/<id>` и выберите его в дашборде.

На странице **«Источники»** выберите загруженную конфигурацию и нажмите
**«Выбрать каталог» в её шапке**, рядом со статусом и удалением. Достаточно
базовой структуры schema v1: заранее загружать код не требуется. Кнопка
появляется, только когда доступны корни `/config-sources/`. В открывшемся
окне выберите корень и нажмите **«Подключить»**. После привязки в той же
шапке доступны **«Сменить каталог»** и **«Обновить из каталога»**. Интерфейс
показывает только непосредственные каталоги под `/config-sources/`, без
обхода их подпапок и без приёма произвольного пути компьютера. Это область,
которую администратор выделяет для mounts; Docker socket серверу не нужен.
При привязке проверяются доступность, безопасное дерево и совпадение вида и
внутреннего имени конфигурации. Имя папки и версия не являются identity;
обновление версии допустимо. Клоны с одинаковым внутренним именем этот
контракт не различает. Привязки сохраняются в
`data/config-source-bindings.json`, переживают restart; отключение привязки
не удаляет ни каталог, ни уже загруженные данные. Привязки расширений пока
не поддержаны, их загрузка через ZIP остаётся доступной.

Кнопка **«Обновить из каталога»** появляется только у привязанной конфигурации.
Она заново проверяет identity и SHA-256 всех файлов выбранного корня, после
чего сразу запускает подготовку полного обновления Source B (`update_full`)
и открывает обычный Предпросмотр без выбора состава. Для Source B во всех
путях intake доступны только `create` и `update_full`; частичной загрузки нет.
Только **«Опубликовать»** меняет активное поколение. Перед
публикацией содержимое каталога проверяется повторно: подмена конфигурации,
отключение привязки, недоступность или изменение файлов после preview
блокируют публикацию.
Предпросмотр и действующие данные сохраняются; исправьте источник и
подготовьте новое обновление. На время проверки и публикации завершите
выгрузку файлов: read-only mount запрещает запись контейнеру, но не хосту.

При полном обновлении общий backend для каталога, browser и incoming
сначала сверяет SHA-256 входа, identity и происхождение всех слоёв. Если вход
совпадает с действующим полным поколением source B и версии разбора/отбора
не изменились, повторный разбор пропускается. Остаются обычные preview и
подтверждение no-op; новое поколение не публикуется. Новые даты файлов при
тех же байтах не мешают проверке. При отличии транспорта, имени источника,
наличии структуры source A или неполном совпадении выполняется полный разбор.
Каталог перед подтверждением снова проверяется целиком; для ZIP подтверждается
подготовленный снимок. Повторные обходы каталога объединены, но полное чтение
для SHA-256 остаётся. Фонового наблюдателя, Git и инкрементального parser-а нет. Кнопки каталога получают состояние
отдельным лёгким запросом, не хеширующим выгрузку.
Подготовленное обновление каталога открывается только у своей конфигурации;
preview ZIP остаётся в общем блоке. Закрытие окна не отменяет подготовку,
повторное открытие доступно и после перезапуска. Проверка `incoming`
выполняется по `GET .../intake`. В одном экземпляре сервера одновременно
выполняется одна тяжёлая операция intake.

Если сервер перезапущен непосредственно во время разбора, незавершённая
операция становится `failed` с явной причиной: процесс, владевший ею, уже
завершён, поэтому автоматически продолжать её небезопасно. Запись операции и
её параметры сохраняются для аудита, а частичные рабочие файлы и preview
удаляются. Запустите обновление заново по актуальному кандидату.

Административный API (нужен `ADMIN_TOKEN`; браузерная сессия также проверяется
на same-origin):

| Запрос | Параметры JSON / результат |
|---|---|
| `GET /api/v1/sources/directories` | `roots`, `bindings`, `configuration_names`; без чтения содержимого выгрузок |
| `GET /api/v1/sources/intake/jobs` | сохранённые `jobs` с `transport`; без обнаружения и хеширования новых выгрузок |
| `POST /api/v1/sources/directories/bind` | `configuration`, `source_id`; проверить и сохранить/заменить привязку |
| `POST /api/v1/sources/directories/unbind` | `configuration`; отключить каталог |
| `POST /api/v1/sources/directories/refresh` | `configuration`; проверить источник и вернуть `candidate` для существующего `/intake/start` |

Для замеров на большой выгрузке предусмотрен изолированный стенд. Он копирует
исходник во временный каталог и создаёт отдельный Registry; рабочий сервер
и оригинал не меняются. Сценарии: первое полное обновление, повтор без изменений,
добавление процедуры в один BSL-файл копии. JSONL содержит размер, длительности
проверки/подготовки/публикации и накопленный пик RSS процесса; ожидание стабильности
файлов и копирование в длительности стадий не включены.

```bash
.venv/bin/python tools/lab/measure_directory_refresh.py --source /path/to/export > /tmp/directory-bench.jsonl
# Синтетическая нагрузка из BSL без разнообразия реальных форм и ролей:
.venv/bin/python tools/lab/measure_directory_refresh.py --modules 1024 --kib 256 > /tmp/directory-synthetic.jsonl
```

Замер 2026-09-06 указанной командой с `--source`: 24 111 файлов,
767 109 138 байт, macOS arm64, Python 3.12.6, без Docker. Сумма стадий:
первая загрузка 95,9 с; повтор без изменений 26,7 с; изменение одного BSL
91,4 с. Это единичный прогон на копии; время зависит от файловой системы.
Полный SHA-256 каталога остаётся обязательным, поэтому no-op не мгновенный.

Для разбора затрат добавьте `--profile-dir /tmp/directory-profile`: стенд сохранит
отдельный cProfile для каждой стадии. Откройте профиль командой
`.venv/bin/python -m pstats /tmp/directory-profile/unchanged-prepare.prof`,
затем введите `sort cumulative` и `stats 20`. Профилирование само замедляет выполнение: его время нельзя сравнивать
с обычным прогоном как результат оптимизации. Файлы профилей сохраняйте локально.

`SettingsStorages` в текущий приём source B намеренно не входят целиком:
дескрипторы, `Form.xml`, модуль менеджера и модули форм отбрасываются до
coverage и не создают ошибку или статус частичного разбора. Прежний частичный
приём одного BSL без структуры удалён. Поэтому источники, разобранные до
`selection_version=7`, требуют явного повторного разбора, но сервер не изменяет
рабочие данные автоматически.

`Subsystems` из Source B поддерживаются и в tree-, и в flat-выгрузках.
Иерархия входит в каноническое полное имя:
`Подсистема.<Родитель>.<Потомок>...`; это сохраняет различие одноимённых
узлов в разных ветвях. Для навигационного поиска укажите
`search_objects(kind="Подсистема")`; прямое чтение выполняется по полному имени
через `get_object`. Карточка показывает свойства и полный `Content`, а
существующий граф даёт прямые дочерние связи,
состав раздела и обратный ответ «в какие подсистемы входит объект».
Каждая цель состава в карточке явно помечена как разрешённая или неразрешённая.
Неразрешённая ссылка не удаляется и не выдаётся за существующий объект.

`Ext/CommandInterface.xml` сохраняется как **статическая декларация**:
видимость, ролевые переопределения, размещение и порядок команд, групп и
подсистем. Это не фактический интерфейс текущего сеанса — на него дополнительно
влияют права, функциональные опции и контекст пользователя. Карточка выдаёт не
более 50 элементов состава и интерфейса за вызов. Продолжение приходит готовым
вызовом прежнего `get_object` с непрозрачным `cursor`, привязанным к объекту и
поколению; новый MCP-инструмент не добавлен. Source A этих сведений не содержит.

Source A и Source B представляют одну конфигурацию, а не две независимые базы.
Отсутствующий `Configuration.Version` допустим в обоих источниках: версия
конфигурации сохраняется как неизвестная (пустая строка) при публикации и после
перезапуска. Версия конфигурации не заменяет runtime-версию платформы.
Если активна A, сервер работает в режиме `A_ONLY`: доступны только её
самостоятельная runtime-структура и точные сведения о платформе. Если активен
B, сервер работает в режиме `B_FULL`: один согласованный снимок даёт базовую и
расширенную структуру, код, формы и роли. Эти режимы не смешиваются. Загрузка A
поверх B атомарно отключает все B-слои и расширения; загрузка B поверх A строит
чистый B-снимок, а прежние расширения сами не воскресают.
При аварии после переключения active generation восстановление завершает
снятие roots только тех расширений, которые записаны в durable recovery-плане.
До переключения прежние расширения остаются активными. Поиск, карточки,
граф и MCP работают с одним active resolved-каталогом: общие реквизиты, параметры
сеанса, журналы
документов, планы обмена, подписки, задания, общие формы и поддержанные боты не
требуют отдельного режима запроса. Несовместимый overlay в смешанном A/B view
отклоняется до смены active generation. Повторная Source A с тем же
семантическим SHA `base_structure` является no-op только внутри уже активного
`A_ONLY`; после `B_FULL` она всё равно меняет active generation. Компактный
каталог происхождения основной структуры восстанавливается из проверенного
слоя native generation и после restart. Старое mixed-поколение получает
`RELOAD_REQUIRED` и не мигрирует само.

HTTP-сервисы доступны из Source B теми же `search_objects` и `get_object`, что
и остальные объекты. Карточка показывает `RootURL`, URL-шаблоны, HTTP-методы и
точные адреса функций `HTTPСервис.<Имя>::<Handler>`; `get_callers` возвращает
обратную привязку метода к функции. Путь выводится относительно публикации как
`/hs/<RootURL><Template>`: адрес сервера и имя публикации информационной базы
в файловом descriptor отсутствуют. `ReuseSessions` и `SessionMaxAge` появились
в платформе 8.3.9 и относятся ко всему сервису. Если этих узлов нет, сервер не
подставляет default: при известной платформе ниже 8.3.9 они неприменимы, а без
точной runtime-версии остаются не представленными в Source B. Поддерживается
всё перечисление `HTTPMethod`, включая `Any`; новое неизвестное значение
сохраняется с диагностикой, а не отклоняет всю выгрузку.

Карточки больших HTTP-сервисов выдаются ограниченными страницами: не более 40
URL-шаблонов и 80 методов за вызов. Если данные остались, ответ содержит
готовый следующий вызов `get_object` с непрозрачным `cursor`; его нужно
повторить без изменения `full_name`, `config` и `detail`. Новый поиск или новый
инструмент для продолжения не нужен. Курсор связан с выбранным объектом и
поколением данных: если за время чтения источник сменился, сервер отклонит
курсор и предложит начать карточку заново, не смешивая две версии сервиса.

XDTO-пакеты доступны из доказанной tree-раскладки Source B. Корневая карточка
имеет адрес `ПакетXDTO.<Имя>`, а определения —
`ПакетXDTO.<Имя>.ТипОбъекта.<Имя>`,
`ПакетXDTO.<Имя>.ТипЗначения.<Имя>` и
`ПакетXDTO.<Имя>.Свойство.<Имя>`. Они находятся обычным `search_objects` и
читаются обычным `get_object`; нового MCP-инструмента не требуется. В памяти
постоянно остаётся компактный индекс имён, пространств и импортов, а полный
`Ext/Package.bin` выбранного пакета читается лениво из проверяемого member
поколения. Карточка различает локальные, межпакетные, платформенные и
неразрешённые ссылки, понимает QName с локальной областью префикса и Clark
notation `{namespace}name`. Semantic hash нормализует эти формы по фактическому
пространству имён: смена привязки префикса считается изменением пакета, а простое
переименование префикса — нет. Отсутствующие `elementFormQualified`,
`attributeFormQualified` и `xdto:qualified` не подменяются значением `false`.
Namespace scope переиспользуется между элементами, а локальное объявление
создаёт неизменяемый overlay без копирования родительской области. На один
пакет действуют пределы: 64 МиБ, 1 000 000
XML-элементов, 100 000 объявлений namespace, 10 000 namespace в одной области
и глубина 512; превышение безопасно отклоняется. Неизвестный узел сохраняется
в semantic hash и выдаёт диагностику. Flat-имя и
семантика XDTO-пакетов, а также XDTO из расширения пока не заявлены: в
проверенном корпусе такого образца нет.

Если во время построения индексов Source A другая операция обновила или
удалила ту же конфигурацию, загрузка A завершается ошибкой с предложением
повторить её. Уже опубликованное состояние не заменяется устаревшим:
повторная загрузка заново проверит актуальную базу и сохранит слои B.
В дашборде конфликт отображается в результате фоновой загрузки; исходный
файл можно загрузить повторно после завершения конкурирующей операции.
Разбор A не блокирует чтение текущей конфигурации.

Основная файловая выгрузка должна быть опубликована раньше первого поколения
расширения: расширение не создаёт родительскую конфигурацию. Дальше каждый
extension-layer живёт отдельно и сохраняет собственные объекты, код, формы,
роли и жёсткие ссылки заимствований. Полное обновление базы строго заменяет её
структуру и одним линейным проходом перепроверяет сохранённые ссылки всех
расширений без чтения их исходных ZIP. Исчезнувшая цель получает
`target_missing`: preview называет расширение и адрес, orphan-overlay не входит
в resolved context, но публикация базы не блокируется, а собственный слой
расширения не удаляется. Фактическая активность расширения по-прежнему известна
только из отдельного сеансового снимка; его отсутствие не означает
«отключено».

Удаление карточки расширения требует точного подтверждения и снимает весь
опубликованный слой расширения: active generation, структуру, код, формы, роли,
индексы и журнал покрытия. Родительская конфигурация и независимый сеансовый
снимок активности остаются. Для native generation кнопка доступна и без
отдельной legacy-строки `sources`; снятое расширение не возвращается после
restart.

После полной native-публикации удаление не зависит от наличия прежних строк
`sources`. Source A и основной корпус Source B отдельно не удаляются: на
странице есть одно действие «Удалить целиком». Оно каскадно снимает
`base_structure`, `extended_structure`, код, формы, роли, их индексы и журналы,
сеансовый снимок, все привязанные расширения и относящиеся к агрегату
intake-job/preview/commit/work. Пустые каталоги поколений и расширений также
удаляются, включая родительский каталог конфигурации после последнего
legacy-расширения. Удаление отдельного расширения по-прежнему затрагивает только
его поколение. Операция требует ввода точного идентификатора; `incoming/` и
read-only исходники она не изменяет, поэтому оставшийся там ZIP снова виден как
кандидат создания. Повтор того же административного удаления по точному имени
также завершает очистку durable jobs, если Registry уже был снят прежней
версией сервера.

Удаление оставшегося неиспользуемого файла через
`POST /api/v1/sources/forget` требует административного доступа и точного
относительного пути в `path` и `confirmation`. Registry проверяет текущее
владение непосредственно при удалении: активный или подготавливаемый файл
получает HTTP 409. На время загрузки защищены читаемый вход, сохраняемая копия
и временный файл; они не показываются как неиспользуемые. После ошибки загрузки
резерв освобождается. Другие неиспользуемые файлы можно удалять параллельно.
Удаляются только обычные файлы внутри `sources/`, без перехода по символическим
ссылкам; отсутствующий файл возвращает HTTP 404.

Schema v1 снимается из работающей конфигурации и поэтому уже может видеть
собственные объекты активного расширения как обычные объекты базы. При выборе
этого расширения resolver считает такую запись runtime-проекцией только при
совпадении полного адреса и точного набора адресов всех полей; тогда в
resolved context используется native-объект source B. Расхождение хотя бы
одного поля останавливает разрешение как несинхронную пару, а аналогичный
дубль между двумя native-слоями никогда не маскируется. Provenance
`schema-v1` сохраняется и после Source A поверх native generation,
поэтому та же сверка `Fields` не превращается в ложный native-конфликт.

Цена этой перепроверки измерена 2026-09-02 на синтетическом снимке из 57 892
base identities и 458 рёбер на расширение:

```bash
.venv/bin/python tools/lab/measure_extension_recheck.py \
  --base-identities 57892 --edges-per-extension 458 \
  --extensions 0,1,3 --repeat 20
```

Медиана составила 0,001 / 7,328 / 9,077 мс для 0 / 1 / 3 расширений, максимум
— 0,028 / 9,976 / 10,234 мс. Дополнительный peak RSS — 0 / 6,141 / 6,219
МиБ: base identity index строится один раз на все расширения, поэтому память не
умножается на их число. Команда читает только сохранённый generation snapshot,
а не source ZIP.

Во время атомарной публикации нового поколения `/api/v1/sources` может
кратковременно ответить `409`: это означает конфликт чтения поколений, а не
повреждение источника. SPA ограниченно повторяет запрос и не ослабляет
generation-safe проверку снимка.

Не подходят ни `.cf` из команды «Сохранить конфигурацию в файл», ни `.dt`
выгрузки информационной базы. Для `incoming/` в диалоге «Выгрузить конфигурацию
в файлы…» нужно выбрать именно вариант **«Архив»**, а не каталог XML-файлов.

### Стандартные реквизиты объектов

Карточки `get_object`, поиск и индексы показывают стандартные реквизиты рядом
с реквизитами разработчика. Они не копируются в исходные слои: сервер
одинаково выводит их из свойств Source A или Source B при построении единого
runtime-view.

| Объект | Стандартные реквизиты в карточке |
|---|---|
| Документ | `Ссылка`, условный `Номер`, `Дата`, `Проведен`, `ПометкаУдаления` |
| Справочник | `Ссылка`, условные `Код` и `Наименование`, условные `Владелец`, `Родитель`, `ЭтоГруппа`, затем `ПометкаУдаления`, `Предопределенный`, `ИмяПредопределенныхДанных` |
| Журнал документов | фактический состав `StandardAttributes`, приведённый к русским query-именам: `Тип`, `Ссылка`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления` |
| Регистр сведений | условный `Период`; при подчинении регистратору — `Регистратор`, `НомерСтроки`, `Активность` |
| Регистр накопления | `Период`, `Регистратор`, `НомерСтроки`, `Активность`; у регистра остатков — `ВидДвижения` |
| Регистр бухгалтерии | `Период`, условный `УточнениеПериода`, `Регистратор`, `НомерСтроки`, `Активность`; с корреспонденцией — `СчетДт`/`СчетКт`, без неё — `Счет`/`ВидДвижения` |
| Регистр расчёта | `ПериодРегистрации`, `Регистратор`, `НомерСтроки`, `ВидРасчета`, условные поля периода действия и базового периода, `Активность`, `Сторно` |

`Ссылка` имеет точный тип самого объекта. `Код` и `Номер` сохраняют строковые
либо числовые квалификаторы; фиксированная и переменная длина различаются в
карточке. Если нескольким документам назначен нумератор, Source B читает его
descriptor как скрытую структурную зависимость и применяет эффективные
правила ко всем этим документам — отдельная карточка нумератора не создаётся.
Отсутствующий descriptor останавливает публикацию, а старый снимок без
доказанных правил оставляет тип `Номер` неизвестным.

У журнала `Ссылка` является составным типом зарегистрированных документов, а
`Номер` — объединением их фактических строковых и числовых типов. Неизвестный
зарегистрированный документ не заменяется догадкой. `Проведен` остаётся
системным полем документа независимо от настройки проведения; эта настройка
управляет поведением проведения, а не существованием поля. Здесь описана
структура метаданных, а не экземпляры: UUID созданных объектов и другие данные
информационной базы сервер не читает.

Карточка регистра показывает не только доступные таблицы запроса, но и причины
наличия или отсутствия условных таблиц:

| Таблица | Условие платформы |
|---|---|
| `СрезПервых`, `СрезПоследних` | регистр сведений периодический |
| `Остатки`, `ОстаткиИОбороты` регистра накопления | вид регистра — `Остатки` |
| `ОборотыДтКт` регистра бухгалтерии | включена корреспонденция |
| `Субконто` регистра бухгалтерии | задан план счетов и известно число субконто |
| `ФактическийПериодДействия` | включен период действия регистра расчёта |
| `ДанныеГрафика` | включен период действия, задан и разрешён регистр графика |
| `База<ИмяРегистра>` | включен базовый период; через план видов расчёта разрешён конкретный базовый регистр |

Базовый период и период действия — независимые условия: базовый период не
создаёт `ДанныеГрафика`, а период действия сам по себе не создаёт таблицу
`База<ИмяРегистра>`. Правила являются встроенным знанием сервера; Source A/B
поставляет только свойства конкретного регистра и ссылки на связанные планы и
график. Если свойство отсутствует в Source A/B или не было прочитано, карточка
показывает `unknown`: условная таблица или поле не перечисляются, но сервер не
называет признак выключенным и значение нулевым. Явные `false`, пустая ссылка
и ноль остаются доказанным отсутствием. Серый стандартный реквизит
Конфигуратора, который нельзя выбрать в запросе, не выдаётся как доступное поле.

Для точного состава дебетовых, кредитовых и корреспондирующих полей серверу
нужен признак `balance` каждого измерения и ресурса регистра бухгалтерии.
Source B уже содержит его в descriptor. Source A получает его начиная с
`exporter_version=2.1`; старый архив остаётся читаемым, но для точной карточки
бухгалтерского регистра его нужно перевыгрузить новой обработкой.

В `bootstrap/` принимаются:

- ZIP структуры конфигурации по schema v1;
- `shcntx_ru.hbk` — справка платформы.

На Linux копируйте сразу с владельцем контейнера:

```bash
sudo install -o 10001 -g 10001 -m 0640 \
  /путь/к/СтруктураКонфигурации.zip \
  /srv/mcp1c/data/bootstrap/

sudo install -o 10001 -g 10001 -m 0640 \
  /opt/1cv8/8.3.X.Y/shcntx_ru.hbk \
  /srv/mcp1c/data/bootstrap/
```

Пути и наличие `.hbk` зависят от установленной поставки платформы. В
репозитории этих файлов нет.

Большой архив команды Конфигуратора «Выгрузить конфигурацию в файлы…» кладите
в `incoming/`, не в `bootstrap/` и не в форму загрузки дашборда. Он разбирается
по явной административной команде из дашборда и не блокирует каждый старт
контейнера.

Запустить пустой сервер допустимо: health будет зелёным, но инструменты честно
сообщат, что конфигурации и справка не загружены. Исходники можно добавить
позже через дашборд или CLI.

### Встроенная общая справка

Каноническая SQLite schema v1 доставляется внутри одного подписанного
ZIP-артефакта с однозначным расширением `.mcp1cref`. Проверенная release-копия
лежит в `release-assets/reference/reference.mcp1cref` и при сборке образа
копируется в `/app/reference/reference.mcp1cref`, вне перекрываемого bind mount
`/data`. Исходные HBK, рабочая лаборатория и приватный signing key в публичный
артефакт, образ и репозиторий не входят.

Пакет фиксирован в образе по пути `/app/reference/reference.mcp1cref` и не
перекрывается bind mount `data/`. Runtime-загрузки, внешние override и
отключение источника не предусмотрены. Новый пакет поставляется только новым
подписанным образом. При старте проверяются строгий ZIP, manifest, Ed25519,
SHA-256, schema v1 и целостность SQLite; ошибка проверки останавливает startup.

В дашборде доступен только read-only просмотр статуса и материалов. Загрузка,
замена и удаление пакета отсутствуют.

Строгий состав `.mcp1cref` — ровно три файла без каталогов, симлинков,
шифрования и посторонних записей:

- `manifest.json` — канонический ASCII JSON в UTF-8: ключи отсортированы,
  разделители без пробелов, после объекта ровно один `LF`;
- `manifest.sig` — raw detached-подпись Ed25519 длиной 64 байта над точными
  байтами `manifest.json`;
- `reference.sqlite3` — каноническая база schema v1 размером до 32 МиБ.

Manifest содержит только `artifact`, `artifact_sha256`, `artifact_size`,
`format`, `format_version`, `key_id`, `logical_sha256`, `schema_version` и
`signature_algorithm`. Для текущего формата обязательны
`artifact=reference.sqlite3`, `format=mcp1c-reference`, `format_version=1`,
`schema_version=1` и `signature_algorithm=ed25519`. `artifact_sha256` связывает
все байты SQLite, а `logical_sha256` — её каноническое содержимое schema v1.
`key_id` выбирает один из встроенных открытых ключей и позволяет безопасно
добавлять следующий ключ до снятия предыдущего; неизвестный ключ всегда
`untrusted`.

Первый release-ключ имеет `key_id=reference-2026-01`. SHA-256 fingerprint его
raw 32-byte public key:
`509d077f669ebf935aa03453bdb1e904f95e0192fdf265b2c45b239678615c2e`.
Fingerprint позволяет независимо сверить trust root официального исходного
кода; приватная половина в репозиторий, образ и `data/` не входит.

Порядок fail-closed: сервер сначала проверяет строгий ZIP, канонический manifest,
известный `key_id`, detached-подпись, размер и SHA-256 SQLite. Только затем он
извлекает базу в закрытый расходный каталог, открывает её read-only с
`immutable=1` и проверяет точную схему, `integrity_check`, внешние ключи,
JSON-поля и подписанный логический SHA-256. Некорректный кандидат не заменяет
прежний артефакт и не создаёт провайдер.

Наличие `search_reference` и `get_reference` определяется только capability
`reference`; состояние производного индекса на состав MCP не влияет.
Административный маршрут сначала отвечает `202`, затем завершает только
серверный процесс; Compose с `restart: unless-stopped` поднимает тот же
контейнер и bind-том. SPA ждёт новый `runtime_id` в `/health`, после чего
направляет на повторный вход: MCP-сеансы и cookie хранятся в памяти процесса.
Без `MCP1C_ALLOW_SELF_RESTART=1` кнопка скрыта, чтобы запуск без внешнего
supervisor не мог погасить себя окончательно.

Поисковый индекс — расходный файл `data/index/reference/reference.search`.
Он не очищается при каждом старте: совпавшие SHA-256 базы, версия Python и
отпечаток кода дают тёплый `cache hit`. Замена базы, изменение кода, неверный
штамп или повреждение кэша приводят к безопасной пересборке из SQLite.

Для выпуска новой встроенной версии заменяют только
`release-assets/reference/reference.mcp1cref` уже подписанным и независимо
проверенным пакетом командой
`.venv/bin/python tools/sync_reference_release_asset.py`. Она повторно проверяет
подпись, manifest, schema v1 и строгий состав ZIP, затем атомарно заменяет
tracked-копию. Предварительная проверка без записи:
`.venv/bin/python tools/sync_reference_release_asset.py --dry-run`. После
синхронизации запускают reference, signature и deployment-тесты. Приватный ключ
для этой операции не нужен и не должен появляться в рабочем дереве.

Страница «Общая справка» доступна из навигации SPA с правом чтения.
Она вызывает тот же поиск и чтение карточки, что MCP, и ничего не изменяет.
Боковая панель показывает подтверждённую подпись только для готового пакета с
`ed25519`; при `missing`, `untrusted`, `corrupt`, несовместимом формате или
ошибке status API она показывает причину и не объявляет справку доверенной.
Диалог доступен с клавиатуры: фокус входит при открытии, `Tab` остаётся внутри,
`Escape` закрывает его и возвращает фокус на исходную кнопку.
Основная форма содержит поисковую фразу и понятный раздел; точный вид,
проверка совместимости с версией, служебные и архивные материалы раскрываются
отдельно. Сначала показываются пять компактных результатов, следующие
запрашиваются кнопкой без ручного ввода лимита. Сигнатура, причина совпадения
и доступность видны прямо в списке, а полный безопасно разобранный Markdown
открывается отдельной карточкой с возвратом к выдаче и продолжением длинного
текста. В состояниях `disabled`, `missing`, `untrusted`, `incompatible` и
`corrupt` страница показывает безопасную причину и ссылку на «Источники», но
не рисует неработающую форму.

## Публикация, хранение и проверка результата

### Быстрая базовая загрузка — source A

Source A — архив `СтруктураКонфигурации_*.zip`, созданный внешней обработкой
проекта. Внутри есть `manifest.xml` или `manifest.json` и части
`objects/*`; полный файловый экспорт Конфигуратора таким manifest не обладает.

Передать source A можно тремя способами:

1. На странице «Источники» выбрать «Загрузить источник».
2. Положить архив в `data/bootstrap/` для первой загрузки чистого Registry.
3. Выполнить `python -m mcp1c.cli --data data reg-add <путь>`.

Эта операция публикуется сразу после проверки schema v1. Отдельного
Предпросмотра для неё нет. В новом или ещё не мигрировавшем Registry она
остаётся совместимой записью `legacy`: установка нового пакета и обычный
рестарт сами по себе не создают native `manifest`, не копируют исходник и не
переразбирают рабочие данные.

Если для этой конфигурации уже опубликована полная source B, source A
атомарно создаёт следующее native-поколение режима `A_ONLY`. В нём остаётся
только новый `base_structure`; `extended_structure`, код, формы, роли и
расширения прежнего B-поколения отсоединяются и не участвуют в active view.
После рестарта сохраняется `A_ONLY`, а старые B-данные не воскресают.
Идентичная source A является no-op только если такой же `A_ONLY` уже активен;
переход из `B_FULL` всё равно публикует новый A-переход.
Неполная Source A с `truncated=true` или
`predefined_available=false` поверх native generation не публикуется:
иначе признаки неполноты были бы потеряны после restart. Отказ не
меняет прежнее активное поколение.

Source A не содержит объявленных прав ролей и не расширяется ради них. Он
также не гарантирует все виды метаданных, доступные в файловой выгрузке.
Source A и source B никогда не смешиваются в одном active-поколении.

### Полная загрузка — source B

Source B — ZIP штатной команды «Конфигурация → Выгрузить конфигурацию в
файлы… → Архив» в Конфигураторе или эквивалентный файловый экспорт EDT. Один
его снимок строит пять независимых слоёв:

- `base_structure` — базовая проекция объектов и полей;
- `extended_structure` — сведения, которых нет в schema v1;
- `code` — фактически найденные модули;
- `forms` — формы и их доказанная структура;
- `roles` — descriptor ролей и объявленные права, включая RLS.

Исходник source B можно предоставить так:

- загрузить ZIP до 4 ГиБ в блоке «Полная файловая выгрузка» страницы
  «Источники»;
- самостоятельно положить ZIP в `data/incoming/` и нажать «Проверить
  обновления»;
- смонтировать корень распакованной выгрузки в `/config-sources/<id>` с `:ro`
  и выбрать его кнопкой «Выбрать каталог» в шапке загруженной конфигурации.

Предел 4 ГиБ относится только к передаче browser-upload. Для уже размещённого
`data/incoming/` и настроенного read-only источника сырой размер ZIP или
каталога не ограничивается. Принятый через браузер ZIP и архив из `incoming`
читаются одинаково: без отдельных пределов на размер элемента, коэффициент
сжатия и суммарный распакованный объём. В обоих случаях проверяются безопасные
и однозначные пути, symlink, специальные файлы, шифрование, предел 100 000
записей, CRC и неизменность архива. Проверка `Configuration.xml` ограничена
8 МиБ. Известный игнорируемый балласт не распаковывается и не блокирует
обнаружение. У настроенного read-only источника открытые parser-ом элементы
остаются в общем ресурсном бюджете.

Показываются только непосредственные корни `/config-sources/`, не подпапки.
Произвольный путь машины через HTTP передать нельзя. Singleton-переменная
удалена. Привязки сохраняются в `data/config-source-bindings.json`.
Подключение и «Обновить из каталога» проверяют внутреннее имя и вид
конфигурации; перед публикацией также сверяется полный SHA-256 с preview.
Подмена или недоступность каталога блокируют обновление без изменения
действующей конфигурации. Одинаковые внутренние имена клонов не различаются.
Изменение версии допустимо. Git, наблюдение в фоне и инкрементальный разбор
не включены. «Обновить из каталога» после проверки сразу запускает
`update_full` и показывает Предпросмотр без выбора состава; публикация остаётся
отдельным действием. Подробные примеры Compose приведены в [инструкции по установке](installation.md); API описан в разделе [двухфазного intake](#двухфазный-intake-api).

### Действие, Предпросмотр и публикация

После обнаружения source B интерфейс показывает только допустимые действия:

| Состояние | Действие | Какие слои публикуются |
|---|---|---|
| Основной конфигурации ещё нет | «Создать конфигурацию» | все доступные слои |
| Основная конфигурация есть только как `legacy` | «Обновить полностью» | первое native-поколение: все пять слоёв из одного снимка |
| Основная конфигурация уже имеет native generation | «Обновить полностью» | все пять слоёв из одного снимка |
| Новое или существующее расширение | «Обновить полностью» | отдельное поколение расширения; обязательна родительская конфигурация |

Нажатие действия запускает серверный разбор, но ещё не меняет активные данные.
Готовый Предпросмотр показывает послойный semantic diff, сохранённые слои,
локальные ошибки и no-op. Только кнопка «Опубликовать изменения» атомарно
переключает `manifest` активного поколения. Durable preview сохраняется на
сервере до открытия диалога; крестик лишь закрывает его, а список готовых
preview обновляется автоматически. «Отменить и удалить preview» снимает job и
её рабочие данные без повторного запроса уже удалённой job. Параллельный
снимок списка видит согласованное состояние до либо после удаления, но не
частично удалённую job и временный HTTP 409.
Закрытие вкладки само по себе не является ни публикацией, ни удалением.
При полном обновлении с изменениями публикуются все пять слоёв нового Source B,
включая семантически неизменённые: provenance у них относится к одному снимку.
Старое A/B-поколение без валидной активации или native pointer получает
`RELOAD_REQUIRED` и не выдаёт конфигурационные данные до явной полной
загрузки A или B;
restart сам его не исправляет. Частично опубликованное B/B-поколение с
валидной активацией остаётся читаемым, но требует полного обновления для
выравнивания структуры с ZIP.

Частичного действия `update` в planner нет. Старый durable request с этим
значением показывается как устаревшая failed-job; публикация возвращает
контролируемый конфликт и не меняет Registry.

После публикации native generation кнопки удаления не зависят от прежних строк
legacy Registry. Корзина у «Основной конфигурации» снимает `code` и `forms`, но
создаёт новое атомарное поколение с сохранёнными `base_structure`,
`extended_structure` и ролями. Кнопка «Удалить» в шапке конфигурации — другое,
каскадное действие: она снимает структуру, основной корпус, все поколения
привязанных расширений и связанные intake-job/preview/commit/work. Пустые
каталоги поколений и расширений также удаляются. Диалог заранее показывает
границу и требует точного идентификатора. Архивы в `incoming/` ни одно из этих
действий не удаляет; поэтому их можно снова увидеть как кандидатов создания.

Расширение никогда не создаёт основную конфигурацию. До разбора нужно явно
выбрать уже загруженный `parent_configuration`; без выбора действие
недоступно, а неверный родитель даёт отказ до публикации. Основная
конфигурация и каждое расширение имеют независимые generation pointers.

### Что записывается в `data/`

`data/` — переносимый рабочий том установки, а не часть пакета и не часть git.
Пакет создаёт каталоги только по мере реальной операции:

- browser-upload source B сначала попадает в управляемый durable staging;
- после Предпросмотра и подтверждения Registry записывает неизменяемое
  поколение и active pointer в `registry.json`;
- после durable commit временные collection/materialized-копии удаляются, а
  для повторного идемпотентного `confirm` остаётся компактная job с commit
  result; browser-upload после успешной публикации также удаляется;
- `data/incoming/` принадлежит оператору: сервер читает, но не удаляет
  положенные туда архивы;
- исходник read-only mount также не меняется;
- расходные поисковые и role-индексы строятся из опубликованного поколения и
  могут быть безопасно восстановлены без исходного ZIP.

При замене поколения старые payload удаляются только после durable commit.
Ошибка до commit сохраняет прежнее поколение. Обычная переустановка пакета не
является загрузкой, миграцией или подтверждением: она не создаёт manifest для
старого `legacy` Registry. Переход происходит после первой успешно
подтверждённой полной загрузки source B; затем прежние управляемые base/code
файлы снимаются с учёта.

### Проверка после публикации

На странице «Источники» проверьте имя конфигурации, active generation, SHA
источника и состояния каждого слоя. `roles=ready` означает только наличие
снимка объявленных прав; это не эффективный доступ пользователя.

Затем откройте конфигурацию обычным MCP-вызовом `list_configurations`, найдите
объект и процедуру, а для ролей откройте `/roles`. Большие роли и RLS читаются
страницами: полный текст ограничения появляется только по явному запросу.

Для расширения дополнительно проверьте выбранного родителя и состояния
заимствованных связей. `target_missing` сообщает, что цель исчезла из новой
базы: собственные объекты, код, формы и роли расширения сохраняются, но
orphan-overlay не подмешивается к структуре родителя.
