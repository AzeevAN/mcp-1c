# Дашборд MCP-сервера

Дашборд — браузерный интерфейс к тому же `Registry`, который обслуживает MCP.
Он не читает `data/` напрямую, не запускает второй backend и не создаёт вторую
копию индексов. Переключение интерфейса не меняет `/mcp`, формат источников или
содержимое каталога данных.

Полный запуск контейнера, включая подготовку прав Linux, описан в
[основном README](../README.md#запуск-в-docker). Этот файл описывает только
режимы и разработку интерфейса.

## Режимы

| Режим | Compose-файлы | Что доступно |
|---|---|---|
| Без UI | `docker-compose.yml` | `/mcp`, `/health`, служебный HTTP API |
| Классический | базовый + `docker-compose.classic.yml` | серверный HTML без frontend-сборки |
| SPA | базовый + `docker-compose.dashboard.yml` | React-интерфейс и `/api/v1/*` |

SPA — основной современный интерфейс, классический HTML сохранён как
совместимый fallback. Оба используют одни операции backend и один Registry.

Запуск классического интерфейса:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.classic.yml \
  up -d --build --force-recreate
```

Запуск SPA:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.dashboard.yml \
  up -d --build --force-recreate
```

Оба варианта открываются на `http://127.0.0.1:5001/`, если
`MCP1C_PORT` не переопределён. Одновременно поднимать их из одной рабочей копии
не нужно: у них один service, имя контейнера, порт и каталог данных. Команда
`up --force-recreate` заменяет текущий вариант выбранным.

## Доступ

| Уровень | Как получить | Возможности |
|---|---|---|
| Открытый локальный | `API_TOKEN` пуст | чтение всех страниц для доступного по сети клиента |
| Читатель | вход с `API_TOKEN` | просмотр Registry, карточек, поиска и связей |
| Администратор | вход с `ADMIN_TOKEN` | чтение плюс загрузка, разбор, удаление и словарь |

При заданном `API_TOKEN` прямой адрес страницы ведёт на `/login` и после входа
возвращает на исходный URL. Серверная сессия хранится в `HttpOnly`,
`SameSite=Strict` cookie; frontend токен не хранит. Изменяющие запросы из
cookie-сессии дополнительно проходят same-origin-проверку.

`ADMIN_TOKEN` не следует передавать MCP-клиентам: агенту достаточно токена
чтения, а административный даёт право удалять источники и менять словарь.
Прямой API-клиент передаёт значение `ADMIN_TOKEN` в обычном для дашборда
`X-Api-Token` или Bearer-заголовке; `X-Admin-Token` относится только к
служебному `/admin/reload`, а не к `/api/v1/*`.

## Страницы

Классический интерфейс предоставляет:

| Страница | Назначение |
|---|---|
| Обзор | состав Registry, версии платформы, предупреждения источников |
| Источники | загрузка, входящие архивы, покрытие кода, удаление |
| Запросы | пакетный прогон формулировок с оценкой и причиной ранжирования |
| Связи | граф непосредственного окружения объекта |
| Карточка | тот же состав объекта или синтаксиса, который получает агент |
| Словарь | встроенные и локальные правила с происхождением |

SPA предоставляет те же предметные разделы в адаптивной оболочке. Выбранная
конфигурация и параметры страниц сохраняются в URL; результаты «Запросов» — в
`sessionStorage`, чтобы возврат из карточки не стирал прогон.

## Загрузка и входящие архивы

Форма «Загрузить» принимает:

- `СтруктураКонфигурации_*.zip` по schema v1, созданный внешней обработкой
  проекта;
- `shcntx_ru.hbk` со справкой платформы.

Большой ZIP с модулями и формами через эту форму не передаётся. Его создают в
**Конфигураторе: «Конфигурация → Выгрузить конфигурацию в файлы…», затем в
диалоге выбирают «Архив»**. Полученный ZIP копируют непосредственно в
`data/incoming/`, дожидаются завершения копирования и запускают «Разобрать» в
отдельном блоке страницы «Источники».

Это не тот же файл, что ZIP структуры из внешней обработки. Структура создаёт
конфигурацию в Registry, а incoming-архив только привязывает к уже существующей
конфигурации её код и формы. Поэтому структура должна быть загружена первой;
без родительской конфигурации кнопка «Разобрать» намеренно недоступна. Файлы
`.cf`, `.dt` и выбранный вместо архива каталог XML-файлов для `incoming/` не
подходят.

HTTP-предел файла — 500 МиБ, предел всего multipart-тела — 501 МиБ. Предел
применяется к `/sources` и `/api/v1/sources/upload`; остальные API сохраняют
меньшие самостоятельные границы. Загрузка сначала пишет временный файл,
проверяет фактический объём и только затем передаёт его общему `Registry`.

Единая форма «Загрузить источник» также принимает каноническую `.sqlite3`
schema v1 размером до 32 МиБ. Интерфейс сам направляет её в отдельный backend-
маршрут; в Registry она не попадает. Backend сначала проверяет структуру,
целостность, логический хеш и доверие к подписи, а затем атомарно сохраняет
файл в `data/reference/`. Отдельная карточка показывает только состояние базы.
Прежний снимок остаётся активным до перезапуска сервера. Некорректная загрузка
его не заменяет.

После перезапуска валидный файл добавляет MCP-инструменты `search_reference` и
`get_reference`; статус виден и в classic, и в SPA. При внешнем пути
`MCP1C_REFERENCE_DB` форма отключена, потому что жизненным циклом файла
управляет оператор. Экспериментальный неподписанный режим предназначен только
для локальной разработки и не разрешает деплой.

Разбор `data/incoming/` запускается отдельно: такие архивы могут занимать
гигабайты, поэтому сервер не перебирает их при каждом старте. При нескольких
конфигурациях родителя выбирает администратор; основной код или расширение
определяются по содержимому, а не по имени файла.

Неполная структура с `truncated=true` по умолчанию отклоняется. Явное
разрешение в UI публикует её с постоянным предупреждением, а не превращает в
обычный полный источник.

## Разработка SPA

Нужны Node.js 22 и npm. Backend для frontend-тестов не требуется:

```bash
cd dashboard
npm ci
npm test
npm run typecheck
npm run build
```

`npm run build` создаёт `dashboard/dist/`. Каталог является производным и не
коммитится. Docker target `runtime-dashboard` собирает его в отдельном
Node-stage и копирует только готовую статику; Node и `node_modules` в runtime
не переходят.

Для локальной разработки интерфейса:

```bash
cd dashboard
npm run dev
```

Vite проксирует API к backend согласно `dashboard/vite.config.ts`. Проверка
production-пути всё равно обязательна: прямые ссылки, `/login`, cookie,
статические `/assets/*` и внешний HTTP guard в dev-сервере не воспроизводятся
полностью.

## Граница реализации

- Python формирует предметные снимки, выполняет поиск, строит граф и проверяет
  права.
- React отвечает за навигацию, состояние формы и представление ответа.
- API не публикует файловые пути без административной необходимости.
- Frontend не рассчитывает собственный Registry и не повторяет ранжирование.
- MCP продолжает работать при `off`, `classic` и `spa` одинаково.

Подробный контракт API и причины архитектурных решений находятся в
[docs/dashboard-design.md](../docs/dashboard-design.md).
