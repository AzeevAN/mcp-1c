# Формат выгрузки структуры конфигурации 1С — schema_version 1

Контракт между обработкой 1С (`exporter-1c/`) и загрузчиком MCP-сервера.

Один и тот же логический формат сериализуется в **XML** или **JSON**. Выбор
формата делает пользователь при выгрузке. Загрузчик определяет формат по
манифесту и приводит оба варианта к единой внутренней модели.

---

## 1. Структура архива

```
СтруктураКонфигурации_<ИмяКонфигурации>_<ГГГГ-ММ-ДД>.zip
├── manifest.xml            (или manifest.json)
└── objects/
    ├── catalog.001.xml
    ├── catalog.002.xml
    ├── document.001.xml
    ├── informationregister.001.xml
    └── ...
```

* Объекты разбиты на чанки по видам метаданных, `chunk_size` объектов на файл
  (по умолчанию 500, задаётся на форме обработки).
* Имена файлов — **латиницей**, чтобы избежать проблем с кодировкой имён внутри ZIP
  на разных реализациях. Настоящий вид объекта хранится внутри файла и в манифесте.
* Кодировка всех файлов — UTF-8.
* Расширение файлов чанков совпадает с форматом манифеста. Смешение форматов
  внутри одного архива не допускается.

## 2. Конвенция «структура → XML»

Сериализация полностью механическая, поэтому XML-ридер и JSON-ридер отдают
идентичный словарь.

| Значение в модели | XML | JSON |
|---|---|---|
| скаляр (строка/число/булево) | атрибут элемента | свойство объекта |
| массив структур | `<ключ><item .../></ключ>` | `"ключ": [ {...} ]` |
| массив скаляров | `<ключ><item value="..."/></ключ>` | `"ключ": [ "..." ]` |
| вложенная структура | `<ключ .../>` | `"ключ": {...}` |
| пустой массив | элемент не пишется | свойство не пишется |

Булево в XML — строки `true` / `false`. Даты — ISO-8601 `yyyy-MM-ddTHH:mm:ss`.

## 3. Манифест

**manifest.xml**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<manifest schema_version="1"
          format="xml"
          exporter_version="2.0"
          name="УправлениеТорговлей"
          synonym="Управление торговлей"
          version="11.5.14.123"
          vendor="Фирма 1С"
          platform="8.3.21.1607"
          exported_at="2026-08-13T10:22:31"
          objects_total="14872"
          chunk_size="500"
          truncated="false"
          predefined_available="true">
  <warnings>
    <item text="Платформа не поддерживает перечисление предопределённых элементов…"
          details="Метод менеджера: … | Запрос: …"/>
  </warnings>
  <files>
    <item path="objects/catalog.001.xml" type="Справочник" count="500"/>
    <item path="objects/catalog.002.xml" type="Справочник" count="312"/>
    <item path="objects/document.001.xml" type="Документ" count="447"/>
  </files>
</manifest>
```

`warnings` — то, что выгрузка не смогла получить на этой платформе. Секция
пишется только при наличии проблем, максимум 20 уникальных сообщений. Загрузчик
обязан показать их пользователю: молчаливо неполная выгрузка хуже явной ошибки.

`predefined_available` — смог ли выгрузчик перечислить предопределённые
элементы. При `false` секции `predefined` в чанках нет, и конфигурация считается
неполной, пока не подгружен второй источник. Загрузчик обязан ориентироваться на
этот атрибут, а не разбирать текст предупреждений. Подробности и правило —
[data-sources.md](data-sources.md).

**manifest.json**

```json
{
  "schema_version": "1",
  "format": "json",
  "exporter_version": "2.0",
  "name": "УправлениеТорговлей",
  "synonym": "Управление торговлей",
  "version": "11.5.14.123",
  "vendor": "Фирма 1С",
  "platform": "8.3.21.1607",
  "exported_at": "2026-08-13T10:22:31",
  "objects_total": 14872,
  "chunk_size": 500,
  "truncated": false,
  "files": [
    {"path": "objects/catalog.001.json", "type": "Справочник", "count": 500}
  ]
}
```

`truncated="true"` означает, что выгрузка сделана с ограничением числа объектов
(тестовый режим) и **не является полной**. Загрузчик обязан отказаться заливать
такую выгрузку в рабочую коллекцию без явного подтверждения. В текущем
загрузчике подтверждение задаётся административно: `reg-add
--allow-truncated` либо галочкой «Разрешить неполную выгрузку» в дашборде.
Источник сохраняет признак неполноты, а после рестарта все ответы по нему
продолжают предупреждать, что отсутствие объекта или связи ничего не
доказывает. Автозагрузка из `bootstrap/` такого подтверждения не даёт.

Хеши файлов в манифест намеренно не пишутся: при добавлении объектов состав
чанков смещается и хеш файла перестаёт быть полезным. Инкрементальность
загрузчик считает по хешу **каждого объекта**, вычисляя его сам.

## 5. Модель объекта

### 5.1 Общие поля (у всех видов)

| Поле | Тип | Описание |
|---|---|---|
| `full_name` | строка | `Документ.РеализацияТоваровУслуг` — первичный ключ |
| `type` | строка | вид метаданных на русском |
| `name` | строка | имя без вида |
| `synonym` | строка | синоним (может быть пустым) |
| `comment` | строка | комментарий объекта, пишется только если заполнен |

**`type` на уровне объекта — только вид метаданных, строкой.** Список типов
значения живёт в `value_type` (константа, определяемый тип, план видов
характеристик) или внутри поля (§5.2). Ключ один и тот же, и это уже стоило
дефекта: обработка положила в объектный `type` массив типов, `Структура.Вставить`
заменила значение молча, а загрузка упала гораздо позже — на построении
поискового индекса, где вид объекта используется как ключ веса. Загрузчик
теперь отвергает такую выгрузку сразу и называет объект.

### 5.2 Поле (`attributes`, `dimensions`, `resources`)

| Поле | Тип | Описание |
|---|---|---|
| `name` | строка | имя реквизита |
| `synonym` | строка | синоним |
| `comment` | строка | если заполнен |
| `indexing` | строка | режим индексирования, если свойство есть |
| `type` | массив строк | **полные** имена типов, всегда полностью, без схлопывания |
| `string_length` | число | длина строки, если > 0 |
| `digits` | число | разрядность числа |
| `fraction_digits` | число | разрядность дробной части |
| `date_parts` | строка | части даты |

> **Важно.** Список типов пишется **целиком всегда**, даже если типов сотни
> (Регистратор, Субконто, Характеристика). Схлопывание в «(составной)» —
> задача рендера на стороне сервера, не выгрузки. Именно эти реквизиты несут
> основную часть рёбер графа связей.

### 5.3 Специфика по видам

Правило отбора: выгружается то, от чего зависит **состав полей запроса или
компилируемость кода**, а не оформление. `ПериодичностьРегистраСведений`
попадает сюда, потому что у непериодического регистра нет ни поля `Период`, ни
срезов; `ОсновнаяФормаСписка` — нет, она ни на что в коде не влияет.

| Вид | Дополнительные поля |
|---|---|
| Справочник | `hierarchical`, `hierarchy_type`, `code_length`, `description_length`, `code_type`, `owners[]`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| Документ | `posting`, `number_length`, `number_periodicity`, `number_type`, `numerator`, `real_time_posting`, `register_records_deletion`, `register_records_on_post`, `attributes[]`, `tabular_parts[]`, `movements[]`, `based_on[]` |
| РегистрСведений | `periodicity`, `write_mode`, `dimensions[]`, `resources[]`, `attributes[]` |
| РегистрНакопления | `register_kind`, `dimensions[]`, `resources[]`, `attributes[]` |
| РегистрБухгалтерии | `correspondence`, `chart_of_accounts`, `period_adjustment_length`, `dimensions[]`, `resources[]`, `attributes[]` |
| РегистрРасчета | `action_period`, `base_period`, `periodicity`, `chart_of_calculation_types`, `schedule`, `schedule_date`, `schedule_value`, `dimensions[]`, `resources[]`, `attributes[]` |
| Константа | `value_type` (структура с `type[]` и квалификаторами) |
| ОпределяемыйТип | `value_type` |
| Перечисление | `enum_values[]` (`name`, `synonym`) |
| ПланСчетов | `ext_dimension_types`, `max_ext_dimension_count`, `code_mask`, `code_length`, `description_length`, `accounting_flags[]`, `ext_dimension_accounting_flags[]`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| ПланВидовРасчета | `dependence_on_calculation_types`, `action_period_use`, `base_calculation_types[]`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| ПланВидовХарактеристик | `value_type` (тип значения характеристик), `characteristic_ext_values`, `hierarchical`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| ПланОбмена | `distributed_infobase`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| БизнесПроцесс | `task`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| Задача | `addressing`, `main_addressing_attribute`, `current_performer`, `attributes[]`, `tabular_parts[]`, `predefined[]` |
| ОбщийМодуль | `global`, `server`, `client_managed`, `server_call`, `privileged`, `external_connection`, `return_values_reuse` |
| ПодпискаНаСобытие | `event`, `handler` (`X.ИмяПроцедуры`; историческая форма `ОбщийМодуль.X.ИмяПроцедуры` тоже принимается), `source[]` (полные имена объектов) |
| РегламентноеЗадание | `method`, `use`, `predefined`, `key` |
| Отчет / Обработка | `attributes[]`, `tabular_parts[]` |

Любое поле может отсутствовать: свойства берутся по одному, каждое своей
попыткой, и то, чего нет на этой платформе, просто не попадает в выгрузку.
Загрузчик обязан переживать отсутствие любого из них.

## 6. Чего в формате намеренно нет

**Тексты модулей.** Платформа не предоставляет доступ к исходному коду модулей
из встроенного языка — обработка их получить не может в принципе. Индекс
процедур и функций строится из **выгрузки конфигурации в файлы**
(конфигуратор / EDT) отдельным путём загрузки. Метаданные и код — два
независимых источника, дополняющих друг друга.

**Данные.** В формате только структура конфигурации. Содержимое справочников и
регистров не выгружается. Исключение — предопределённые элементы и значения
перечислений: они являются частью конфигурации и нужны при написании кода.

> **Предопределённые на платформах до 8.3.6.** Проверено на 8.3.5: метода
> `ПолучитьИменаПредопределенных()` нет, поля `ПредопределенноеИмяДанных` в
> запросе тоже нет — имя предопределённого элемента там не хранится в данных и
> перечислить их из встроенного языка нельзя. Выгрузка пишет в манифест
> предупреждение и не создаёт секцию `predefined`. Источником для таких
> конфигураций должна стать выгрузка конфигурации в файлы. На 8.3.6+ секция
> заполняется обработкой штатно.

**Граф связей.** Обработка его не считает. Рёбра выводит загрузчик из `type[]`,
`movements[]`, `owners[]`, `based_on[]`, `handler`. Это снимает с 1С лишнюю
работу и позволяет менять правила построения графа без перевыгрузки.

**Формы, команды, макеты.** Отложено до schema_version 2 — на качество
генерации серверного кода влияют слабо, а объём выгрузки увеличивают заметно.

## 7. Совместимость и версионирование

* `schema_version` присутствует в манифесте и в каждом чанке.
* Загрузчик обязан отвергать неизвестную мажорную версию схемы с внятной ошибкой.
* Добавление новых **необязательных** полей версию не повышает.
* Удаление или переименование поля, изменение семантики — повышает.

До построения модели один validator проверяет весь конверт fail-closed:

* корни `manifest`/`objects`, `format` и обязательную строковую версию `1.x`;
* пути `objects/<имя>.<номер чанка из трёх цифр>.<формат>`, их уникальность и
  наличие в архиве;
* совпадение `schema_version`, `type`, `chunk` и `count` чанка с манифестом и
  именем файла;
* равенство фактического числа объектов `count`, суммы всех `files[].count` —
  `objects_total`, а также уникальность `full_name` во всей выгрузке.

XML хранит атрибуты строками, JSON — собственными scalar-типами. Загрузчик
нормализует документированные числовые и булевы свойства, поэтому выбор
формата не меняет модель объекта, граф или ответы инструментов.

Пустая конфигурация допустима: `files` может быть пустым массивом только при
`objects_total=0`. Любое расхождение — ошибка до публикации источника, а не
предупреждение. Официальные JSON- и XML-варианты экспортёра пишут `count` и в
манифест, и в конверт каждого чанка.

### Legacy-формат

Старая выгрузка (`objects.csv` + `*.md`, обработка v1) текущим загрузчиком не
поддерживается: без манифеста строгую границу целостности доказать нельзя.
Такой источник получает явный отказ и требует перевыгрузки текущей обработкой
из `exporter-1c/dist/`.
