# Приём выгрузки конфигурации в файлы — постановка

Дата: 2026-08-19. Статус: **реализовано 2026-08-19**; постановка оставлена как
запись решений, подробности реализации — в `CHANGELOG.md`.

Разведка до реализации измерила модель загрузки и состав выгрузки; здесь
решается только одно: **как файл
попадает на сервер и во что превращается**.

## Зачем

Выгрузка конфигурации в файлы — гигабайты. Замерено на Рознице 2.3.10.5:
**zip 1,35 ГБ, развёрнутая 2 063 МБ, 33 188 файлов**. Метаданные, с которыми
сервер работает сегодня, — единицы мегабайт, и весь приём построен под них.

Из чего состоит выгрузка (разведка, раздел 1):

| Тип | Файлов | МБ | Доля | Что это |
|---|---|---|---|---|
| `.cf` | 1 | 713 | 34,6% | конфигурация поставки |
| `.bin` | 501 | 665 | 32,3% | драйверы ККТ, весов, внешние компоненты |
| `.xml` | 21 606 | 378 | 18,3% | метаданные объектов и формы |
| `.bsl` | 7 878 | 260 | **12,6%** | **код** |
| прочее | 3 202 | 45 | 2,2% | справка HTML, картинки, тексты |

Три места, где нынешний приём об это ломается.

**Предел приёма.** `MAX_UPLOAD = 500 МБ` — файл на 1,35 ГБ откажется ещё в
браузере.

**Тройное копирование.** `await request.form()` вычитывает тело целиком в
буфер, код копирует его в `tempfile.mkdtemp()`, а `add_configuration` с
умолчанием `keep_source=True` кладёт **третий** экземпляр в
`data/sources/configurations/`:

| Копия | Объём | Где |
|---|---|---|
| буфер `form()` | 1,35 ГБ | `/tmp` внутри контейнера |
| копия в `mkdtemp()` | 1,35 ГБ | там же |
| `_store_source` | 1,35 ГБ | **на томе**, `data/sources/` |
| **итого** | **≈ 4,05 ГБ** | две копии в overlay, одна на томе |

Распаковки на диск сегодня не происходит: `add_configuration` читает zip
schema v1 напрямую. Она появилась бы, только если бы выгрузку в файлы пустили
этим же путём.

**1,35 ГБ по HTTP.** Десятки минут при риске обрыва на девяноста процентах, без
возможности продолжить с места разрыва.

## Что решено

| Развилка | Решение | Почему |
|---|---|---|
| как файл попадает на сервер | каталогом тома, не по HTTP | ноль копий, ноль обрывов, `MAX_UPLOAD` не участвует |
| что остаётся на диске | код без балласта | тело процедуры есть что отдать, переразбор без повторной передачи |
| что при нехватке **места на диске** | отказ до начала, с цифрами | сервер продолжает работать; полуразобранного источника не возникает |

Решения от 2026-08-19, владелец.

**Объём результата — замерено 2026-08-19: 351,4 МБ, 11 072 файла**, то есть
17,0% развёрнутого. Складывается из `.bsl` (260,3 МБ, 7 878 файлов) и `Form.xml`
(91,1 МБ, 3 194 файла). Воспроизводится:

```bash
python3 tools/lab/measure_intake.py <выгрузка.zip>
```

Расширение на этом фоне бесплатно: выгрузка расширения к ней — архив 1 МБ,
развёрнутая 8 МБ, отбираем 6,9 МБ из 155 файлов. Проверка места для расширений
формальность, но делается тем же кодом.

**`.cf` поставки не сохраняем — и это отмена, а не умолчание.** Разведка
называет его полезным материалом, который приходит бесплатно: «исходная типовая
до доработок, `v8container.py` такие контейнеры читать умеет, материал для
сравнения „типовая против доработанной“ просить отдельно не нужно». Мы его
отбрасываем: 713 МБ — вдвое больше, чем весь сохраняемый код, а задачи
«сравнить типовую с доработанной» в работе нет. Цена названа честно: после того
как человек уберёт zip из `incoming/`, взять `.cf` будет неоткуда. Сравнение
типовой с доработанной сейчас не реализуется. Вернуться к нему стоит только для
живой задачи, которой действительно потребуется такое сравнение.

## 1. Поток данных

Развёрнутых 2 ГБ не появляется никогда: zip читается членом за членом, на диск
ложится только отобранное.

```
./data/incoming/Розница_модули.zip           ← ZIP или уже распакованный каталог
./data/incoming/Розница/                     ← тот же отбор, без повторной распаковки ZIP
        │
        │  ZIP читается членом за членом; каталог копирует только отобранное;
        │  отбираются модули и формы, остальное пропускается
        ▼
data/modules/РозницаДляКазахстана/           ← только код, 351 МБ
```

Пик по диску — размер результата. Пик по памяти — один член zip за раз; для
плоской выгрузки (8.3.5) это контейнер `.Form` целиком, потому что код формы
лежит записью внутри него.

Исходный zip или каталог остаётся в `incoming/`: сервер его не копирует, не
перемещает и не удаляет. Источник модулей регистрируется **с `keep_source=False`**
— иначе `_store_source` положит второй экземпляр в `data/sources/`.

Идентичность каталога — sha256 `ConfigDumpInfo.xml`, а если его нет —
`Configuration.xml`. Файл `VERSION` выгрузки gitSync, когда лежит рядом,
входит в тот же отпечаток. Список на дашборде эти же файлы не обходит глубже
верхнего уровня (или единственной обёртки): дерево модулей не хешируется и
не суммируется. ZIP по-прежнему хешируется целиком.

**Как отличить конфигурацию от расширения** — проверено на живых файлах
2026-08-19, и здесь разведку надо поправить. Её таблица называет `NamePrefix`
признаком расширения, но тег есть **у обоих**:

```
конфигурация:  <NamePrefix/>                 ← пустой
расширение:    <NamePrefix>ПРЕФИКС_</NamePrefix>
```

Различает не наличие тега, а непустое значение. Проверка по наличию
классифицировала бы конфигурацию как расширение.

Надёжные признаки, проверенные на паре «типовая конфигурация розничных
продаж 2.3.10.5 + расширение к ней»:

| Тег | Конфигурация | Расширение |
|---|---|---|
| `ObjectBelonging` | нет | **есть** |
| `ConfigurationExtensionPurpose` | нет | **есть** |
| `CompatibilityMode` | **есть** (`Version8_3_21`) | нет |
| `NamePrefix` | есть, **пустой** | есть, со значением |
| `ConfigurationExtensionCompatibilityMode` | есть | есть |

Последние два — ложные признаки: по наличию не различают. Разведка знала про
один из них, про `NamePrefix` — нет.

Таблица описывает корневой объект `Configuration`, по которому классифицируется
архив, а не каждый узел метаданных внутри расширения. Read-only проверка
2026-08-28 на обезличенном корпусе из трёх расширений показала обратную для
вложенных собственных добавлений картину: шесть реквизитов заимствованного
справочника не имеют тега `ObjectBelonging` вовсе. Все заимствованные узлы
помечены `Adopted`, но их UUID отличаются от UUID соответствующих узлов базы;
сопоставлять нужно по виду, имени и иерархическому пути. Поэтому правило
классификации архива нельзя использовать как готовое правило принадлежности
внутреннего объекта.

**Что считается модулем и формой** — по форматам, они разные (разведка,
раздел 6):

| | иерархическая (8.3.23) | плоская (8.3.5) |
|---|---|---|
| модули | `*.bsl`, запись `module` в `Form.bin` | `*.txt`, запись `module` в `*.Form`, два канонических вида скомпилированных `.Module` |
| формы | XML-дескриптор, `Form.xml`, `Form.bin` | `*.Form` и отдельный `*.Form.Module.txt` |

В плоской выгрузке `.txt` носят не только модули. **Маска уточнена при
реализации: берём обычные `.txt`, все `.Form` и канонические
`CommonModules/<Имя>.Module` и `CommonModule.<Имя>.Module`;
`*.Template.txt` исключаем.** Отделить прочий
текст от модуля по произвольному имени нельзя, но имя `Template` платформа
резервирует для текстового макета. Лишний `.txt` стоит байты, тогда как
пропущенный модуль стоил бы дыру в индексе. Скомпилированный `.Module`
сохраняется как факт существования общего модуля: исходного текста внутри нет.
Определение формата выполняется только после нормализации и проверки
безопасности имён: путь наружу, служебный каталог Finder и ресурсная вилка не
могут переключить формат или выдать небезопасный манифест за schema v1.
Обёртка, `Configuration.xml`, манифест, формат, предпроверка, план и распаковка
читают одну карту нормализованных целей; если два сырых имени сводятся к одной
цели, во всех этапах побеждает последняя запись центрального каталога ZIP.
После снятия обёртки скомпилированный модуль распознаётся только по двум
каноническим положениям; похожий `*.Module` внутри постороннего каталога не
меняет формат всей выгрузки.
Контейнер `.Form` сохраняется **целиком**,
вместе с двоичной записью формы: код обычной формы лежит внутри него записью
`module`, и вынимать его на приёме означало бы тащить сюда разбор контейнера
1С (`v8container`). Правило записано в `intake.is_wanted`, его версия — в
`intake.SELECTION_VERSION` (текущая версия 5). Иерархический XML-дескриптор и
`Ext/Form.bin` также сохраняются целиком; производный `.bsl` не создаётся.
Версия 5 добавляет не исходные XML объектов, а производный gzip-каталог
происхождения структуры. Он строится во время того же приёма и публикуется
тем же атомарным swap; старый корень selection v4 восстановить его без ZIP не
может и поэтому показывается как требующий переразбора.

**Каталог `incoming/` — новый, и `bootstrap/` его не заменяет.** Сегодня
`data/bootstrap/` разбирается при каждом старте целиком; гигабайтную выгрузку
так разбирать нельзя. Обратный случай тоже надо закрыть: человеку сегодня
задокументирован ровно один каталог тома — `bootstrap/`, прямо в
`docker-compose.yml`. Положенная туда выгрузка в файлы будет хешироваться
целиком при каждом старте, уходить в `add_configuration` как schema v1, падать
— и повторяться вечно, потому что упавший файл в реестр не попадает, а `known`
считается один раз до цикла. `bootstrap()` обязан узнавать выгрузку в файлы и
говорить «этот файл кладут в `incoming/`» вместо ошибки разбора. Комментарий в
`docker-compose.yml` правится тем же коммитом: каталогов приёма станет два.

## 2. Состояния: что видит человек

Страница «Источники» показывает файлы из `incoming/` **своим блоком**, со своим
текстом и своим удалением. В раздел «Исходные файлы» они не подмешиваются:
`orphan_sources()` обходит только `data/sources`, а его заголовок — «для
ответов эти файлы не нужны» — для неразобранной выгрузки прямая ложь.

| Состояние | Как определяется | Действие |
|---|---|---|
| разобрано | источник с этим `sha256` есть в реестре | `переразобрать` |
| разбирается | задание по этому файлу выполняется | кнопки нет |
| не разобрано | хеша нет, неудачи не записано | `разобрать` |
| разбор не удался | записана последняя неудача: причина и дата | `разобрать` |
| обновлённая выгрузка | имя то же, `sha256` другой | `переразобрать` |
| отбор устарел | версия правила отбора в индексе ниже нынешней | `переразобрать` |

**Страница запускает не более одного разбора вообще; реестр сериализует каждый
источник отдельно.** Новая заявка резервирует поколение до долгих операций, а
устаревшая очередь не доходит до проверки места. Авторитетная проверка стоит в
реестре после выбора конфигурации и вида источника, поэтому прямой вызов не
обходит её.

**Неудача хранится не в `_JOBS`.** `_JOBS` — обычный список в памяти процесса,
он теряется при рестарте и вытесняется после десяти завершённых заданий
(`JOBS_KEPT = 10`). Битый zip, чужая конфигурация, расширение вместо
конфигурации — через рестарт все эти отказы стали бы неотличимы от «ещё не
разбирали». Причина последней неудачи ложится туда же, где живёт кэш хеша.

**Файл, который ещё копируется, разбирать нельзя.** `cp` полутора гигабайт идёт
минуты, и файл виден с первой секунды. Для ZIP признак готовности — `mtime`
архива; для каталога — `mtime` файлов идентичности (`ConfigDumpInfo.xml` или
`Configuration.xml` и `VERSION`). Отказ здесь громкий и без того — центральный
каталог zip лежит в конце файла, и `zipfile` на недокопированном отдаёт
`BadZipFile`, — но без признака готовности этот отказ попадёт в «разбор не
удался» и потребует ручного повтора.

**Ключ источника — не имя конфигурации.** `Registry.sources` — словарь по `id`,
а `id` конфигурации это её имя (`registry.py:565`). Модули привязываются к
конфигурации по имени, то есть естественный `id` у них тот же — и присвоение
`self.sources[source.id] = source` молча вытеснило бы учётную запись метаданных,
после чего `save()` записал бы реестр уже без неё. Тем же ключом называется файл
кэша. Поэтому: `id = "<ИмяКонфигурации>:modules"`, для расширений
`"<ИмяКонфигурации>:ext:<ИмяРасширения>"`, а поиск источника при вычислении
состояний идёт **по паре `(kind, sha256)`**, не по одному хешу.

**Хеш кэшируется.** sha256 полутора гигабайт считается секунды, и считать его на
каждое открытие страницы нельзя. Ключ кэша — `(путь, размер, mtime)`; изменилось
любое из трёх — пересчёт. Это и кэш хеша, и место для записи последней неудачи —
единственное новое хранилище, которого в реестре сегодня нет.

### Почему «отбор устарел», а не «код изменился»

Первая редакция этой постановки вешала переразбор на `_code_digest()` — sha256
всех файлов пакета из штампа кэша индексов. Это неверно, и вот почему.

Отпечаток намеренно грубый. Его докстрока: «Берётся весь пакет, а не список
„важных“ модулей: такой список сгниёт… **Цена грубости — лишняя пересборка после
любой правки исходников, один раз, полторы секунды.**» Полторы секунды
автоматической пересборки — приемлемая цена. Ручной переразбор гигабайтной
выгрузки после правки любого из тридцати файлов пакета — нет.

Случаев на деле два, и они разной природы:

- **индекс устарел** — сервер чинит сам, пересобрав индекс из `data/modules/`;
  человеку показывать нечего;
- **отбор устарел** — изменилось правило, по которому мы вытаскиваем файлы из
  zip; только это требует переразбора архива.

Второй случай отмечается **отдельной версией правила отбора**, а не отпечатком
пакета. Ручная константа здесь допустима ровно потому, почему в `index_cache` от
неё отказались: там её забыли бы поднять и кэш молча разошёлся бы с кодом, а
здесь забытая константа означает лишь, что переразбор не предложат — заметно и
чинится вручную, в отличие от молчаливого расхождения.

Общее правило разработки «правил разбор → перезагрузи источник» сюда не
переносится: оно существует потому, что у справки исходника не остаётся. Здесь код лежит в
`data/modules/` — за это и заплачено местом.

## 3. Проверка до начала

Сколько места потребуется, известно **до чтения тела**: центральный каталог zip
хранит несжатый размер каждого члена (`ZipInfo.file_size`). Отбираем нужные,
суммируем — цифра за миллисекунды, без распаковки.

Соврать в опасную сторону это не может: `zipfile` обрезает вывод по объявленному
размеру, а несовпадение ловит CRC. Заявленный объём и есть тот, что будет
записан.

Оговорка по форматам снята при реализации: цифра точная для обоих. Она
опиралась на то, что двоичную запись `form` внутри контейнера `.Form` мы не
сохраняем, — но контейнер сохраняется целиком (см. «Что считается модулем и
формой» выше), то есть взвешенное и записанное совпадают.

К сумме отобранного прибавляется запас под индекс: он пишется **после** отбора и
в неё не входит (по разведке — 18,1 МБ сигнатур и 5,8 МБ форм на корпусе
Розницы).

Не хватает — задание сразу в «разбор не удался» с текстом вида «нужно 376 МБ,
свободно 90 МБ». Сервер продолжает работать: ни один загруженный источник не
затронут.

**Чего эта проверка не покрывает:** память (лимит отложен, см. §5), время
разбора, число inode (в выгрузке 7 878 `.bsl` и 3 194 формы — проверка считает
байты, а не файлы), и место, занятое параллельным заданием — последнее снимается
правилом «не более одного разбора одновременно».

### Права и безопасность

**«Разобрать» и «переразобрать» — запись, наравне с загрузкой и удалением.**
Требуют `ADMIN_TOKEN`, при незаданном токене маршрут отвечает 404, как остальные
ручки записи. Иначе `incoming/` станет обходом состояния «загрузка выключена».
Список файлов `incoming/` виден на тех же правах, что журнал заданий: имя файла
говорит, что за база.

**Имена членов архива санируются.** `ZipFile.open` с собственной записью пути не
чистит, в отличие от `extract`. Член с абсолютным путём, с `..` или с признаком
симлинка отвергается; целевой путь после `resolve()` обязан лежать внутри
`data/modules/<Имя>/`.

**Права на файл.** Сервер работает от uid 10001 (`Dockerfile`), а `chown` из
образа на bind-mount не действует. Файл, положенный под чужим uid с правами
`0600`, сервер не прочитает — это должно быть в тексте ошибки, а не оставаться
догадкой.

## 4. Что правится в существующем коде

Механизм заданий, страница и показ ошибки переиспользуются. Но «новым кодом
является только проверка» — неверно, и вот полный список правок:

| Где | Что | Почему |
|---|---|---|
| `dashboard.py` `_run_job` | удаление каталога перестаёт быть безусловным | сейчас `finally: shutil.rmtree(directory)`; на `incoming/` это стёрло бы каталог с исходником и соседями |
| `dashboard.py` `_index_source` | различение вида выгрузки | сейчас `.hbk` → `add_syntax`, всё прочее → `add_configuration`; выгрузка в файлы — тоже `.zip` |
| `dashboard.py` | вторая точка входа для задания | сегодня задание заводится только внутри `upload`, из тела HTTP-запроса |
| `registry.py` `restore()` | ветка нового вида источника | сейчас два ветвления: конфигурация / всё остальное → `add_syntax` |
| `registry.py` `CACHE_KINDS` | запись нового вида | иначе `index_cache.sweep` снесёт кэш на первом же старте — предупреждение об этом висит прямо над словарём |
| `registry.py` `orphan_sources` / `forget` | свой список путей для `incoming/` | сейчас обходит только `sources_dir`, и кнопка «удалить файл» на `incoming/` не действует |
| `registry.py` `bootstrap()` | узнавание выгрузки в файлы | иначе вечная ошибка на каждом старте |
| `.gitignore` | `**/modules/`, `**/incoming/` | второй слой правил — «где бы каталог данных ни лежал и как бы ни назывался»; содержимое чувствительнее разобранной справки: это исходный код внедрения |
| `README.md` | новый источник данных и способ его подать | публичное поведение документируется тем же изменением |

**Каталог `incoming/` серверу удалять запрещено.** Это должно быть выражено в
коде, а не в договорённости.

## 5. Чего эта постановка не решает

**`mem_limit` в `docker-compose.yml` не назначается.** Разведка перечисляет это
первым пунктом в «чего не измерено»: числа складывались по отдельным замерам,
пики частично накладываются. Лимит по такой сумме — то же самое, что цифра без
прогона.

Отдельно: `restart: unless-stopped` уже стоит. Лимит, поставленный наугад, даёт
не отказ, а цикл — OOM убивает контейнер, `restart` поднимает, тот снова грузит
те же источники и снова упирается. Поэтому строка «отказ до начала» в таблице
решений сужена до **места на диске**: по памяти без лимита гарантии нет, и
делать вид, что она есть, нельзя.

**Что для этого нужно:** снять пик памяти одним прогоном на контейнере с
модулями одной конфигурации. Это закрывает первый пункт «чего не измерено».

Известное на сегодня, для ориентира, — **не основание для лимита**:

| Что | Память |
|---|---|
| пять конфигураций и три справки сейчас | 628 МБ |
| поиск по всем процедурам (136 909) | 473 МБ |
| поиск только по экспортным (49 068) | 156 МБ |
| сигнатуры на диске / в памяти | 18,1 МБ / 65 МБ |

Отбор экспортных — рабочий рычаг, минус 67% памяти поиска; решено 2026-08-18.
Неэкспортную процедуру из чужого модуля всё равно не вызвать.

## 6. Границы

Здесь решается приём и хранение. **Решено раньше и не пересматривается:**

- модель загрузки (конфигурация → модули → расширения, каждый уровень
  необязателен) — разведка, раздел 5;
- определение «конфигурация или расширение» по `Configuration.xml` — там же;
- привязка к конфигурации по имени и версии — там же;
- отбор экспортных и включение провайдера на конфигурацию, а не на сервер —
  решения 2026-08-18;
- два формата выгрузки — разведка, раздел 6.

**Уточнение 2026-08-19.** «Привязка к конфигурации
по имени и версии» в списке выше — про то, что провайдер `modules` должен
делать это сам, сверяя манифест выгрузки с загруженными конфигурациями. Пока
он этого не делает, а владелец с четырьмя загруженными конфигурациями упёрся
в отказ вживую: привязку решили снять самым дешёвым способом — явным выбором
человека. На странице «Источники», рядом с кнопкой «разобрать», при
нескольких загруженных конфигурациях появляется выбор; при одной он не нужен.
Автоматическая привязка по манифесту остаётся провайдеру `modules` и этим
решением не отменяется.

**Приём по HTTP остаётся как есть** для того, подо что он и делался: справка
платформы и выгрузки метаданных — десятки и сотни мегабайт.
`MAX_UPLOAD`, полоса передачи и журнал заданий продолжают работать без
изменений. Каталог `incoming/` — второй путь, а не замена первому.
