# BSL change review и ручная реализация

Версия skill: `0.3.0-candidate`

Совместимость: `mcp-1c 3.3.0+`; нужен доступ к коду процедур. Проверка API
платформы требует синтаксической справки `mcp-1c`.

Статус: экспериментальный candidate. Наличие каталога не означает, что skill
принят: пользу подтверждает отдельное слепое baseline/candidate-сравнение.

## Результат и границы

Подготовь один из двух результатов по точному текущему коду:

- `review` — визуальное ревью с unified diff;
- `manual-implementation` — инструкция ручного внесения с копируемыми блоками.

В обоих режимах укажи точный адрес изменения, источник текущего кода, причины,
риски, выполненные и невыполненные проверки. Отделяй доказанные факты от
предположений и ничего не применяй без отдельного разрешения пользователя.

Skill подходит для процедуры, функции, формы, реквизитов или небольшого
связанного набора объектов. Он работает с локальными исходниками и только с
read-only MCP. Он не предназначен для автоматического изменения конфигурации,
полного архитектурного проектирования, публикации кода конкретного внедрения
или передачи полного локального файла удалённому MCP ради построения diff.

## Выбор режима и обязательное чтение

У skill ровно 2 режима. Выбери режим до чтения подробной инструкции.

### `review`

Выбирай для просьб показать изменения, разницу или diff, сравнить «сейчас и
будет», оценить изменение или провести ревью.

Русские алиасы: «покажи изменения», «сделай ревью», «покажи разницу», «покажи
дифф», «сравни текущий и новый код».

После выбора обязательно прочитай
[`references/review.md`](references/review.md). Не читай инструкцию второго
режима, если она не нужна для отдельного результата пользователя.

### `manual-implementation`

Выбирай для пошаговой инструкции, готового кода для копирования, пакета ручного
переноса в Конфигуратор или бинарной формы/модуля, недоступных локальному patch.

Русские алиасы: «подготовь инструкцию», «сделай инструкцию для ручного
внесения», «подготовь код для копирования», «покажи, что найти и на что
заменить», «подготовь пакет ручной реализации», «подготовь изменения для
Конфигуратора», «форма бинарная, подготовь ручное изменение».

После выбора обязательно прочитай
[`references/manual-implementation.md`](references/manual-implementation.md).
Не читай инструкцию второго режима, если она не нужна для отдельного результата
пользователя.

Если пользователь явно назвал режим, не меняй его. Если запрос однозначен,
назови выбранный режим в начале ответа. Если допустимы оба результата и цель
неясна, задай один короткий вопрос до чтения reference-файлов.

«Скилл проверки изменений BSL» и «проверка изменений BSL» — русские названия
этого skill. Технический ID остаётся `bsl-change-review`; harness с точным
вызовом использует `$bsl-change-review`, а режим можно назвать по-русски.

## Вход

Нужны задача пользователя, текущий код или возможность получить его из файла
либо `mcp-1c`, целевая версия платформы при наличии и выбранный режим. Если
место изменения неизвестно, найди его сам. Не спрашивай сведения, доступные
через MCP или локальные файлы.

## Обязательные границы

- MCP и чтение файлов не разрешают менять конфигурацию, Registry, `data/`,
  контейнер, информационную базу или внешний сервис.
- Применение, компиляция, запуск 1С, FTP/HTTP-вызов и фоновое задание —
  отдельные действия с отдельным разрешением.
- Не показывай секреты и не помещай код конкретного внедрения в публичный
  репозиторий.
- Не отправляй локальный файл удалённому MCP, если его можно прочитать локально.

## Состояния доказательств

Используй только:

- `confirmed` — подтверждено указанным источником или проверкой;
- `not_checked` — проверка возможна, но не выполнялась;
- `unknown` — достоверного значения нет;
- `blocked` — начатая проверка не завершена; укажи причину;
- `not_applicable` — проверка не относится к предложению; объясни почему.

Не заменяй `unknown` предположением, а `not_checked` словом «готово».

## Общий порядок работы

### 1. Получи точный текущий код

Через доступный `mcp-1c` самостоятельно найди конфигурацию, целевую процедуру,
достаточный контекст и подтверждённых вызывающих, когда точка вызова влияет на
решение. Ориентируйся на фактический `tools/list`: названия вроде
`list_configurations`, `search_procedures`, `get_procedure` и `get_callers` не
считай безусловно доступными.

Локальный файл является источником текущего текста; MCP можно использовать для
поиска связей и справки. Не восстанавливай текущий код по памяти или пересказу.
Если точный текст получить нельзя, остановись со статусом `blocked`.

### 2. Зафиксируй источник

До проектирования запиши:

- конфигурацию и расширение либо `unknown`;
- полный адрес объекта, модуля и процедуры;
- источник: локальный файл или MCP;
- платформу либо `unknown`;
- хеш файла, digest ответа или хеш точного текста;
- время чтения, если оно доступно.

Не выдумывай строки и слой. Вычисленные вручную номера так и обозначай.
Отсутствие имени расширения не доказывает основную конфигурацию.

### 3. Подготовь минимальное предложение

Меняй только требуемое задачей. Не скрывай незавершённые части и не называй
частичное предложение полной реализацией. Формат, обязательные блоки и
специфические проверки бери только из reference-файла выбранного режима.

### 4. Проверь BSL API

Для добавленного или существенно изменённого API платформы, а также метода,
чей возврат или ошибка влияет на новую логику, прочитай точную карточку
синтаксической справки и сверь сигнатуру, контекст и версию появления.

Для `Переменная.Метод()` сначала докажи тип переменной по созданию,
присваиванию или возвращающей функции, затем проверяй `<Тип>.<Метод>`. Не
присваивай результат метода без подтверждённого возвращаемого значения и не
вставляй некомпилируемые placeholder. При недостающем контракте ставь
`unknown`, `not_checked` или `blocked`, а не выдумывай код.

### 5. Повторно прочитай исходник

Перед выдачей снова прочитай процедуру или файл и сравни идентификатор снимка:

- совпал — `Актуальность исходника: confirmed`;
- изменился — `blocked`, предложение устарело;
- перечитать нельзя — `not_checked`.

### 6. Верни или сохрани результат

По умолчанию верни полный результат в чате и не создавай файлов или каталогов.
Записывай только по явно указанному пути файла или каталогу результатов.

- Явный путь файла используй как есть.
- Для явного каталога `review` создаёт `change-review.md`, а
  `manual-implementation` — `IMPLEMENTATION.md`.
- Родительские каталоги создавай только внутри явно указанного пути.
- Если запись невозможна, верни Markdown в чате и сообщи об этом.

Никогда самостоятельно не сохраняй в корень проекта, текущий каталог,
`_scratch/`, `data/` или каталог skill. Каталог skill содержит инструкции, а не
результаты выполнения.

### 7. Самоаудит

Перечитай исходник и результат как независимый ревьюер. Проследи порядок строк
от создания значения до проверки и вызова. Не приписывай проверке защиту от
предыдущего вызова. Устрани противоречия источников, строк, слоёв и состояний.
Компиляцию и runtime не называй выполненными без фактического запуска.

## Установка и переносимость

Устанавливается весь каталог `bsl-change-review`, включая `references/`.
Клиент с поддержкой skills подключает каталог обычным способом. Клиент без
поддержки сначала получает `SKILL.md`, а затем только указанный в нём
reference-файл выбранного режима. Обновление заменяет весь каталог; удаление
удаляет его целиком. Конкретный путь зависит от harness.

## Проверка полезности candidate

Сравни 2 чистых прогона одной задачи: baseline с обычным MCP без skill и
candidate с тем же MCP и всем каталогом skill. Не подсказывай инструменты,
порядок, ключи или ожидаемый ответ. Сравни итоговый артефакт, фактические
ошибки, повторные попытки, самостоятельность, MCP-вызовы и расход контекста.
Отдельно фиксируй ошибки стенда; отсутствие авторизации или MCP не доказывает
качество skill.
