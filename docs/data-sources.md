# Источники данных: что откуда берём

Правило проекта. Определяет, какой источник отвечает за какой кусок знания о
конфигурации, и почему граница проходит именно так. Нарушать — только с правкой
этого документа. Пользовательский порядок передачи, preview, публикации и
миграции описан отдельно в
[инструкции загрузки](configuration-loading.md).

## Четыре источника Registry и явное отсутствие данных ИБ

| Источник | Что даёт | Как получаем |
|---|---|---|
| **A. Обработка выгрузки** (`exporter-1c/`) | runtime-структура метаданных, точная версия работающей платформы и признаки полноты | запуск в информационной базе |
| **B. Выгрузка конфигурации или расширения в файлы** | файловая базовая проекция, расширенная структура, тексты модулей и доступная структура `Form.xml`; descriptor и объявленные права ролей; собственные объекты и borrowed overlays расширений | конфигуратор / EDT |
| **C. Снимок расширений** (`СнимокРасширений_*.json`) | зарегистрированные, действующие и не применённые расширения конкретного сеанса | отдельная обработка на платформе 8.3.8+ |
| **D. Ничего** | данные информационной базы | не собираем принципиально |

## Разделение по элементам

| Элемент | Источник | Примечание |
|---|---|---|
| Состав объектов, реквизиты, табличные части | **A или B** | A авторитетна при наличии; B строит самостоятельную проекцию |
| Полные имена типов, квалификаторы | **A или B** | основа графа связей |
| Движения документов, основания ввода, владельцы | **A или B** | рёбра графа |
| Значения перечислений | **A или B** | A работает на всех поддержанных платформах; B читает файловые descriptor |
| Свойства объектов (иерархичность, периодичность, проведение) | **A или B** | B использует закрытый список доказанных свойств и fail closed для неизвестного обязательного descriptor |
| Стандартные реквизиты документов, справочников и журналов | **вычисляются из A или B** | единая runtime-проекция; не отдельный источник и не данные экземпляров |
| Подписки на события, регламентные задания | **A или B** | `handler`/`method` дают рёбра к общему модулю; B дополнительно проверяет привязку по разобранному BSL |
| **Предопределённые элементы** | **A** | проверено на 8.3.5 и 8.3.23 |
| Тексты модулей, сигнатуры процедур | **B** | из встроенного языка недоступны в принципе |
| Структура, элементы и события форм из `Form.xml` | **B** | доступны, когда формат выгрузки содержит `Form.xml` |
| Descriptor ролей, явные права, RLS и шаблоны ограничений | **B** | состав ролей конфигурации; не пользователи, назначения или эффективный доступ |
| Хранилища настроек | — | текущий source B намеренно отбрасывает весь вид до coverage |
| Собственные объекты и заимствованные объекты/поля расширения | **B** | отдельный generation расширения с обязательным родителем и сохранёнными semantic edges |
| Фактическая активность расширений в текущем сеансе | **C** | `СеансАктивные` / `СеансОтключенные`; без снимка — `unknown` |
| Порядок элементов, возвращённый API расширений | **C** | сохраняется дословно, но не выдаётся за порядок исполнения модулей |
| Команды, макеты и недостающие в schema v1 данные форм | — | общего источника и принятой задачи сейчас нет |
| Содержимое справочников и регистров | **D** | не собираем |

## Единая конфигурация A/B

Source A и Source B — два доказательства одного агрегата конфигурации. Они не
создают два пользовательских объекта и не требуют разных MCP-инструментов.
Только A даёт точную runtime-версию платформы; `CompatibilityMode` из B не
подменяет этот факт. Только B даёт код, формы, роли и типизированные сведения,
которых нет в schema v1.

При B-only базовая проекция B обслуживает поиск, карточки и граф. При A-only
работает прежняя schema-v1 структура. При A+B весь `base_structure` берётся из
A, а `extended_structure`, код, формы и роли — из B. Extended-only объекты и
overlays входят в один resolved-каталог вместе с базой; физические слои не
склеиваются и сохраняют собственные provenance и SHA. Поэтому обновление
одного источника остаётся атомарным и не создаёт смешанного частичного runtime.

Удаление A либо основного B не имеет отдельной семантики: пользователь удаляет
конфигурацию целиком вместе со всеми её слоями и дочерними расширениями.
Отдельное расширение удаляется независимо. Файлы `incoming/` обе операции не
трогают.

Источник C намеренно не добавлен в schema v1. Структура может быть актуальна
месяцами, тогда как состав расширений меняется между сеансами и областями
данных. JSON несёт собственные `snapshot_id`, UTC-время и identity
конфигурации; несовпадение помечается `stale`, отсутствие — `unknown`.
Три списка доступны с 8.3.8; отдельный признак изменения после старта сеанса —
только с 8.3.22, поэтому на 8.3.8–8.3.21 его значение равно `null`.

Extension-структура из источника B не входит в schema v1. Для каждого
расширения native generation отдельно хранит собственные объекты и overlay
заимствованных объектов вместе с жёсткими ссылками на базовые объекты и поля.
Первое поколение требует уже загруженного и явно выбранного родителя. При
полном обновлении базы её структура строго заменяется, а один transient
identity index перепроверяет сохранённые edges всех расширений без повторного
чтения их ZIP. Исчезнувшая цель получает `target_missing`: orphan-overlay не
участвует в resolved context, но собственные объекты, код, формы и роли
расширения сохраняются. Это состояние связи не доказывает активность
расширения в сеансе; её показывает только источник C.

Источник A строится из runtime-метаданных и уже может включать собственный
объект активного расширения без доказанного происхождения. При разрешении
выбранного native-расширения такая schema-v1 проекция заменяется объектом
source B только если совпали полный адрес и точный набор адресов всех его
полей. Иное множество полей считается несинхронной парой и даёт fail-closed
ошибку. Для базового слоя с provenance `source-b` совпавшее имя всегда
остаётся конфликтом. После повторной Source A её provenance `schema-v1`
сохраняется в manifest и после restart, поэтому для неё применяется та же
точная сверка `Fields`.

Source A остаётся быстрым schema-v1 профилем и сам по себе хранится как
совместимый `legacy`, пока конфигурация не получила native generation. Полная
source B заменяет его базовую структуру и публикует все слои одним manifest.
Частичный source-B `update` над таким legacy-состоянием недоступен: сохранить
структурные слои как независимые payload ещё не из чего, поэтому сначала нужен
явный полный `update_full`. После него content-only обновление сохраняет оба
структурных слоя native generation и заменяет только код, формы и роли.
Последующая source A уже не возвращает Registry в legacy: она атомарно
заменяет только `base_structure` нового поколения, сохраняя активные
`extended_structure`, код, формы и роли. Установка новой версии пакета и
обычный restart ничего не мигрируют и не создают manifest автоматически.
Если Source A помечена `truncated=true` или
`predefined_available=false`, наложение поверх native generation
отклоняется без смены active pointer: признаки теперь сохраняются в базовом
слое и переживают restart, но неполная A не может стать авторитетной базой при
сохранённых коде, формах и ролях полного B.

Стандартные реквизиты не сериализуются второй копией в `attributes`: платформа
создаёт их из вида и свойств объекта, поэтому Registry материализует их после
сведения слоёв. Для документа это `Ссылка`, условный `Номер`, `Дата`,
`Проведен` и `ПометкаУдаления`; для справочника — `Ссылка`, условные `Код` и
`Наименование`, зависящие от владельцев и иерархии `Владелец`, `Родитель` и
`ЭтоГруппа`, а также `ПометкаУдаления`, `Предопределенный` и
`ИмяПредопределенныхДанных`. Настройка проведения не удаляет поле `Проведен`.

Журнал использует свой фактический список `StandardAttributes`: английские
имена descriptor приводятся к русским query-именам, `Ссылка` получает состав
зарегистрированных документов, а `Номер` — объединение их эффективных типов и
квалификаторов. Нумератор Source B — скрытая зависимость базового слоя: его
descriptor уточняет свойства документов, но не становится самостоятельной
пользовательской карточкой. Отсутствующая обязательная зависимость отклоняет
новый слой; старый снимок без доказанных правил остаётся читаемым с неизвестным
типом номера. Эти поля описывают структуру кода и запросов, а не ссылки/UUID
конкретных записей информационной базы.

Воспроизводимый синтетический замер 2026-09-02:

```bash
.venv/bin/python tools/lab/measure_extension_recheck.py \
  --base-identities 57892 --edges-per-extension 458 \
  --extensions 0,1,3 --repeat 20
```

Для 0 / 1 / 3 расширений медиана равна 0,001 / 7,328 / 9,077 мс,
дополнительный peak RSS — 0 / 6,141 / 6,219 МиБ. Снимок содержит 57 892 base
identities и по 458 edges на расширение; второй постоянный граф или индекс не
строится.

Объявленные права ролей также принадлежат только источнику **B**. Первый общий
source-B проход сохраняет descriptor и, когда он существует, соответствующий
`Rights.xml` в неизменяемом слое native generation; schema v1 источника A
ролями не расширяется. Descriptor без `Rights.xml` представляет пустую роль:
её права равны нулю, а отсутствующие default-флаги остаются `null`. Обратный
вариант, `Rights.xml` без descriptor, считается ошибкой ролевого слоя. Из
сохранённого snapshot, а не из исходного ZIP, строится расходный файловый
`RoleAccessIndex`. Он дедуплицирует цели, виды прав и тексты условий и
проверяется до открытия; повреждённый кэш перестраивается из того же snapshot.
Каждый `restrictionByCondition` сохраняется одной записью, его прямые `field`
остаются упорядоченным массивом `fields`, а пустой `condition` не теряет
признак условного права; то же правило действует для пустого условия
`restrictionTemplate`. Пустой `Synonym/item/lang` хранится как пустой языковой
код, если `content` присутствует. Tree- и доказанная flat-раскладки приводятся
к одному каноническому role snapshot.

MCP `find_roles_for_access`/`get_role_access`, read-only API
`GET /api/v1/roles*` и SPA `/roles` используют один backend-resolver и одну
generation. Они различают explicit false, безусловный true и условный RLS,
возвращают SHA источника и выдают роли, права, шаблоны и тексты условий только
ограниченными страницами. Ссылка ограничения несёт `fields`, но полный текст
RLS читается лишь по явной ссылке.
Слой не содержит пользователей, назначений ролей и эффективного доступа;
операций изменения или назначения ролей нет. `roles=missing|error` не мешает
структуре, коду и формам, а без хотя бы одного `roles=ready` две MCP-схемы не
регистрируются.

Общая `schema_version 2` не запланирована. Доступная структура `Form.xml` и
модули форм уже приходят из источника **B**. Для команд, макетов или
недостающей разновидности формы сначала нужна конкретная живая задача и замер,
а затем отдельное решение об источнике и формате; номер версии заранее это
решение не заменяет.

## Отдельный артефакт общей справки

Каноническая SQLite schema v1 стоит вне источников A–D и вне Registry. Это
готовый подписанный read-only артефакт общего знания, а не выгрузка конкретной
информационной базы. Репозиторий публикует адаптер и контракт двух MCP-
операций, но не саму базу, исходные материалы или способ её сборки.

SQLite доставляется только внутри строгого `.mcp1cref` с каноническим
`manifest.json` и detached-подписью Ed25519 `manifest.sig`. Файл можно
установить в управляемый `data/reference/reference.mcp1cref` через дашборд либо
указать внешним `MCP1C_REFERENCE_ARTIFACT`. Отсутствие, несовместимость,
повреждение или недоверенная подпись отключают только `search_reference` и
`get_reference`; источники A–C и одиннадцать основных операций продолжают
работать. Производный индекс живёт отдельно в `data/index/reference/`,
восстанавливается между стартами и перестраивается при изменении файла, кода
или формата кэша.

Режима без подписи в runtime нет. Проверка происхождения и целостности не
заменяет конфиденциальность: `.mcp1cref` не шифрует SQLite, поэтому доступ к
файлу и каталогу `data/` ограничивает оператор.

## Сгенерированные слои поверх источников

Всё выше — про знание, добытое из базы или из справки. Отдельно стоит текст,
который **сочинён нами**: он не источник знания и не имеет права им казаться.

**Правило: сгенерированное не смешивается с выгруженным.** Три требования,
все три обязательны.

1. **Живёт отдельным слоем в git**, а не приписывается к разобранному
   элементу. Разобранная страница справки и наш текст лежат в разных местах и
   различимы по происхождению — как встроенный словарь отличается от
   локального.
2. **В ответ агенту не попадает.** Ответ по-прежнему собирается только из
   справки. Сгенерированное работает исключительно на попадание в нужную
   статью, а не на её содержание. Иначе агент получит наш пересказ вместо
   документации фирмы «1С» и не сможет их различить.
3. **Отсутствие источника не молчит.** Слой привязан к элементам по
   идентификатору. Элемента нет — привязка не состоялась, и это должно быть
   видно при загрузке, а не проявляться просевшим поиском.

Требование 3 — из того же класса дефектов, что уже ловили дважды: пустое имя
платформы в `list_configurations` и скрытое по версии, выданное за
ненайденное. Молчащая деградация дороже громкого отказа.

| Слой | Что там | Где | Ответ агенту |
|---|---|---|---|
| Поисковые ключи справки | формулировки, которыми спрашивают статью или платформенный метод | `search_keys.py`, git | нет, только поиск |
| Встроенный словарь | синонимы и псевдонимы объектов | `synonyms.py`, git | нет, только поиск |
| Локальный словарь | терминология конкретного внедрения | `data/dictionary.json` | нет, только поиск |
| Оговорки в карточке | предупреждение о ловушке платформы | `render.py`, git | **да**, см. ниже |

### Оговорки в карточке — единственный слой, доходящий до агента

Требование 2 выше писалось для слоёв, работающих на поиск, и для них остаётся
безусловным. Оговорка — другой случай: она нужна ровно в ответе и ровно в тот
момент, когда агент читает поля и пишет по ним запрос. Пересказывать ею справку
по-прежнему нельзя; она говорит только то, чего в справке нет, а без чего
выданные нами верные данные приводят к неработающему коду.

Отсюда два требования сверх общих трёх:

4. **Происхождение видно в самом тексте, а не в комментарии к коду.** Цитата
   из справки называется цитатой («справка прямо запрещает»), наш вывод —
   советом («считайте небезопасным»). Агент поведёт себя одинаково, а читатель
   через полгода отличит проверяемое от нашего.
5. **Непроверенное не выдаётся за проверенное.** Что не подтверждено ни
   справкой, ни живым прогоном, формулируется как осторожность, а не как факт
   о платформе.

**Строки неограниченной длины** — первая такая оговорка, заведена 2026-08-18 по
живому промаху и в тот же день доведена до конца: всё, что стояло советом,
проверено владельцем на живой базе и стало фактом. Разбивка по происхождению:

| Утверждение | Откуда | Что сказала платформа |
|---|---|---|
| нельзя в `КОЛИЧЕСТВО`, `МИНИМУМ`, `МАКСИМУМ` | архивные карточки справки 1С `COUNT`, `MIN`, `MAX` | «Не может применяться к … Строкам неограниченной длины» |
| нельзя сравнивать | прогон 2026-08-18, соединение по `КодСкидки` | «неверные параметры в операции сравнения. Нельзя сравнивать поля неограниченной длины и поля несовместимых типов» |
| нельзя группировать | прогон 2026-08-18 | запрос не выполняется |
| нельзя упорядочивать | прогон 2026-08-18 | «недопустимое поле для упорядочивания КодСкидки» |
| нельзя в `РАЗЛИЧНЫЕ` и `ОБЪЕДИНИТЬ` | прогон 2026-08-18 | «в запросе с предложениями РАЗЛИЧНЫЕ или ОБЪЕДИНИТЬ нельзя использовать поля неограниченной длины» |
| рецепт `ПОДСТРОКА(поле, 1, N)` | прогон владельца, работает | — |
| выборка поля без конструкций выше | прогон 2026-08-18, контрольный запрос | работает |

Три вывода из текстов ошибок, которых не было в первой редакции оговорки:

1. **`ОБЪЕДИНИТЬ` тоже под запретом** — платформа называет его в одном ряду с
   `РАЗЛИЧНЫЕ`. В первой редакции его не было вовсе.
2. **Запрет на сравнение шире условия соединения.** Платформа говорит «нельзя
   сравнивать поля неограниченной длины», не «нельзя соединять», — значит под
   него попадают и равенство в `ГДЕ`, и `В (…)`.
3. **Упорядочивание — отдельное ограничение, не следствие сравнения**: у него
   свой текст ошибки («недопустимое поле для упорядочивания»).

Проверено отдельно: страницы `GROUPStatement`, `ORDERBYSection`,
`KeyWordsDISTINCT`, `JOIN`, `UNIONSection`, `query_cast` про неограниченные
строки **молчат**. Справка знает об ограничении только в трёх агрегатных
функциях из шести; остальное знание — наше, и получено оно прогоном.

Второй рецепт, `ВЫРАЗИТЬ(поле КАК СТРОКА(N))`, в карточку не пошёл: справка
описывает `ВЫРАЗИТЬ` как средство для составного типа и ставит потолок
«максимальный размер строки составляет 1024», а на живой базе его никто не
проверял. `ПОДСТРОКА` проверена и потолка не имеет.

## Правило про предопределённые

**Источник — обработка (A), на всех проверенных платформах.** Если платформа
всё же не сможет — не пропускает молча, а помечает выгрузку.

Правильный способ установлен пробником
(`exporter-1c/probe/ПробникПредопределенных.bsl`) на платформе **8.3.23.1997**:

| Способ | Результат |
|---|---|
| `Менеджер.ПолучитьИменаПредопределенных()` | ✗ метод объекта не обнаружен |
| **`ОбъектМетаданных.ПолучитьИменаПредопределенных()`** | **✓ работает** |
| Запрос `ПредопределенноеИмяДанных` | ✗ поле не найдено |
| **Запрос `ИмяПредопределенныхДанных`** | **✓ работает** |
| Запрос `ГДЕ Предопределенный = ИСТИНА` | ✓ признак существует |
| `ОбъектМетаданных.ЭлементыПредопределенныхДанных` | ✗ свойства нет |

Метод висит на **объекте метаданных**, а не на менеджере. Поле запроса —
`ИмяПредопределенныхДанных`.

Ранняя гипотеза «до 8.3.6 предопределённые недоступны в принципе» была сделана
по одной платформе и **не подтвердилась**: на 8.3.23 отказ был тот же самый,
то есть причиной было обращение не к тому объекту, а не версия платформы.

После исправления предопределённые собираются **на обеих платформах**:

| Конфигурация | Платформа | `predefined_available` | Объектов | Имён |
|---|---|---|---|---|
| Отраслевая конфигурация | 8.3.5.1570 | `true` | 33 | 283 |
| Розница для Казахстана | 8.3.23.1997 | `true` | 40 | 1015 |

Предупреждений — ноль в обоих случаях. Источник **B** для предопределённых
не нужен; он остаётся только для текстов модулей.

Исторические цифры таблицы сняты 2026-08-27 командами на соответствующих
выгрузках; `info` подтверждает флаг, `stats` — состав объектов и число имён:

```bash
PYTHONPATH=src .venv/bin/python -m mcp1c.cli info /путь/к/выгрузке.zip
PYTHONPATH=src .venv/bin/python -m mcp1c.cli stats /путь/к/выгрузке.zip
```

Порядок попыток в выгрузке:

1. `ОбъектМетаданных.ПолучитьИменаПредопределенных()`
2. запрос `ВЫБРАТЬ ИмяПредопределенныхДанных … ГДЕ Предопределенный = ИСТИНА`
3. при отказе обоих — флаг, предупреждение, дальше не пытаемся

Обращение делается только к видам, у которых предопределённые вообще бывают:
справочники, планы видов характеристик, планы счетов, планы видов расчёта.
Иначе исключение на плане обмена или бизнес-процессе ложно пометило бы всю
платформу как неподдерживающую.

Загрузчик ориентируется на **атрибут манифеста**, а не на текст предупреждения:

```xml
<manifest ... predefined_available="false">
```

* `true` — предопределённые в выгрузке есть, источник **A** закрыл вопрос.
* `false` — секции `predefined` нет, конфигурация считается неполной,
  и это должно быть видно агенту.

### Почему это важно для генерации кода

Предопределённые адресуются в коде по имени:

```bsl
Если Номенклатура.ВидНоменклатуры = Справочники.ВидыНоменклатуры.Услуга Тогда
```

Без списка агент видит только тип реквизита и начинает угадывать имя —
`.Услуги`, `.Сервис`. Такой код компилируется и падает в рантайме.

загрузчик должен такие ссылки отбрасывать штатно, а не считать ошибкой.

## Возможные источники — обсуждалось, не решено

Пометка на будущее, чтобы граница источников продумывалась заранее, а не
задним числом. Перечисленные ниже направления в работу не взяты.

| Источник | Что дал бы | Как получаем |
|---|---|---|
| **D. Технологический журнал** | долгие запросы, планы СУБД | файлы `.log` с сервера 1С |
| **E. Схемы обмена** | EnterpriseData, правила КД2/КД3 | пакеты обмена и XML-схемы |

Обе — данные о **работе** системы, а не о её устройстве, и меняются они на
несколько порядков быстрее конфигурации. Смешивать их с A и B в одном
хранилище нельзя: у A и B горизонт «до следующей выгрузки», у D — минуты.

## Почему граница проходит здесь

Разделение не по типу данных, а по **скорости изменения** и по тому, что
источник физически способен отдать:

* Обработка ходит по `Метаданные` — видит структуру, но не видит исходный код:
  платформа не даёт доступа к текстам модулей из встроенного языка.
* Файловая выгрузка содержит всё, включая код и предопределённые, но метаданные
  в ней разложены по GUID-ссылкам между файлами — читать их дорого и муторно.
* Данные информационной базы меняются постоянно и к структуре конфигурации
  отношения не имеют.

Каждый источник отвечает за то, что отдаёт дёшево и точно.
