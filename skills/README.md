# Skills для агентов

Этот каталог предназначен для публичных инструкций, которые помогают агентам
решать повторяющиеся задачи разработки на 1С с использованием `mcp-1c` и
локальных инструментов. Само наличие идеи в этом файле не означает, что skill
принят, реализован или рекомендован к установке.

## Текущий статус

Принят [`bslfmt`](bslfmt/SKILL.md): в независимом сравнении он помог агенту
обнаружить локальный форматтер и применить результат. Экспериментальный
[`bsl-change-review`](bsl-change-review/SKILL.md) остаётся кандидатом и ждёт
отдельного слепого baseline/candidate-прогона. Новый кандидат
[`1c-form-creator`](1c-form-creator/SKILL.md) собирает управляемые формы
локально. Два чистых Luna-прогона подтвердили самостоятельное обнаружение
skill и сборку комплектов XLSX/CSV; владелец затем загрузил обе обработки,
открыл формы и добавил колонки. Два контрольных прогона через развёрнутый
MCP без skill не прошли итоговые проверки, но сервер работал на более старом
коде. После пересборки из того же кода ещё два агента без skill получили
структурный `passed` через MCP, но XLSX-комплект сохранили без BOM и не
импортировали в 1С во время прогона. После нормализации файлов владелец
загрузил конфигурацию, но обе формы не открылись. В двух парах
некэшированный вход у MCP выше;
устойчивая разница в стоимости и чтение файлов не проверены. Подробности —
в локальном `docs/form-creator-wip-mcp-eval-2026-09-29.md`.

Создание форм и метаданных перенесено из MCP в локальные skills.
`1c-form-creator` содержит собственный compiler/checker, а
[`1c-metadata-creator`](1c-metadata-creator/SKILL.md) создаёт descriptor
объекта с формой или без неё. Ранние слепые прогоны metadata skill выявили
разные недостатки: в одном после успешной статической проверки агент добавил
пустой `Module.bsl` вне канонического комплекта, в другом собрал список вместо
формы элемента. После уточнения инструкций чистый агент собрал форму элемента
справочника; `build` и оба
`validate` завершились `static_passed` без ошибок и повторов. Владелец сообщил,
что перенесённые справочник и обработка загрузились в тестовую 1С, конфигурация
обновилась и запустилась, а объекты отработали корректно; это
`passed_owner_reported`, а не наблюдение разработчика. BSL API, чтение файлов и
отдельная оценка визуального качества остаются `not_checked`. Оба skills
сохраняют статус кандидатов; результат ограниченной проверки не доказывает
универсальную поддержку типов объектов и форм.

Сейчас MCP-сервер:

- не публикует каталог skills;
- не добавляет инструкции из этого каталога в `initialize` или `tools/list`;
- не предоставляет `list/get`-инструменты, prompts или resources для skills;
- не устанавливает skills в клиентские агенты;
- не включает этот каталог в Docker-образ или Python-пакет.

Возможная доставка через MCP остаётся отдельной гипотезой. Она будет
обсуждаться только после того, как конкретный skill докажет пользу для агента.

## Как предполагается распространять принятый skill

Основной вариант — каталог в репозитории:

```text
skills/
  <skill-id>/
    SKILL.md
    references/     # при необходимости
    scripts/        # только для локального выполнения агентом
```

Пользователь скачивает выбранный каталог и подключает его средствами своего
агента. Поддержка формата, место установки и разрешения зависят от конкретного
агента; появившийся skill обязан описать проверенный способ подключения.

Файлы в `scripts/` не становятся операциями MCP-сервера. Локальное выполнение,
рабочий каталог, allowlist команд, таймауты, секреты и изменения файлов остаются
в зоне ответственности агента и пользователя.

## Как идея становится принятым skill

До создания каталога кандидата нужны пункты 1–3. Пункты 4–7 выполняются до
принятия skill; каталог кандидата допускается для независимого прогона:

1. Сформулировать реальную задачу и наблюдаемую проблему агента.
2. Проверить, не решается ли она яснее описанием существующего MCP-инструмента,
   обычной документацией или локальной командой.
3. Согласовать границу: что делает skill, что делает MCP, что остаётся локальной
   работой агента и что требует решения пользователя.
4. Провести слепое baseline/candidate-сравнение на одинаковой задаче. Baseline
   не получает skill; candidate получает только публичный skill и обычный MCP.
5. Сравнить итоговый артефакт, фактические ошибки, повторные попытки,
   самостоятельность, MCP-вызовы и расход контекста.
6. Зафиксировать `unknown`, `not_checked` и `blocked`; отсутствие доказательства
   не превращать в успешный результат.
7. Отдельно решить: отклонить идею, оставить skill только в репозитории или
   исследовать read-only доставку той же инструкции через MCP.

Один удачный или неудобный прогон сам по себе не является основанием для новой
MCP-ручки, Runner или расширения публичного контракта.

## Требования к принятому skill

В `SKILL.md` должны быть указаны:

- назначение и задачи, для которых skill применять не следует;
- требуемые MCP-capabilities, локальные инструменты и версии;
- входы, ожидаемый результат и критерии проверки;
- разрешённые изменения и обязательные owner-gates;
- состояния `unknown`, `not_checked` и `blocked`;
- правила работы с секретами, локальными файлами и внешними сервисами;
- способ установки, удаления и обновления;
- версия skill и совместимость с версиями `mcp-1c`;
- воспроизводимое свидетельство пользы.

Skill не должен скрыто расширять полномочия агента, выполнять произвольный код
в процессе MCP-сервера или превращать read-only доступ в разрешение менять
Registry, `data/`, конфигурации, контейнеры либо внешние системы.

## Возможная доставка через MCP

Если репозиторный skill докажет пользу, отдельно можно проверить read-only
доступ к той же канонической инструкции через MCP для клиентов без нативной
поддержки skills. Такой механизм не считается установкой skill и не даёт
агенту дополнительных локальных полномочий.

До реализации нужно доказать, что агент самостоятельно обнаруживает инструкцию
и решает задачу лучше, чем с обычными `initialize`, `tools/list` и
`tools/call`. Затем отдельно согласуются discoverability, токеновая стоимость,
версионирование, digest, совместимость клиентов и граница доверия.

## Публичность и лицензия

Каталог является частью публичного репозитория и распространяется на условиях
Apache-2.0. В него не попадают:

- `data/` и производные индексы;
- выгрузки и исходный код конкретных внедрений;
- реальные имена конфигураций, организаций и локальные пути;
- токены, пароли, адреса закрытых сервисов и другие секреты;
- материалы фирмы «1С», на распространение которых проект не имеет прав.

Каждое добавление или изменение skill одновременно обновляет этот файл и
основной [README](../README.md). Публичная функциональность MCP дополнительно
обновляет документацию инструментов и `CHANGELOG.md`.
