# Инструменты MCP

Сервер всегда предоставляет одиннадцать основных инструментов. Валидная и
доверенная каноническая SQLite общей справки добавляет ещё два. Ещё две
role-операции появляются, только когда хотя бы одна конфигурация имеет
`roles=ready`; без готового ролевого слоя они вообще не попадают в
`tools/list`. Схема каждого зарегистрированного инструмента остаётся в
контексте агента всю сессию, тогда как данные приходят только по вызову.

## Полный список

| Инструмент | Параметры | Результат |
|---|---|---|
| `list_configurations` | — | конфигурации, платформы, доступные провайдеры и предупреждения |
| `list_extensions` | `config` | действующие и не применённые расширения по снимку конкретного сеанса |
| `search_objects` | `query`, `config`, `kind`, `limit` | точные имена объектов по человеческой формулировке |
| `search_procedures` | `query`, `config`, `extension`, `scope`, `limit` | процедуры основной конфигурации или одного расширения |
| `get_procedure` | `address`, `config`, `extension`, `start_line`, `lines` | оглавление модуля либо ограниченное тело точной процедуры |
| `get_callers` | `address`, `config`, `extension`, `limit` | подтверждённые места вызова, подписки, задания и события форм |
| `get_object` | `full_name`, `config`, `detail` | структура объекта, доказанное происхождение, таблицы запроса и кодовые сведения |
| `get_related` | `full_name`, `config` | один шаг входящих и исходящих связей |
| `compare_configurations` | `full_name`, `configs` | различия объекта между конфигурациями |
| `search_syntax` | `query`, `config`, `kind`, `limit` | синтаксис и таблицы запросов платформы |
| `get_syntax` | `name`, `config`, `detail` | сигнатура, доступность, версия появления, пример и замена |
| `search_reference` | `query`, `domain`, `kind`, `platform`, `include_explicit`, `include_hidden`, `limit` | короткие карточки общей справки и точные `id` |
| `get_reference` | `item_id`, `section_id`, `cursor`, `max_chars`, `platform` | страница точной карточки или раздела и `next_cursor` |
| `find_roles_for_access` | `full_name`, `operations`, `config`, `child_path`, `include_conditional`, `cursor`, `limit` | роли-кандидаты, доказанные пробелы и точное сопоставление операций правам платформы |
| `get_role_access` | `role`, `config`, `full_name`, `cursor`, `limit`, `restriction_ref`, `restriction_cursor`, `max_chars` | страница объявленных прав роли либо окно одного явно выбранного RLS/шаблона |

Если загружено больше одной конфигурации, `config` обязателен там, где он
предусмотрен. Сервер не выбирает первую конфигурацию молча.

`search_reference` и `get_reference` условны и не принимают `config`: общая
справка — отдельный read-only провайдер, а не часть Registry конфигураций.
Обе role-операции также условны, но принадлежат выбранной конфигурации и
используют её generation.

Состав role-инструментов меняется без monkey patch и без автоматического
restart: после intake confirm, удаления источника или admin reload сервер под
одним lock добавляет либо снимает сразу обе схемы и отправляет стандартное
уведомление `tools/list_changed`. Современная сессия обновляет `tools/list` по
уведомлению; клиент без такой поддержки должен переподключиться. Пока ни
одного `roles=ready` нет, постоянная цена двух схем в контексте равна нулю.

## Рабочая последовательность для объявленных прав ролей

1. `list_configurations` — выбрать точную конфигурацию и убедиться, что её
   ролевой слой готов.
2. `search_objects` — получить точное полное имя корневого объекта.
3. `find_roles_for_access(full_name=..., operations=[...])` — получить
   кандидатов, доказанные пробелы и, только при полном покрытии, минимальный
   набор.
4. `get_role_access(role=...)` — прочитать descriptor и одну страницу прав
   выбранной роли. `full_name` ограничивает страницу одной точной целью;
   ссылка каждого RLS содержит упорядоченный массив `fields`, но не condition.
5. Если у страницы есть `next_cursor`, повторить вызов с тем же запросом и
   курсором. Текст RLS не приходит на этом шаге.
6. Только когда нужно само условие, передать его `restriction_ref` обратно в
   `get_role_access`; `restriction_cursor` дочитывает следующие окна до
   `null`.

Шесть начальных пользовательских операций сопоставляются ровно одному праву
платформы каждая: `read → Read`, `update → Update`, `insert → Insert`,
`delete → Delete`, `posting → Posting`, `use → Use`. Ответ всегда повторяет
это сопоставление. Resolver различает `explicit_false`,
`unconditional_true` и `conditional_true`: false никогда не предоставляет
доступ, а условный true участвует в кандидатах только при явном
`include_conditional=true`. Default-флаги роли сохраняются как свидетельство,
но недоказанное наследование не подмешивается в расчёт. Если у descriptor роли
нет `Rights.xml`, список прав пуст, а каждый отсутствующий default-флаг равен
`null` («не задано»), не `false`.

`find_roles_for_access` возвращает не больше 20 кандидатов за страницу,
`get_role_access` — не больше 100 прав. Окно одного RLS ограничено 256–8 000
символами; курсор позволяет дочитать исходный текст полностью. Одно XML-
ограничение не размножается по полям: `fields` сохраняет все цели в исходном
порядке, а пустой `condition` остаётся доступным условным RLS или шаблоном с
нулевой длиной текста. Состояния
`missing` и `error` возвращаются коротким структурированным ответом для
выбранной конфигурации, если каталог включён готовыми ролями другой
конфигурации.

Все role-ответы содержат generation и SHA-256 исходного snapshot и называют
результат **объявленными правами**, а не эффективным доступом пользователя.
Инструменты не читают пользователей и назначения ролей, не назначают и не
изменяют роли. Если пропустить `find_roles_for_access`, роль придётся выбирать
без серверного доказательства покрытия. Если пропустить `get_role_access`, не
будут проверены explicit false, условные права и точные дочерние пути
кандидата.

## Рабочая последовательность для общей справки

1. Выбрать предметный `domain`: `bsl`, `query`, `dcs`, `dcs_ui`,
   `configurator`, `development_tools` либо архивный `legacy`. Когда предмет
   известен, область нужно задавать: поиск без неё намеренно смешивает разделы.
2. `search_reference(query=..., domain=...)` — найти короткую карточку и точный
   `id`. `kind` — точный внутренний вид; первый поиск обычно выполняется без
   него. Неизвестные значения фильтров возвращают допустимый список, а не
   молчаливо пустую выдачу. Если широкая фраза не дала нужного, поиск
   повторяется с более короткой задачей и известным термином языка; `id` не
   угадывается.
3. `platform` не меняет текстовое совпадение, а проверяет применимость. Для
   вопроса по загруженной конфигурации версия берётся из
   `list_configurations`, для общего вопроса опускается. Известные границы
   появления, удаления и подтверждённого присутствия возвращаются в
   `availability` в обоих случаях. `limit` принимает значения от 1 до 50.
4. `include_explicit=true` добавляет служебные и словарные карточки внутри
   обычного раздела. Полностью специальные разделы открываются уже своим явным
   `domain`. `include_hidden=true` — только скрытые и legacy-материалы по
   прямой просьбе об устаревшем поведении.
5. `get_reference(item_id=...)` — прочитать точную карточку. Найденный раздел
   можно выбрать через `section_id`.
6. Если `continuation.next_cursor` не равен `null`, повторить `get_reference`
   с теми же `item_id`/`section_id` и полученным `cursor`. `max_chars`
   ограничивает страницу диапазоном 256–20 000 символов.

`platform` не скрывает доказанно недоступное совпадение молча: поиск отделяет
его в `unavailable_matches`, а карточка возвращает состояние доступности и
доказательства. Без `platform` итог сравнения остаётся `unknown`, но известные
факты не теряются: `introduced` называет версию появления, `removed` — удаления,
`known_present_in` — самый ранний подтверждённый полный снимок. Поле `reason`
объясняет эту границу одинаково для агента и дашборда.

Методы, свойства и объекты платформы ищутся не здесь, а через
`search_syntax` / `get_syntax`. Общая справка отвечает за конструкции BSL,
язык запросов, СКД, Конфигуратор и инструменты разработки.

Если пропустить `search_reference`, точный `item_id` придётся угадывать. Если
пропустить `get_reference`, останется заголовок, сигнатура и причина
совпадения, но не полный материал. Если не продолжить чтение по курсору,
длинная карточка останется неполной.

## Рабочая последовательность для метаданных

1. `list_configurations` — выбрать точное имя конфигурации и увидеть, каких
   источников не хватает.
2. `search_objects` — перевести пользовательское название в полное имя.
3. `get_object` — получить фактические поля и свойства.
4. `get_related` — проверить непосредственные зависимости.
5. `search_syntax` и `get_syntax` — проверить синтаксис и описанные платформой
   таблицы запросов для версии этой конфигурации.

Если пропустить `get_object`, агент увидит имя, но не узнает точные реквизиты,
периодичность регистра, виртуальные таблицы и производные имена полей. Такой
запрос часто выглядит правдоподобно и падает уже в 1С.

`get_related` возвращает только один шаг. Глубокий обход через универсальные
объекты быстро превращается в большой правдоподобный, но бесполезный список.
Нужная цепочка строится повторными вызовами по выбранным объектам.

## Рабочая последовательность для кода

1. `list_configurations` — проверить наличие провайдера `modules`.
2. Если задача зависит от фактической активности расширений — вызвать
   `list_extensions`. Без отдельного снимка он отвечает `unknown`.
3. `search_procedures` — получить точный адрес процедуры.
4. `get_procedure` с адресом модуля — сначала оглавление; с
   `Модуль::Процедура` — тело.
5. `get_callers` — увидеть последствия изменения.

Потери при пропуске шагов:

- без `search_procedures` приходится угадывать точный модуль и имя;
- без `get_procedure` нет тела, контекста компиляции и аннотации расширения;
- без `get_callers` не видны вызовы, подписки, регламентные задания и формы,
  которые зависят от процедуры.

`extension` выбирает ровно одно расширение. Если он не задан, инструменты
работают только с основной конфигурацией и не подмешивают чужой код.

`list_extensions` читает независимый point-in-time JSON-снимок, сделанный в
текущем сеансе и его текущей области данных. Он различает `snapshot`, `stale`
и `unknown`, показывает UTC-время и SHA-256 источника. `stale` означает, что
версия конфигурации разошлась со структурной выгрузкой, платформа изменилась
или сама 1С сообщила об изменении набора расширений после старта сеанса.
Автоматического срока годности нет: возраст снимка виден явно, а произвольный
TTL выдавал бы догадку за факт.

Позиция действующего расширения — ровно место в массиве
`ИсточникРасширенийКонфигурации.СеансАктивные`, возвращённом платформой. Справка
метода `Получить` не обещает, что это порядок исполнения модулей; для цепочки
конкурирующих `&Вместо` по-прежнему нужно наблюдение на безопасной базе.

`scope` — явная область, например `Документ.ЗаказПокупателя` или
`ОбщийМодуль.ОбменаДанными`. Обычный поиск поднимает её модули в выдаче.
Распознанное типовое событие разрешается только внутри области; без `scope`
сервер показывает каноническое имя и число реализаций, а не случайный адрес.

`get_procedure` ограничивает окно тела максимум 200 строками. Продолжение
читается новым вызовом с `start_line`; это удерживает большие модули вне
контекста, пока они не понадобились.

## Что возвращает `get_object`

`detail` принимает:

| Значение | Состав |
|---|---|
| `brief` | основные свойства и предупреждения |
| `fields` | плюс реквизиты, табличные части и таблицы запроса |
| `full` | полный доступный состав, включая связи и кодовые сведения |

Для регистров карточка строит таблицы запроса с реальными именами полей:
остатки, обороты, срезы, движения с корреспонденцией и субконто. Эти имена не
совпадают буквально с именами ресурсов в конфигураторе, поэтому карточка
является обязательным источником перед написанием запроса.

Если загружен код, карточка показывает модули, процедуры, экспортность,
контексты компиляции, обработчики форм и агрегаты покрытия. Нулевой счётчик не
доказывает отсутствия, если соответствующая часть корпуса отмечена как
непрочитанная.

Native generation расширения хранится отдельно от базы и требует явно
выбранного родителя. При выборе одного расширения Registry строит resolved
context на запрос: собственные объекты добавляются, а borrowed overlay
применяется только к существующей цели. После полного обновления базы
сохранённые object/field edges перепроверяются без исходного ZIP; исчезнувшая
цель получает `target_missing`, поэтому orphan-overlay не маскируется под
собственный объект. Собственные объекты, код и роли расширения при этом
остаются доступны.

Эта статическая связь ничего не говорит об активности расширения. Активность
показывает только `list_extensions` из отдельного runtime-снимка; отсутствие
снимка означает `unknown`, а не disabled. Без параметра `extension` никакой
extension-layer в контекст не подмешивается.

## Источники независимы

| Источник | Что добавляет | Что теряется без него |
|---|---|---|
| Структура конфигурации | объекты, поля, связи, таблицы запроса, предопределённые | поиск по метаданным и точная структура объекта |
| Код конфигурации | процедуры, тела, места вызовов, элементы и события форм, база происхождения, `get_callers` | анализ основной реализации и доказательство структурной дельты |
| Код расширения | собственная структура, отдельный корпус процедур и тел, места вызовов, роли и borrowed overlays | изменения конкретного расширения и их проверяемые связи с базой |
| Снимок активности расширений | зарегистрированные, действующие и не применённые расширения текущего сеанса | активность, область и порядок ответа платформы (`unknown`) |
| Справка платформы | методы, свойства, события, таблицы запросов, доступность и примеры | синтаксис встроенного языка и версионные таблицы запросов |

Код конфигурации полезен без кода расширения. Код расширения полезен без кода конфигурации. Структура полезна без обоих. Статус каждого корпуса публикуется отдельно.

## Синтаксис и версия платформы

`search_syntax` ищет по `shcntx_ru.hbk`. `kind` позволяет ограничить выдачу:
`method`, `property`, `event`, `object`, а также `query_table` и `query_field`
для таблиц запросов, описанных самой версионной справкой платформы.

Несколько справок платформы сливаются в единый индекс. Для одноимённого
элемента сохраняются варианты сигнатур и доступности, а не произвольно
выбранная последняя запись. Если точной справки версии конфигурации нет,
ответ сообщает, использована более старая или более новая.

`get_syntax` нужно вызывать перед применением найденной функции на старой
платформе. Недоступный элемент помечается, а известная замена приводится рядом.
Контекст доступности так же важен, как версия: серверный метод может
существовать в платформе, но не компилироваться на клиенте.

## Границы провайдера кода

- Поиск по словам индексирует экспортные процедуры; точное имя находит и
  неэкспортные.
- Сервер не выполняет BSL и не доказывает, какая строка сработала в runtime.
- Наличие процедуры в файле не доказывает, что конфигурация скомпилирована.
- Формы представлены плоской структурой доступных элементов и событий.
- Динамические вызовы по вычисляемой строке не разрешаются в точный модуль.
- Значения документов, справочников и регистров информационной базы не
  загружаются вообще.

Формат и границы источника кода подробнее описаны в
[modules-provider-design.md](modules-provider-design.md), а типовые события —
в [standard-procedure-intents.md](standard-procedure-intents.md).
