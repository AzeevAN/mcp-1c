# Управление данными и командная строка

`data/` — полное состояние установки. В нём находятся исходники, разобранные
индексы, кэш, реестр и локальный словарь. Каталог не входит в git и переносится
отдельно.

## Структура каталога

| Путь | Назначение | Восстановимость |
|---|---|---|
| `bootstrap/` | ZIP структуры и `.hbk`, которые проверяются при старте | исходники оператора |
| `incoming/` | ZIP-кандидаты файловой выгрузки для on-demand intake | исходники оператора |
| `intake-v2/` | managed browser candidates, durable jobs и незапубликованные preview | управляется сервером; активным Registry не является |
| `sources/` | сохранённые сервером исходные архивы и JSON-снимки | нужны для восстановления Registry |
| `index/` | разобранная справка и кэш поисковых и ролевых индексов | часть расходная, часть является единственной разобранной копией справки |
| `modules/` | опубликованный код основных конфигураций | восстанавливается повторным разбором incoming-архива |
| `extensions/` | опубликованный код расширений | восстанавливается повторным разбором incoming-архива |
| `logs/` | журналы покрытия кода schema v1 | пересоздаются при разборе корпуса |
| `registry.json` | учёт источников и их состояния | авторитетный снимок установки |
| `dictionary.json` | локальные псевдонимы и синонимы | авторитетное локальное знание |
| `incoming-state.json` | расходный снимок статусов incoming | может быть пересобран сканированием |

Кэш расходный: несовпадение штампа, повреждение или отказ записи не должны
ронять чтение. Исходники и `registry.json` расходными не являются.

Готовый role snapshot активного native generation строит в `index/cache/`
отдельный файловый SQLite-индекс объявленных прав. Он не является внешней БД и
не заменяет канонический snapshot: при несовпадении кода, semantic/physical
hash или `quick_check` индекс пересобирается. Если каталог кэша недоступен для
записи, provider использует временный файловый индекс и удаляет его при
закрытии; весь корпус прав в память процесса не поднимается.

## Добавление структуры и справки

Это путь для ZIP, созданного внешней обработкой проекта
`ВыгрузкаСтруктурыКонфигурации`, а не для штатной выгрузки Конфигуратора в
файлы. Внутри ожидаются schema-v1 manifest и чанки `objects/*.xml` либо
`objects/*.json`. На работающем сервере рекомендуемый путь — форма «Загрузить»
в дашборде; `bootstrap/` удобен для первого запуска.

Самый простой путь — положить файлы в `bootstrap/` до старта:

```bash
sudo install -o 10001 -g 10001 -m 0640 \
  СтруктураКонфигурации.zip /srv/mcp1c/data/bootstrap/
sudo install -o 10001 -g 10001 -m 0640 \
  shcntx_ru.hbk /srv/mcp1c/data/bootstrap/
```

При старте одинаковый подписанный пакет не разбирается повторно: используется
SHA-256. Обновление общей справки поставляется новым образом.

Добавление в работающий Registry:

```bash
docker compose exec mcp1c \
  python -m mcp1c.cli reg-add --data /data /data/bootstrap/СтруктураКонфигурации.zip
```

После изменения Registry отдельным процессом работающий сервер нужно
перечитать:

```bash
curl -X POST \
  -H 'X-Admin-Token: ВАШ_ADMIN_TOKEN' \
  http://127.0.0.1:5001/admin/reload
```

В дашборде загрузка и reload объединены в одну операцию.

## Двухфазная загрузка файловой выгрузки

ZIP команды **Конфигуратор → Конфигурация → Выгрузить конфигурацию в
файлы… → Архив** проходит через общий intake. До 4 ГиБ его можно передать в
managed staging через `POST /api/v1/sources/intake/upload`; архивы любого
размера можно поместить в `data/incoming/`. Третий вариант — заранее настроенный сервером
read-only ZIP, каталог ZIP или корень распакованной выгрузки через
`MCP1C_CONFIG_SOURCE`.

Предел 4 ГиБ действует только при передаче browser-upload. После приёма
браузерный ZIP и ZIP из `incoming` одинаково читаются без фиксированных
лимитов размера элемента, коэффициента сжатия и общего распакованного объёма.
Для `incoming` не ограничен и сырой размер ZIP. Сервер проверяет весь состав
обоих архивов на безопасные пути, дубликаты, symlink, специальные файлы,
шифрование и предел 100 000 записей, а при чтении — CRC и неизменность
архива. Проверка `Configuration.xml` ограничена 8 МиБ для обоих путей.
У настроенного read-only источника сырой ZIP или каталог также не
проходит через HTTP-лимит, но открытые parser-ом элементы остаются в общем
ресурсном бюджете.

`GET /api/v1/sources/intake` по запросу обновляет список кандидатов. Затем
`POST /api/v1/sources/intake/start` строит durable preview для `create`
или `update_full`, а `POST /api/v1/sources/intake/confirm` отдельно
публикует проверенное поколение. `POST /api/v1/sources/intake/discard` явно
отменяет неопубликованный preview и удаляет его job/work. Одновременный
intake snapshot читает список jobs и их payload согласованно: он видит
состояние до либо после удаления, но не отвечает временным HTTP 409. Прежняя
универсальная форма «Загрузить» не предназначена для такого ZIP;
browser-передача использует именно `/api/v1/sources/intake/upload`.
Произвольный путь в HTTP не принимается.

На странице «Источники» эти операции собраны в блоке «Полная файловая
выгрузка». Кнопка «Проверить обновления» явно обновляет кандидатов из
`incoming` и read-only источника; автоматического polling списка нет. Для
каждой новой конфигурации доступно создание, для существующей — полное
обновление; публикация доступна только
после послойного preview. Готовый preview сразу появляется в списке без
ручного обновления страницы и уже сохранён на сервере. Закрытие диалога
оставляет его для продолжения после обновления страницы или рестарта, а явная
отмена удаляет его. После публикации временные collection/materialized-копии
и managed browser-upload удаляются; компактный commit result сохраняет
идемпотентность повторного
`confirm`. Каскадное удаление конфигурации также удаляет связанные intake-job
основы и расширений, но никогда не меняет `data/incoming/` и read-only источник.

## Управление локальной общей справкой

Образ содержит проверенную release-копию в
`/app/reference/reference.mcp1cref`; bind mount `/data` её не перекрывает.

Артефакт не загружается через dashboard и не заменяется во время работы.
До открытия вложенной SQLite сервер проверяет строгий ZIP-контейнер,
канонический `manifest.json`, detached-подпись Ed25519 и SHA-256.

В Compose-профиле `MCP1C_ALLOW_SELF_RESTART=1`: кнопка «Перезапустить и
применить» отвечает до остановки процесса, затем `restart: unless-stopped`
возвращает тот же контейнер. Дашборд ждёт новый `runtime_id` через `/health` и
просит войти заново. Это не пересборка образа и не замена контейнера.
Backend полного restart общий: он допускает запрос только при pending
capability-настроек и возвращает массив `reasons`. Экран «Дополнительные
модули» отдельно просит подтвердить перезапуск.

Общая справка не имеет операций загрузки, замены или удаления. Она обновляется
только вместе с новым образом.

Для обновления встроенной версии заменяют только tracked-файл
`release-assets/reference/reference.mcp1cref` уже подписанным пакетом, затем
проверяют подпись, manifest, schema и deployment-тесты до сборки образа.
Приватный signing key, исходные HBK и `reference-lab` в release-контекст не
добавляются.

Не монтируйте Docker socket ради этой кнопки: сервер завершает только себя и
полагается на уже настроенный внешний supervisor. Для bare-запуска capability
по умолчанию выключена.

## Снимок активности расширений

Статическая файловая выгрузка расширения показывает код и назначение, но не
доказывает, применено ли расширение в конкретном сеансе. Для этого используется
отдельный файл `СнимокРасширений_*.json` из BSL-модуля
`exporter-1c/dist/СнимокРасширений_УправляемаяФорма_JSON.bsl` (платформа
8.3.8+). Инструкция создания обработки — в
[exporter-1c/README.md](../exporter-1c/README.md).

Порядок действий:

1. Сначала загрузить schema-v1 структуру конфигурации.
2. Открыть обработку снимка в нужном сеансе и области данных 1С.
3. Сохранить JSON и загрузить его через страницу «Источники» либо CLI:

   ```bash
   python -m mcp1c.cli reg-add --data data \
     /путь/к/СнимокРасширений_Конфигурация_2026-08-29.json
   ```

4. Вызвать MCP-инструмент `list_extensions`.

Если структурной конфигурации ещё нет, загрузка JSON отказывает: runtime-снимок
нельзя привязать догадкой. Последняя загрузка заменяет прежний снимок этой
конфигурации. Без него состояние `unknown`; при несовпадении версии или
платформы конфигурации либо точном признаке изменения набора после запуска
сеанса — `stale`. Сам признак доступен с платформы 8.3.22; на 8.3.8–8.3.21 в
JSON записывается `null`, а не ложное `false`.
Время снятия всегда показывается, автоматический TTL не применяется.

JSON не кладётся в `bootstrap/`: это point-in-time состояние, которое должно
загружаться осознанно. После `reg-add` из отдельного процесса работающему
серверу нужен `/admin/reload`, как и для других изменений Registry; дашборд
делает сохранение и публикацию в одном процессе.

## Выгрузка конфигурации в файлы

Это отдельный источник кода, а не ZIP структуры по schema v1. Создайте его в
Конфигураторе последовательностью:

1. Откройте нужную конфигурацию.
2. Выберите **«Конфигурация → Выгрузить конфигурацию в файлы…»**.
3. В диалоге «Выгрузить файлы конфигурации» выберите **«Архив»**, не
   «XML-файлы».
4. Сохраните полученный ZIP.

Архив содержит `Configuration.xml`, модули и формы. Не используйте здесь `.cf`
из «Сохранить конфигурацию в файл», `.dt` информационной базы или ZIP
`СтруктураКонфигурации_*.zip` нашей внешней обработки.

ZIP с кодом не кладётся в `bootstrap/` и не передаётся через форму «Загрузить»:
он может занимать гигабайты и не должен разбираться на каждом старте.

1. Сначала загрузите ZIP структуры через дашборд и убедитесь, что родительская
   конфигурация появилась в Registry.
2. Положите архив Конфигуратора в `data/incoming/` с владельцем `10001:10001`.
3. Дождитесь завершения копирования, откройте или обновите страницу «Источники»
   с административным токеном.
4. Выберите родительскую конфигурацию, если их несколько. Если конфигураций
   нет, кнопка «Разобрать» не показывается: код не к чему привязать.
5. Запустите разбор и дождитесь итогового состояния.
6. Проверьте три таблицы покрытия и полный JSON-журнал.

Единая диагностика различает состояния `готов`, `готов с ограничениями` и
`ошибка`. Для форм отдельно считаются полностью, частично и не прочитаны.
Короткая сводка показывает первые 20 причин и число оставшихся, полный журнал
сохраняет причины каждой формы. Одни и те же агрегаты видны в
`list_configurations`, `reg-list` и `/sources`. Нулевой счётчик не доказывает отсутствие процедуры или формы, если соответствующая часть корпуса не прочитана.
При `status=error` войдите как администратор и откройте карточку
корпуса: страница покажет bounded техническую причину без имени
исходного ZIP. Полный traceback пишется в server log. Ссылка на JSON-
журнал покрытия появляется только для текущего готового индекса;
физически оставшийся старый файл при ошибке не публикуется.
Native source-B generation создаёт тот же журнал после успешного переключения
pointer. Если расходный файл отсутствует или не совпадает с текущим индексом,
restart восстанавливает его из активного generation snapshot без исходного ZIP.

Индекс сохраняет локаторы, агрегаты покрытия, тела модулей; сырая запись формы
остаётся доступна по локатору. Строгий roundtrip проверяет, что cold и warm
загрузки совпадают; семантически повреждённый или read-only кэш считается
промахом и уходит на безопасную пересборку без публикации битого состояния. Размер одной
процедуры ограничен 256 МиБ, одной записи формы — 512 МиБ. Локальные причины каждой формы остаются в журнале.

Подробный формат приёма — [modules-intake-design.md](modules-intake-design.md),
провайдер — [modules-provider-design.md](modules-provider-design.md).

## Локальный словарь

Встроенная терминология живёт в коде и одинакова для всех установок. Локальные
названия конкретного внедрения хранятся только в `data/dictionary.json`.

Начинать диагностику поиска следует с:

```bash
docker compose exec mcp1c \
  python -m mcp1c.cli dict-show --data /data --all
```

Команды:

```bash
# Группа взаимозаменяемых слов
python -m mcp1c.cli dict-synonyms --data data слово1 слово2
python -m mcp1c.cli dict-synonyms --data data слово1 слово2 --remove

# Фраза, ведущая к одному или нескольким точным объектам
python -m mcp1c.cli dict-alias --data data \
  'человеческая фраза' 'Справочник.Пример'
python -m mcp1c.cli dict-alias --data data \
  'человеческая фраза' --config ИмяКонфигурации --remove
```

HTTP-правка словаря требует `ADMIN_TOKEN`. Изменение применяется сразу без
пересборки индексов.

## Стенд `mcp1c.bench`

Стенд измеряет качество, а не превращает его в хрупкий процентный assert.

| Ключ | Значение |
|---|---|
| `--data` | каталог Registry |
| `--sets` | ручные наборы через запятую, например `modules-procedures` |
| `--auto` | автоматические наборы точных и одноимённых запросов |
| `--config` | конфигурация для `metadata` и `procedures` |
| `--extension` | отдельный корпус расширения для `procedures` |
| `--limit` | глубина выдачи |
| `--save` | JSON текущего прогона |
| `--baseline` | JSON для сравнения |
| `--check-notes` | сверка ожидаемых пометок ручного набора |

Домены наборов: `syntax`, `metadata`, `procedures`.

```bash
PYTHONPATH=src .venv/bin/python -m mcp1c.bench \
  --data data \
  --config ИмяКонфигурации \
  --sets roznica-metadata,modules-procedures \
  --auto \
  --limit 10 \
  --check-notes \
  --save data/bench/current.json
```

Сохранённый JSON является производным от локальных данных и остаётся внутри
`data/`.

## Ручной запуск `mcp1c.server`

Полный набор флагов:

| Флаг | Назначение |
|---|---|
| `--data PATH` | каталог данных, по умолчанию `data` |
| `--transport streamable-http|stdio` | транспорт |
| `--host HOST` | адрес HTTP, по умолчанию `127.0.0.1` |
| `--port PORT` | порт HTTP, по умолчанию `8000` |
| `--trust-proxy-headers` | доверять `X-Forwarded-*` только за своим reverse proxy |
| `--require-writable-data` | создать рабочие подкаталоги и проверить запись; Docker включает автоматически |
| `--require-tokens` | до старта потребовать разные безопасные `API_TOKEN` и `ADMIN_TOKEN`; Docker включает автоматически |

```bash
PYTHONPATH=src .venv/bin/python -m mcp1c.server \
  --host 127.0.0.1 --port 8000 --data data
```

Флаг проверки записи отделён намеренно: контейнер — изменяемый сервер и обязан
уметь загружать источники, тогда как локальный `stdio` можно осознанно
направить на уже готовый read-only Registry.

`MCP1C_ACCESS=local|http|https-proxy` задаёт доверие к сетевой топологии.
Для bare-запуска прямой `http` дополнительно требует `--host 0.0.0.0` либо
конкретный IP; Compose вместо этого использует `MCP1C_BIND_ADDRESS`.

## Внутренние capability-модули

Capability-модули — startup-only шов для заранее известных внутренних модулей
mcp-1c, а не загрузчик сторонних плагинов. Постоянный desired-набор хранится в
общем серверном файле `data/server-settings.json`, schema v2:

```json
{
  "version": 2,
  "capabilities": {
    "enabled": ["module_source_download"]
  }
}
```

Если файла нет, сервер применяет встроенные начальные значения: все прежние
модули выключены, а `module_source_download` включён. Дашборд сохраняет полный
набор настроек в версии 2. В ней `module_source_download` — отдельный элемент
массива `capabilities.enabled`; пустой массив выключает его. Существующий файл
версии 1 продолжает включать скачивание полного модуля до сохранения настроек;
при сохранении он переводится на версию 2. Пустой список прежних capability-
модулей сохраняет основной каталог `tools/list` и не импортирует реализации.
Capability `role_access` по умолчанию выключен: это только видимость
`find_roles_for_access` и `get_role_access` в MCP-каталоге. Role layer и его
индексы при этом всё равно строятся и сохраняются. Включение или выключение
меняет только desired-настройку и применяется после полного перезапуска;
загрузка, удаление или смена A/B не посылают `tools/list_changed`. При
включённом `role_access` обе ручки остаются зарегистрированы и для A-only,
где возвращают `unsupported_by_source`, и для B с состояниями
`available`/`present_empty`/`load_error`.
Цена `module_source_download` в `tools/list`: 1 инструмент, 2 744 байта
и 466 токенов (`o200k_base`, 2026-09-26); воспроизведение:
`.venv/bin/python tools/measure_capability_context.py module_source_download --check`.
Цена `role_access` в `tools/list`: 2 инструмента, 7 170 байт и 1 245 токенов
(`o200k_base`, 2026-09-22); воспроизведение:
`.venv/bin/python tools/measure_capability_context.py role_access --check`.
Создание форм и метаданных перенесено в локальные skills; имена прежних
capability `forms` и `metadata_authoring` удалены из каталога и панели
переключателей. Семь authoring-инструментов не публикуются в `tools/list`.
Старые значения этих двух имён в сохранённом `server-settings.json`
игнорируются при чтении; следующее сохранение настроек удаляет их из файла.
Новые запросы `PUT` с удалёнными именами отклоняются.

Файл ограничен 64 КиБ, обязан быть обычным файлом с версией 1 или 2 и точной
схемой соответствующей версии; неизвестное имя, повтор или повреждённая схема
fail-closed останавливают startup до создания Registry. Настройки сохраняются
атомарной заменой и меняются через дашборд, а не через переменные окружения.
При выключенном `module_source_download` после полного перезапуска из
`tools/list` исчезает `get_module_source_file`, а HTTP-маршрут
`GET /api/v1/modules/source` больше не регистрируется.

Перед добавлением сервер проверяет весь набор имён против ядра, условных
reference/role-tools и других модулей; частично зарегистрированный набор при
ошибке откатывается. `GET /api/v1/capabilities` с правом администратора отдаёт
`available`, фактический startup-набор `active`, сохранённый `desired` и
`pending_restart`. `PUT /api/v1/capabilities` принимает полный JSON-массив
`enabled`, требует admin и same-origin для cookie-сессии и атомарно заменяет
только capability-секцию; неоднозначный JSON с повторяющимися ключами
отклоняется до записи. В дашборде этот контракт доступен на экране
«Дополнительные модули». Изменение файла не меняет живой `tools/list`: общий
`POST /api/v1/server/restart` разрешён при pending capability,
перечисляет причины и применяет новый набор только после полного старта процесса.
Экран требует явно сохранить desired-набор и отдельно подтвердить полный restart,
если self-restart разрешён; иначе он оставляет операторскую инструкцию.
`tools/list_changed` для capability startup-события не отправляется.

Экран «Дополнительные модули» показывает каждый модуль отдельной карточкой:
название, технический id, краткое описание, число инструментов, измеренную цену
контекста, tokenizer и дату замера. Состояния `Включен`, `Выключен` и `Изменён`
различаются отдельно от сводки «Активно сейчас»/«Сохранённый выбор». В верхней
сводке также показывается сумма измеренной стоимости контекста всех активных
модулей для старта MCP-сессии. Dashboard использует две согласованные темы
одной Paper-системы: `Paper Light` и `Paper Dark`.

Главная страница dashboard служит оперативной сводкой: показывает готовность
сервера, опубликованные конфигурации, объекты и справки платформы, фактически
активные capability-модули с измеренной стоимостью контекста, состояния,
требующие внимания, и быстрые переходы к запросам, связям, источникам и
настройке модулей. Неизмеренная стоимость остаётся явной и не подменяется
нулём.

После изменения bind-mounted `server-settings.json` bare-процесс нужно полностью
остановить и запустить заново; для Compose достаточно
`docker compose restart mcp1c`, потому что новый Python-процесс перечитает файл.
Управляемый dashboard restart выполняет тот же полный restart процесса.
