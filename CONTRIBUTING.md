# Как править проект

Спасибо за интерес. Ниже — правила, по которым живёт репозиторий. Они не
формальность: каждое появилось после того, как без него что-то сломалось.

## Прежде чем писать код

Заведите issue и опишите задачу. Проект ведёт один человек, и большой PR
«сюрпризом» может разойтись с уже принятыми решениями — часть предложений
уже разбиралась и была отклонена с цифрами.

## Язык

**Весь текст для человека — русский**: документация, комментарии в коде,
сообщения коммитов, описания PR. Технические идентификаторы (имена файлов,
функций, полей, команд, переменных) остаются как есть.

Комментарии объясняют **почему**, а не что делает строка.

## Запуск и тесты

```bash
python3 -m venv .venv
.venv/bin/pip install --require-hashes -r requirements-dev-lock.txt
.venv/bin/python -m pytest          # 1788 тестов (прогон 2026-09-02)
```

Тесты **не зависят от содержимого `data/`**: проприетарных выгрузок и справки
в репозитории нет, а тест, который без них не запускается, бесполезен. Всё
нужное собирается синтетически в `tests/conftest.py`. Тест, требующий реальных
данных, принят не будет.

Проверяется наблюдаемое поведение, а не внутреннее устройство: «индекс не
построен заново», «выдача совпала», «старт не упал».

**Качество поиска тестами не проверяется** — оно меряется стендом
(`python -m mcp1c.bench`). Пороги в процентах ломались бы от каждой правки
словаря, поэтому стенд печатает цифры, а решение принимает человек. Файлы
`tests/queries/*.json` — не тесты, а наборы запросов для стенда.

## Данные — `data/`

**Каталог `data/` целиком вне git.** Это том, который монтируется в
контейнер: источники, разобранные индексы, кэш, реестр, локальный словарь.

Правило шире, чем «не коммитить `.hbk`», и это разница, на которой уже
споткнулись: исходники в git не попадали, а **производный от них разобранный
индекс справки — попал** и пролежал в истории 20 коммитов. Контент тот же,
просто распакованный: 24 331 описание и 1 502 примера кода фирмы «1С».
Историю переписывали `git filter-repo`.

Проверять так: не «это `.hbk`?», а **«это лежит в `data/`?»**. Если да — вне
git, независимо от того, чем оно получено.

## README — правило, которое нарушать нельзя

**Функциональность без записи в README не считается сделанной.**

Появился инструмент, флаг, CLI-команда, источник данных, переменная
окружения, способ подключения — README правится **тем же коммитом**, что и
код. Changelog сохраняет историю изменений, а README остаётся основным
документом для человека, который впервые открывает проект.

В README обязаны быть описаны: все инструменты с параметрами и порядком
вызовов, все CLI-команды со всеми ключами, все источники данных, все
переменные окружения и токены, и **цифры замеров вместе с командой, которой
они воспроизводятся**. Цифра без команды устаревает молча.

Раздел разросся так, что README перестал читаться, — суть остаётся в README,
подробности уезжают в `docs/` со ссылкой отсюда. Молча выкидывать нельзя:
отсутствие раздела неотличимо от отсутствия возможности.

## Документы — `docs/`

В репозиторий входят только документы-контракты: [формат
выгрузки](docs/schema-v1.md), [граница источников](docs/data-sources.md),
[дашборд](docs/dashboard-design.md), [приём выгрузки кода](docs/modules-intake-design.md),
[провайдер кода](docs/modules-provider-design.md), а также пользовательские
руководства по [клиентам](docs/clients.md),
[инструментам](docs/tools.md), [операциям](docs/operations.md) и
[архитектуре](docs/architecture.md). Публичные документы должны быть
самодостаточными и не ссылаться на материалы, которых нет в репозитории.

Документ публикуется, если на него ссылается README **или** он описывает
внешний контракт. Добавляете такой — снимите его из `.gitignore` явной
строкой-исключением рядом с остальными.

## Зависимости

По умолчанию — **стандартная библиотека**. Это не жёсткий запрет: если
внешняя библиотека действительно упрощает или ускоряет, о ней нужно сказать
самому. Обоснование по форме: цифры до и после, цена (размер образа,
сопровождение, ещё один процесс, который может лежать) и чего именно не
хватило в stdlib. **Без цифр не предлагать.**

Сейчас зависимостей три, у каждой замер в `CHANGELOG.md`: `mcp` (SDK
протокола, заперт в `server.py`), `numpy` (постинги индекса, заперт в
`search.py`), `snowballstemmer` (стемминг русского, заперт в `search.py`).

Нижние границы публичного пакета живут в `requirements.txt` и
`pyproject.toml`, воспроизводимые установки — в сгенерированных
`requirements-*-lock.txt` с hashes. Docker и CI ставят только lock с
`--require-hashes`; вручную менять его нельзя. Порядок одновременного
обновления всех lock-файлов и локального dependency audit описан в
[архитектурном руководстве](docs/architecture.md#зависимости).

Тяжёлая инфраструктура (Elasticsearch, векторные БД, эмбеддинги) не
добавляется «на всякий случай». Сначала измерение, потом решение.

## Обработка выгрузки — `exporter-1c/`

- Правим **только `src/`**. `dist/` — результат сборки, руками не трогаем.
- После правки: `python3 exporter-1c/build_modules.py`.
- Сборка двухфазная: сначала формируются и проверяются все четыре BSL-файла,
  затем публикуется полный набор. Любая ошибка обязана оставить прежний
  `dist/` без частично обновлённых вариантов.
- Два `.epf` в `dist/` собираются в конфигураторе. Меняется модуль —
  пересобрать и обработку, тем же коммитом, иначе `.epf` молча разойдётся
  с `dist/*.bsl`.
- XML-варианты обязаны компилироваться на **8.3.5**: ни `ЗаписьJSON`, ни
  `СтрРазделить`, ни прочих возможностей 8.3.6+. Сборщик это проверяет и
  падает с ошибкой — проверку не ослаблять.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/), описание на
русском. Область (`scope`) — по каталогу: `exporter-1c`, `loader`, `syntax`,
`graph`, `docs`, `server`.

```
feat(syntax): парсер справки платформы с доступностью и версиями
fix(exporter-1c): предопределённые берутся с объекта метаданных
docs: правило источников данных
```

Коммитим **после каждой законченной находки или исправления**, не копим.
Изменения в `CHANGELOG.md` идут тем же коммитом, что и сама работа.

## Changelog

Формат [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии по
SemVer, свежее сверху. Сверх стандарта есть раздел **`Найдено`** — выясненные
факты о 1С и её форматах, и он здесь важнее остальных: проект во многом
состоит из выяснения, как всё устроено на самом деле. Отдельно фиксируются
**опровергнутые гипотезы** — вывод вместе с тем, что его опровергло.

## Проверка перед отправкой PR

- Тронул `src/mcp1c/` → прогнал `pytest`, все зелёные.
- Тронул `exporter-1c/src/` → пересобрал `dist/`, сборщик прошёл без ошибок.
- Добавил или изменил функциональность → правил `README.md` тем же коммитом.
- Показал цифру → рядом стоит команда, которой она снимается, и дата прогона.
- Правил разбор (`syntax_parser`, `loader`) → перезагрузил
  источник, иначе проверяешь старый разбор: разобранный индекс лежит в
  `data/index/` и ни рестарт, ни пересборка образа его не трогают.
- Добавил страницу дашборда → открыл её тем же путём, что человек: по ссылке
  из навигации, без параметров в адресе.
- **Заявляешь, что работает → показываешь вывод, а не утверждение.**
